# What-if runner

`tools/whatif/runner/server.mjs`: a local web server that serves the built simulator and runs the what-if optimizer (`tools/whatif/optimize.mjs`) for it, at the lowest operating-system priority on every core. Test: `tools/test/whatif-runner.mjs`.

## Core and shell

The search is one function, `main(settings, seams)` in `tools/whatif/core.mjs`, which imports no `fs`, `process`, `os` or `child_process` (nor does anything it imports: the game tables are static JSON imports, the engine's `Equipment` a static import in `dominated.mjs`). `tools/whatif/optimize.mjs` is the Node shell: it turns the command line into flags (`options.mjs`: `parseFlags`, `makeArg`), loads the data, and hands the core the Node side of each seam from `tools/whatif/node-shell.mjs`. The shell imports `engine.mjs` first (it registers the loader hooks) and the core after it. A test of the search code reads `core.mjs` as text (the search no longer runs on import).

| Seam | Core sees | Node shell |
|---|---|---|
| `data` | `{ setups, market, pricesTimestamp, exportData, userTrig }` | `loadNodeData`: `readParty`, the price snapshot file, `--export`, `--trigger-cands` |
| `store` | `load()` (every saved record), `put(record)`, `readAux(name)`, `writeAux(name, value)` | `createNodeStore`: `--cache-from` files then `<out>/runs.jsonl` (appended per run); `<out>/need.json`, `<out>/probe.json` |
| `pool` | `run(task)` resolves with the run's result or `null` once killed | `createNodePool`: forked `batch.mjs --child` processes (made on demand, kept for the search, at this process's priority); `kill()` on a stop |
| `sink` + `stop` | `progress(p)`, `partial(snapshot)`, `round(r)`, `stopped(snapshot)`, `final(snapshot, markdown)`; `stop.requested` | `createNodeSink`: `progress.json`, `partial.json`, `rounds.jsonl` (one line per round), `result.json`, `result.md` and the IPC messages (`progress`, `partial`, `round`); the `'stop'` message sets `stop.requested` |
| `hash`, `sim` | `hash(text)`; `sim = { runParty, measureNeed, buildDtos, Trigger }` | `sha1`; the real functions of `engine.mjs` and `src/combatsimulator/trigger.js` |

The core keeps the loaded records in memory (the estimates read them synchronously); `main` resolves with `{ stopped }` and the shell exits with code 3 when it is true.

## The rounds search (step 2 of the core split)

The fixed stages (screen at 1 seed, halvings at growing seeds and hours, `cutPool`) are replaced by one driver, `race()` in `tools/whatif/core.mjs`, which keeps refining until the search is stopped or settles. Its pure part is `tools/whatif/rounds.mjs` (no I/O, test `tools/test/whatif-rounds.mjs`); the design is `docs/what-if/anytime-search-design.md` (private repo). It uses only the seams: its output is `sink.round(rec)`.

- **Unit and rounds:** the unit is one seed at `--unit-hours` (50). Round 1 gives every candidate `--first-seeds` (2) seeds; each later round gives every candidate that is not paused `--round-seeds` (1) more. The base gets `baseMult` x the largest seed count of the round (a base run is shared by all candidates, so the cost is the same as before). Every candidate is tested every round (`contention`), so a paused candidate resumes by itself when the leaders' lower bounds fall or its upper bound rises; its runs stay in the store.
- **Pools and pausing:** two pools, free (cost 0) and paid, per player in the foods and drinks stages (`byPlayer`). Ranking inside a pool is the old rank (pool value: the buyer's net on the profit goal, divided by the cost for a paid candidate = payback order, floored at 0; the party gain on EXP). A candidate is **paused** when its upper bound (value + `--pause-mult` errors, 3) is below the lowest lower bound of the pool's `--leaders` (10) leaders. A candidate with no estimate yet is unbounded, so it is never paused. `estimate()` takes any seed count `k`: one formula for every round.
- **Reading seeds:** the shown figure and its range never come from the seeds that chose the leaders (selection bias). Each round the current leaders get seeds 20001.. (`sureOffset + 1`, tag `read`, `--reading-step` 2 more per round; `--reading-min` 8 seeds before a figure is shown); the figure and its range are an ordinary t range at `--coverage` (0.99) over those seeds (`tMult`, incomplete beta; Welch degrees of freedom for the unpaired rule). A leader with too few reading seeds is flagged `tooFew` and shown as such. Searching never uses them.
- **Locking (greedy steps and foods/drinks):** `--lock-rule both` (the elimination rule, the owner 2026-11-12; `eliminate` in `rounds.mjs`): per pool the candidates are the changes plus the current setup (a point at gain 0); a change is out for good when its upper end is below another candidate's lower end, or below the bar, 1% of that player's own profit per day under the unchanged setup (worked out from the base runs the round already has; the current setup is exempt; a change cut by the bar beats no one; a player whose figure is 0 or less has no bar), or, on the profit goal for a paid change, when its cost over the upper end of the buyer's gain is above the payback limit (`overPaybackLimit`, the pick check's own definition: an upper end of 0 or less counts as over; a free change is never cut this way); or the tie rule (`tieOf` in `eliminate`, the owner 2026-11-12, no time or round limit): in a pool with two or more changes standing, the higher one A (the pool's own order) and each other standing change B are tied when A's upper end minus B's lower end (the best-case gap, in the raw unit of the bar, not per coin) is below A's player's bar; when every other standing change is tied with A they all go out as `tied` and A is the pool's last candidate standing (the error margins are inside the ends, so a wide early range does not tie; a change of another player never ties, a player without a bar never ties; the current setup takes no part; a tie with the current setup still standing waits for Accept as before); the pool's last candidate standing, when it is a change whose reading seeds pass the pick-check accept rule (`sure.mjs` `verdict`), is locked, and when it is the current setup the pool ends as "no change"; `reading`: the accept rule alone locks the best leader. A locked leader is then confirmed by the existing code (`firstConfirmed` / `confirmFillings`, `--confirm-seeds` 16 of `--confirm-hours` 300 each, seeds 20001..), unchanged: the pick check, the foods and drinks confirmation, the final confirmation, `basePerUser` and a trigger refinement's judgement measure as they did before the rounds search (the race and its reading seeds run at the unit hours). A pick that fails is refuted and leaves for good (as before).
- **Stop and settle:** the stop is the existing stop; the report at any stop is the leaders as they stand (`result.round`, `partial.json`); a restart resumes from the store. The search settles on its own only when a lock is made, no change is left standing in the pool(s) (all out, or refuted: "no change"), or `--max-rounds` (0 = no limit) is reached. A pool that never narrows to one candidate keeps going until stopped.
- **The round record** (`sink.round(r)` → IPC `{ type: 'round', round }`, `<out>/rounds.jsonl`, `result.round` at the end): `{ round, stage, simHours, simHoursAll, unitHours, coverage, pauseMult, leadersK, goal, candidates: { total, contending, paused, refuted, locked }, pools: [{ key, size, contending, paused, line, leaders: [{ id, player, desc, cost, seeds, readingSeeds, tooFew, status, screen, reading, low, high, buyerNet, netLow, netHigh, payback }] }] }`; `key` is `free` / `paid`, with a `<player>:` prefix in the foods and drinks stages; `status` is `contending`, `paused` or `confirmed`. `simHours` is the hours simulated in this call so far (runs that came from a store are not counted); `simHoursAll` is the hours over every run in the store, saved ones included; the log has a timestamped `round N …` line per round. Step 3 additions: a leader row also carries `change` (what changed: `{ kind: "foods"|"drinks", slots: [{ index, item, trigger }] }` for a foods or drinks candidate, else absent), `searchHours` and `readHours` (hours simulated by its search runs and by its fresh runs; `hours` is their sum) and `status: "zero"` when its range reaches 0 (refuted > zero > few > confirmed > contending/paused); the record has `readingMin` (the fresh runs needed before a range is final) and each pool has `sortedBy` (`buyerNet` for the free pool, `payback` for the paid pool, `reading` for a non-profit goal; `null` while no row of the pool has 4 seeds, the rows then stay in build order, each row's `built` is its place, `sortPending` names the column it will sort by, and `rangeWidth` is null), `rangeWidth` and `rangeWidthPrev` (the top leader's range width now and one round before). The leaders are in that order: one comparator (`rankEst`, a total order), best first (shortest payback first for the paid pool; null payback last). A leader's figure and range show from its first fresh run that gives a range (2 runs); `readingMin` only marks the range as not final. **Provisional rounds:** during round 1 the search sends `{ type: 'round', round }` with `provisional: true` after each sweep (all candidates' seed s, then seed s+1; the requests go seed-major: the base's first run, seed 1 of every candidate, seed 2, ...) and at most every 3 s; it is computed from the cache alone (paired differences over seeds where both arms are cached, grouped by pool), carries `firstLook: { have, total }` and rows with `status: "first"` (or `zero`), is **never** used to choose, pause or lock, and goes over IPC only (not into `rounds.jsonl`). The real round record replaces it at the end of round 1. The result's `singlesNotShown` counts the singles searched but not confirmed (fewer than `readingMin` fresh runs), which the "Each change alone" block does not list.
- **Options (all named, with the proposed value; open until the owner rules):** `--unit-hours` 50, `--first-seeds` 2 (at least 2 under the unpaired rule; 1 is refused), `--round-seeds` 1, `--leaders` 10, `--pause-mult` 3, `--coverage` 0.99, `--reading-step` 2, `--reading-min` 8, `--lock-rule` both, `--max-rounds` 0, `--confirm-seeds` 16, `--confirm-hours` 300. `--stages` and `--keep` (the old fixed stages) are still accepted by the runner and the command line and are ignored.
- **Kept as it was:** the chain guard, the pick check and its progress row, the trigger refinement, the final confirmation, `result.json` shape (`rounds` records the options, `round` the last record). The progress parts show one `screen` row for a race (no `halving` rows).

## Synthetic simulation (test tooling)

A fix round on the what-if rules should take minutes, not an hour of real simulation. `tools/whatif/synthetic.mjs` answers the two seams that cost time, and nothing else, from a scenario file; the core has one code path and does not know it is fake.

- **Scenario** (`tools/test/synthetic/scenario.json`, written by `tools/test/synthetic/make-scenario.mjs`): three generic players (Alice, Bob, Cara), a generic price snapshot, budgets, the request flags (`goal`, `levers` equip + foods + drinks, `slots`, `swaps`, `max-up`, `max-payback`, `max-steps`), a `model` (party loot per day, its noise at 50 sim hours, each player's own consumables per day, the food need, `msPerRun`, a pause per run so a page can watch the search) and `effects`: for an op of a task (`{ op: 'enhance', player, slot, delta }`, `{ op: 'food', player, item }`, `{ op: 'drink', player, item }`; the first match wins, an op that matches none changes nothing) the party loot per day it truly adds, the owner's own consumables per day, an optional `searchBonus` (loot only on the search seeds, 1..10000: a change that looks good in the search and fails the fresh-run check) and `noiseSd`. A task's ops add up, so the chain stacks.
- **Pool seam:** `createSyntheticPool(scenario)`: `run(task)` returns `{ variant, seed, wallSeconds, checkpoints }`, a checkpoint `{ simHours, players: { <name>: { consumablesPerDay } }, party: { profitAfterTaxPerDay, consumablesPerDay, expPerHour, deathsPerHour }, encountersPerHour }` computed from the ops, with one gaussian draw per run seeded by (`model.noiseSalt`, variant key, seed), shrunk by sqrt(50/hours): the same task always gives the same numbers, and a run's readings at different hours agree, so a recorded run answers a reading of any length. The salt picks the draws; the scenario's salt was chosen because most draws leave the screen unresolved for hundreds of rounds (see the report of the synthetic round).
- **Replay counter:** `createCountingPool(pool)` in `node-shell.mjs` wraps any pool seam (real or synthetic) and counts the runs that reach it; the core asks the pool only for a run its store does not hold, so the count is the number of real simulations of the search. `optimize.mjs` logs "N real simulations so far" every 50 and a total at the end. It changes neither the core nor the store.
- **Sim seam:** `syntheticSim(realSim, scenario)`: `measureNeed` returns the scenario's food need, `runParty` throws (only the trigger probe calls it; the trigger lever stays off), `buildDtos` and `Trigger` are the real ones. The core builds its candidates from the scenario's party and prices as it does from a real window: equipment `+1..+3` of the worn head, body and legs (priced from the snapshot's per-level asks), and the foods and drinks fillings of the items that have an ask.
- **No page:** `runSynthetic(scenario, extraFlags, { onRound })` runs `core.mjs` `main` in this process with an in-memory store and sink (a full search of the scenario is about 15 seconds); `onRound(record, stop)` can set `stop.done` to press Accept / Skip, and `poolWrap` can press it in the middle of a round (the Skip tests). Test: `tools/test/whatif-synthetic.mjs` (the elimination rule on the scenario's true numbers, and the whole search).
- **With the page:** `node tools/whatif/runner/server.mjs --synthetic <scenario.json>` puts the scenario's party, prices, budgets and `request` over the window's request (`applyScenarioToRequest`; the search id follows the scenario) and starts the optimizer with `--synthetic <scenario.json>`, which takes the two seams above. The window's own refresh is unchanged. `optimize.mjs --synthetic <scenario.json> --setups <dir> --prices <file>` does the same from the command line.

## Starting it

`node tools/whatif/runner/server.mjs [--port 8787] [--results <dir>] [--dist <dir>] [--demo-runs <runs.jsonl>] [--demo-prices <marketplace.json>]`

- Listens on `127.0.0.1` only. `--port 0` picks a free port; the address is printed on start. `--open` opens the page in the default browser (or `$BROWSER`) once it listens; a port held by a runner of the same version opens the page on it and exits 3, by one of another version exits 4, by anything else exits 1 (details in `runner-zip.md`).
- Users start it from a download, not a checkout: `WhatIfRunner.exe` on Windows (one file; it unpacks into `<home>/MWI-WhatIf/runner-<build id>/` and runs this same `server.mjs`), the zip with the system's Node on Linux. How they are built, started and released (the two release assets, the version info, the checks a publishing session runs): `runner-zip.md`, "Release".
- `--results`: where each search keeps its folder; default `<home>/MWI-WhatIf/results`, never inside the repo.
- `--dist`: the built simulator to serve at `/`; default the repo's `dist/`.
- `--demo-runs` / `--demo-prices` (off by default; generic, for a demonstration on saved material): every search the runner starts gets `--cache-from <runs.jsonl>` (a saved run store, read-only, hits count as cached), and the price file named is used in place, instead of the request's snapshot (`--prices <file>`). The run keys hold the price path relative to the checkout, so a saved run hits only when that path reads the same from the checkout the runner runs in.
- A search's folder, with its `runs.jsonl` and result, is named by its id (`searchId` in `server.mjs`: a hash of the canonical request body). A request that ticks both foods and drinks hashes as the old one-lever request did (`foods` and `drinks` become `consumables`, in `searchId` only), so a rerun with both ticked finds the old search's folder, runs and result; Foods alone and Drinks alone are their own searches. The run keys themselves (`keyOf` in `core.mjs`) never held the levers.
- The runner sets its own priority to Node's `PRIORITY_LOW` (Windows: the idle class) at start (`createRunner`), so every process it starts inherits it; it also sets the optimizer process to it explicitly (`forkOptimizer`). The optimizer gives each run process its own priority (`optimize.mjs`, `ensure`; `batch.mjs` does the same), and `--low-priority` sets the optimizer itself low when it runs from the command line.

## Interface

JSON over HTTP, under `/api/`. Everything else is a static file from `dist/` (`/` is `index.html`); nothing outside `dist/` is served.

| Request | Answer |
|---|---|
| `GET /api/version` | `{ runner, engine }`: the runner's version (with the commit when run from a checkout) and the `bundle.<hash>.js` hash named in `dist/index.html` |
| `POST /api/search` (body JSON, `Content-Type: application/json`, up to 50 MB; a full `marketplace.json` is about 250 KB) | `{ id }`; `409 { error, id, running }` (both the running search's id) while another search runs; `400 { error }` for a malformed request |
| `GET /api/search/<id>[?since=<n>]` | `{ state, progress, error?, result?, partial?, partialVersion?, round?, roundVersion? }`, `state` one of `running`, `stopped`, `done`, `error`; `result` is the search's `result.json`; a running search carries its report so far (`partial`) and its version (`partialVersion`), and the latest round record (`round`, `roundVersion`), each only when its version is above `since` (default 0; one counter serves both), see "Live report" and "The rounds search" |
| `POST /api/search/<id>/stop` | `{ id, stopping: true }`; on a stopped search it resumes it from its `request.json`: `{ id, resumed: true }` (the window's Resume); `409` otherwise |
| `POST /api/search/<id>/done` (body `{ mode: 'accept' \| 'skip' }`) | `{ id, done: mode }`: the race stage running now ends: Accept after its round in flight, with its pick taken as it is (no pick check); Skip at once, the runs already going finishing (the window's "Accept current winner" and "Skip this stage", see `whatif-window.md`); `400` for another mode, `409` when nothing runs |
| `GET /api/results` | finished searches, newest first: `[{ id, finished, goal, players }]` |
| `GET /api/results/<id>` | one `result.json` |

The search body: `setups` (the page's setups, each with its `name`), `options` (`zone`, `tier`, `comdrop`, `comexp`; and the prices: `marketplace`, the game's `marketplace.json` body `{ marketData, timestamp }` as the window fetched it when the search started, or `prices`, a snapshot file name in `tools/calibration/`, never both; neither means the optimizer's committed default), `goal`, `budgets` (`{ "<player>": <coin> }`), `levers`, `players` (default: every setup), `stages`, `keep`, `export` (the character export, for the levers that need one: either the old single export, an object with its `name`, or a map `{ "<player name>": <that player's export> }`, which is what the window sends, one entry per ticked player that has one; written as it came to `export.json` and passed as `--export`; a value that is not an object is refused), `triggerCands`, and the optimizer's other flags by their command-line name without the dashes (`max-minutes` or `maxMinutes`; lists as arrays; `false` becomes `--no-<flag>`). `buildArgs` turns it into the optimizer's arguments and refuses anything else (`out`, `setups`, `cache-from` are the runner's own or not offered).

The id is a hash of the request (key order ignored), so a new snapshot is a new search, and the search's folder is `<results>/<id>/`: `request.json`, `setups/` (one file per player and `party.txt`), `marketplace.json` (the request's `options.marketplace`, written once and passed as `--prices`; a resume finds it and keeps it, because the run cache's key holds the price file), `runs.jsonl` (the run store), `progress.json`, `log.txt` (the optimizer's output, each line timestamped), then `partial.json` or `result.json`. The same request again runs in the same folder, so a stopped search resumes from its run store; a finished one is not run again.

Same origin only: a request whose `Host` is not this loopback address and port (DNS rebinding) or whose `Origin` is another site's is refused with `403`. A page of another origin can neither read the interface (no CORS headers) nor start a search (a cross-origin form post cannot send `application/json`, and its `Origin` is refused).

## The optimizer's side

- **Character exports and the levers that need them:** `owned` (items in the inventory), `abilities` (swaps to a learned ability) and `books` (learning a new ability) need the player's own export (`inventory`, `learnedAbilities`). They never block a search: a player with no export (no entry in the map; for the old single form, any player but the one named) is skipped by that lever, with no candidates, and `result.json` lists `skippedNoExport`: `[ { lever, players: [names] } ]`, empty when nothing was skipped (`partial.json` too). With no export at all those levers find nothing and every player is listed. Ability levels (`abilitylevels`) are not among them: without the export they keep their upper-bound cost, labelled as such, and never skip. In the map form the budgets come from `--budgets` only (the old form's coin still fills a missing budget).
- **Budget per player:** `--budgets A=1.5M,B=200K` (`tools/whatif/budgets.mjs`). `--budget` alone, or the exporter's coin, is every player's budget, and the budget of anyone `--budgets` leaves out; a player with no budget is an error. Each candidate is paid by its own `player`: the screen keeps a candidate whose cost fits its player's budget, and the greedy step and the rebuild after it keep one whose cost fits what its player has left (`affordable`). A change that costs nothing or frees gold is always affordable; a sale never refunds a budget (`pay`).
- **Progress:** `report()` writes `<out>/progress.json` and, when the optimizer has an IPC channel, sends `{ type: 'progress', progress }`. Fields: `stage` (`probe`, `screen`, `halving <n>`, `greedy step <n>`, `confirmation`, `done`, `stopped`), `candidatesLeft`, `runsDone` and `runsPlanned` of the current batch (one stage; cached runs are not counted), `secondsPerRun` (mean core-seconds per run in this batch, else in this call), `etaSeconds` (the batch's sim hours left times the measured core-seconds per sim hour, over the processes in use; `etaScope: 'stage'`: later stages are not in it), `elapsedSeconds`.
- **Progress parts:** `progress` also carries `parts`, one row per part of the search, built by `createParts(plan).sync(progress)` in `tools/whatif/progress.mjs` (pure; `optimize.mjs` creates the tracker once the candidates are known, with `maxSteps` from `--max-steps`, so a `probe` report has no `parts`, and `report()` calls `sync` on every report). A part: `{ kind: 'foods'|'drinks'|'screen'|'halving'|'picks'|'steps'|'step'|'moreSteps'|'confirmation', index, state: 'waiting'|'running'|'done', runsPlanned, runsDone, runsUpTo (waiting halving), candidatesLeft, etaSeconds, maxSteps ('steps'), stepsLeft ('moreSteps') }`. Every bar is there from the first report: with the foods and drinks levers a `foods` and a `drinks` row first, one for each ticked kind (`plan.kinds`, the ticked ones in the order foods then drinks; one row per whole stage, its candidates left shown, its runs counted as a halving's), then the screen (`setCandidates(n)` gives the rest-of-search count once F and D are done), one `halving` per further stage (the waiting ones with `runsUpTo` = the pool entering that stage, the screen's candidates cut by `keep`, times that stage's seeds; a cached run is not counted, so the real count can be lower, and `runsPlanned` is exact once the part starts), a grey `picks` row ("Re-checking each chosen change", one row for the whole greedy phase), a grey `steps` row (`maxSteps`) and a grey `confirmation` row. **The `picks` row** counts distinct runs, not batches: `optimize.mjs` keeps `sure` ({ planned, done, counted }) and `report()` sends it as `progress.picksPlanned` / `progress.picksDone`. A run (one arm on one seed) is added to planned once, when a check asks for it; one already in the run cache is done at once, the others when their run finishes (`ensure`, tag `sure`). So the first check plans 32 (two arms x 16 seeds); 16 more seeds per arm plan 32 more; a replacement pick after a failure plans only its own arm (16), because the "chain so far" arm is the same runs; a pick that joins makes the next step's "chain so far" arm already counted, so the next step plans only the new pick's arm. (The brief's wording added both arms for a replacement; they share the chain arm, so counting the distinct runs keeps done able to reach planned.) `tools/whatif/progress.mjs` shows the row running while `stage` is `confirming picks`, grey with its counts between two checks, done and full once the confirmation starts or the search ends; planned never drops and done never exceeds it (the tracker keeps the larger planned and caps done). When `greedy step <k>` starts a `step` row takes the `steps` row's place (its runs are the re-screen after accepting step k) and a grey `moreSteps` row (`stepsLeft` = `maxSteps` - k; hidden at 0 and once the confirmation has started) follows the steps above the confirmation; the `confirmation` row turns running when it starts. So the number of rows grows as steps are added. Earlier rows turn `done` with `runsDone = runsPlanned` and `etaSeconds` 0; `etaSeconds` is the stage figure for the running row only (null for waiting). The pick check of a foods or drinks stage is the exception: `confirmPick` names its stage in `progress.checking` (`foods`, `drinks`, or `step N` for the greedy chain), and for `foods`/`drinks` the tracker keeps the `picks` row as it was and puts `checking: true` with `checkPlanned` / `checkDone` (the check's own runs: the global counts minus what they were when it began) on that stage's own row, which the window draws as "checking the accepted picks on fresh runs · player N of M · done / total runs" in place of "done" (`confirmPick` passes `progress.checkingWho` = { index, of }, the player among those with a pick; the first block of every player's check is planned before the first check starts (`planSure(sureReqs(...))` in core.mjs, the same planning `confirmPick` uses; the "chain so far" arm is shared, so three players are 16 + 3 x 16 = 64 runs), so the total is whole from the start; it grows only by an extension of a check (a pick between z/2 and z errors, up to 64 seeds per arm) or a next best after a failed pick, neither known before the readings), so the later stages keep their waiting state and the title carries no "part k of n". The running race row also carries the projection after its "still in the running" count (`stageSeparate` from `nearestSeparation` in `rounds.mjs`: of the pools with two or three changes standing, the smallest `roundsToSeparate`, the rounds for the sum of the top two's margins to fall under the gap between their means, margins shrinking as 1/sqrt(rounds so far); "about N more rounds to separate", or "more than 999 more rounds to separate" when the gap is about zero or N is above 999). A stage the user ended says "ended by you after round N" alone in its Best foods / Best drinks heading (no "so far"). A stop (`stage: 'stopped'`) changes no row. The stage fields of a race (`round`, `phase`, `stageContending`, `stagePaused`, `stageAcceptable`, `stageSeparate`, `stageDropped`, `stageRuns`, `stageSimHours`, `stageEnded`, `stageSkipped`; `STAGE_FIELDS` in `core.mjs`) leave the shared `progress` object when the race returns (`race()`'s `finally`), so the confirmation row, a pick check after the race and the end never carry the stage before them (`progress.mjs` copies them onto any row whose message has a `round`). `progress.stageSkipped` is set with `stageEnded` when the stage ended by Skip (row `skipped`). `progress.picksLeftOut` = the number of picks the check left out (`result.notConfirmed`; the check also runs inside a race, on the leaders' reading seeds, with no run of its own): the `picks` row then ends `done` with `leftOut` even when it never started. The runner passes `progress` on unchanged, so `parts` reaches `GET /api/search/<id>` as is. Test: `tools/test/whatif-progress-parts.mjs`.
- **Stop:** the IPC message `'stop'` stops issuing runs and kills the runs in flight. Every finished run is already a whole line of `runs.jsonl` (the parent appends it), so nothing half-written is left; the optimizer writes `partial.json` with `stoppedBy: 'stop request'` and exits with code 3, as `--max-minutes` does.
- **`result.json`** additions: at the top `budgets`, `partySize`, `basePerUser` (the base the search compared against, per user, in the goal's unit: the mean over the last stage's base seeds of the goal's party figure, divided by `partySize`), `options` (zone, tier, comdrop, comexp, `prices` the price file relative to the checkout, `pricesTimestamp` the snapshot's own `timestamp` in seconds, `pricesSource` `committed` for a file of `tools/calibration/` or `snapshot` for any other such as the request's, levers; the last three are not in the run cache's key) and the base `setups`; `overBudget`, the priced candidates whose cost is above their own player's budget (`id`, `player` the payer, `desc`, `cost`, `costBound`, `costPath`, `note`), listed and never ranked, beside `apart` (unknown cost); `dominated`, the market swaps of the equip lever the search never offers because they are no better on any combat stat (`id`, `player`, `slot`, `desc`, `from` and `to` each `{ item, level }`; one entry per distinct swap, including those met when candidates are rebuilt after a step), judged by `tools/whatif/dominated.mjs`: dominated only when neither item has a noncombat stat, no combat stat of either is negative (each at its own level, through the engine's `Equipment.getCombatStat`), every combat stat of the new item is a stat of the worn one and not above it, and the non-stat fields (`combatStyleHrids`, `damageType`, `attackInterval`, `primaryTraining`, `focusTraining`, and any `equipmentDetail` field other than `type`, `levelRequirements` and the four stat and bonus maps) are equal; anything else is offered; owned items, pairs and enhancement are never filtered by it, and the run cache key of the offered candidates is unchanged; `otherStyle`, the swaps (market ones the market sells, and owned ones) never offered because the piece's only bonuses are another combat style's or element's (same row shape as `dominated`, plus `bound` `{ styles, elements }` it is bound to and `wants` `{ style, element }` the player's), judged by `tools/whatif/stylefit.mjs` in the one `styleDrop` both `candidatesFor` and `ownedCands` call (the owner's rule: swaps stay within the player's combat style and, for a mage, his element, with no armour exception): the player's style is `combatStyleOf` (his weapon's `combatStats.combatStyleHrids[0]`, stab, slash and smash are melee, no weapon is melee), his element a mage's weapon `combatStats.damageType` (physical or none: no element); a piece is bound to a style by a POSITIVE base value of `stab|slash|smash|melee|ranged|magic` + `Accuracy|Damage|Experience` (a weapon also by its own `combatStyleHrids[0]`) and to an element by a positive `fire|water|nature` + `Amplify|Penetration` (a weapon also by its `damageType`); negative values (every melee and ranged piece has a negative `magicAccuracy`), Evasion, Resistance, armor and the like bind nothing, and a piece bound to nothing stays a candidate; it fits when it has no style it is bound to or one of them is the player's, and likewise for the element (a player with no element fails any element-bound piece); test `tools/test/whatif-stylefit.mjs`; on every row of `steps` and `singles` its `player`, `ops`, `gainPerUser` and `sePerUser` (the party figure divided by the party size, equal split), with `accepted` and `costBound` as before; each step's `runningSpend` per player (cumulative after it; `runningCost` stays as the sum); `confirmation` carries `gainPerUser`, `sePerUser`, `accepted` and `runningSpend`.
- **Accept rule (profit goal):** a change is accepted (`accepted`) when one of the party's shared loot gain and the buyer's net is above 0 by at least z errors and the other is not a clear loss, at least -(z/2) errors (`acceptBoth`, `tools/whatif/buyer.mjs`; at z 2: one side at 2 errors, the other not below -1 error; at z 0: neither below 0 and one above). A pure cost cut (the group's loot unchanged, the buyer's supplies lower) and a change that does not touch the group at all pass when the buyer's side is clear. **The party figure on the profit goal is the shared loot gain only** (`estimate`: `gain`, `se` are the loot gain of `lootOf`, the party's profit after tax plus its consumables, with no one's food or drink in it; Owner: "Gain is per party, cost is per person"); `gainPerUser` = gain / `partySize` therefore equals `sharedGainPerUser`, which stays as a field. The confirmation's `gain`, `se`, `gainPerUser`, `sePerUser` are that figure on the fresh runs; `buyerByPlayer` is unchanged. The EXP goal keeps its metric and the party test (`gain > 0` and `gain >= z se`). `result.md` writes a gain whose absolute value is below one error as `no change (+288K ± 242K)` with `-` in the error column. Per run q = (the party's loot after tax per day over `partySize`) minus the buyer's own consumables per day; the net and its error are the search's error rule (paired or unpaired) on that one series (`buyerNet` in `tools/whatif/buyer.mjs`, never the loot error plus the supplies error). `score` is the net over the price (1 / the buyer payback; a free change with a net above 0 is Infinity) and `rank` orders by it, then the larger net, then the larger party gain (`scoreOf`, `rankEst`). There is no helps-the-party group (`acceptedParty`, `helpsParty` and `result.helpsParty` are gone; an older result may still carry them). Rows carry `buyerNet` and `buyerNetSe`. The confirmation's `accepted` is the party test; on this goal it also carries `buyerByPlayer` (`{ gain, se, payback }` per player; the payback is the player's spend over that gain, none when the spend or the gain is 0 or below). On another goal (EXP) `accepted` and `score` are as before. Each stage's pool is sorted accepted rows first, then `rankEst` (`rankAcceptedFirst`), so the cut to the next stage keeps rows that can be taken; the log prints a `step N candidate` line per finalist before each greedy step. `result.md` lists Party gain per user, ± se, Buyer's gain per day, ± se, Cost, Payback days and Cost path.
- **Chain guard (greedy steps):** `optimize.mjs` keeps `chain`, the run key of every state the search has been in (the original base, the foods and drinks baseline, the state after each accepted step), and drops, before it is estimated, every candidate whose resulting state is already in it (`dropChainStates` in `tools/whatif/pools.mjs`; the log prints the dropped ids). The key hashes the applied setup, so a full-list trigger op applied last-wins counts as the state it produces. Why: an accepted change becomes the base, and the old state rebuilt as a candidate (a trigger term back to its old value) is measured on its own low seeds against the base's more numerous seeds, so two states that simulate alike showed the same gain in both directions and the greedy loop flipped between them. The guard stays with the same-seeds gain (next bullet): it is still needed for a state the loop would otherwise revisit.
- **Pick check (the greedy chain confirms each pick before it joins; `tools/whatif/sure.mjs` the pure decisions, `confirmPick` in `tools/whatif/optimize.mjs` the runs).** The owner's go, 2026-11-11: "I would just do what we're already trying to do. Confirm the run, reduce the noise, don't recommend what you can't ensure enough." One exception: a pick the user took with "Accept current winner" (`stop.done === 'accept'`, `race()` returns it in `accepted`) joins as it is, with no check and no fresh reading, and its row carries `acceptedAsIs: true` (the greedy step and `confirmFillings`' `asIs`); trigger refinement is skipped for it. In the greedy loop the best accepted candidate (`ok[0]`) no longer joins at once: it is re-measured on fresh seeds against the chain as it is at that moment (`baseOps` before the pick's ops are added). The measurement is two arms on the same seeds, "chain so far" and "chain + this pick", 16 seeds per arm of `fin.h` hours (the last stage's hours), the search's own rules on that one reading: the error rule, and `acceptBoth` for the pass on the profit goal (the party test on another goal). **Seeds:** 20001.. (`sureOffset` = `--confirm-seed-offset` + 10000), the same block for every step, so one step's "chain + pick" arm is the next step's "chain so far" arm and the run cache gives it for free. The search keeps 1..10000, the final confirmation 10001..20000 (`pick` with `fresh` now stops at `sureOffset`; before, it took any seed above 10000). Runs are tagged `sure` in `runs.jsonl`. **Verdict** (`verdict` in `sure.mjs`): accepted passes; not accepted but the deciding figure (the buyer's net on the profit goal, the party gain on another) at least z/2 and under z errors (1 and 2 at z 2) gets 16 more seeds per arm (both arms), again, up to 64; under z/2 errors, or still not accepted at 64, fails. A pick that fails is left out and the next best of `ok` is tried (`firstConfirmed`); none left ends the chain. A failed pick leaves the finalists, so it is not offered again in a later step (a candidate rebuilt for a group the next accepted pick touched is a new candidate and is checked on its own). `result.json`: each step has `fresh` ({ `seeds` per arm, `seedFrom`, `seedTo`, `hours`, `gain`, `se` (the party's shared loot gain, totals), `gainPerUser`, `sePerUser`, `buyerNet`, `buyerNetSe` (per user, profit goal), `accepted` }); `notConfirmed` lists the failed picks, each the candidate's row plus `step` (the greedy step it was tried at) and its last `fresh` (a food or drink filling that failed has `step: null` and `kind: 'food' | 'drink'`, see "Foods and drinks first"); `pickCheck` is { `seedsPerBlock`: 16, `maxSeeds`: 64, `firstSeed`: 20001 }. **A trigger pick is refined first** (batch 2, his go 2026-11-11: "Make it so"): a pick whose ops are a trigger op is not checked as it stands. `refineTrigger` (`tools/whatif/refine.mjs`, pure) takes the owner's local candidates (`localCands`: the same owner's trigger changed one term at a time, built on the trigger as it stands) and judges them against the chain with the current trigger (`estimate` on the search seeds, the usual accept test); the best accepted one (`rank`) is joined to the trigger (`joinTriggerDesc`: the owner's trigger from its value in the chain to its final value, one description, one op that carries the owner's whole list) and the round repeats until none is accepted. The refined trigger is then re-estimated against the chain and goes to the same fresh-seed check as any pick, as one change, so one trigger is one step row (200 -> 3000, not 200 -> 4600 and 4600 -> 3000). `mergeTriggerSteps` (the end-of-chain merge) is gone. The row's `est` is the search-seed reading of the refined candidate and may read `accepted: false` while its `fresh` reading passed. A failed refined pick goes to `notConfirmed` and leaves the finalists as any pick does. The final confirmation is unchanged (original base against the final result on 10001..); every step is confirmed by construction, so it needs no change. **Progress:** a part `picks` (below). Test: `tools/test/whatif-sure.mjs` (scripted fresh readings: pass, fail at once, more seeds then pass, still failing at 64, a failed pick replaced), the end-to-end block of `tools/test/whatif-runner.mjs`.
- **Gain on the same seeds (unpaired rule):** a change's gain is the variant's mean minus the base's mean **on exactly the seeds the variant ran** (its lowest k that reach the stage's hours), not on the base's `baseMult` x k seeds (the owner's pick, 2026-11-10: "Compare on the same seeds"). The error is unchanged: `sqrt(sv^2/kv + sb^2/kb)` with the base's variance over all its `baseMult` x k seeds (`diffStat` in `tools/whatif/buyer.mjs`: `bs` feeds the error, the optional `bsSame` the gain; it also returns `seSame`, the error with the base's variance over the same seeds only, which `result.json` carries beside the shown one: `sharedSeSamePerUser`, `buyerNetSeSame`, the confirmation's `sharedSeSamePerUser` and `buyerByPlayer[p].seSame`; nothing uses it). Applied wherever runs become a gain against a base: `estimate` in `optimize.mjs` (the party figure, the buyer's net, the player's own supplies, the food judge's deaths and kills; so the screen, the halvings and their cuts, the Each change alone rows and ranking, and the greedy steps) and the confirmation (the original base on the result's own fresh seeds; the other fresh base seeds feed the error). The base runs on the variant's seeds are requested with the variant's (`reqPair`), so a base run not yet saved is run by the search; the base's `baseMult` x k seeds are still requested for the error. A variant whose state equals the base's has the same runs and a gain of exactly 0. The `paired` rule is unchanged. `basePerUser` and the skills report's base rates are levels, not gains, and still use the base's `baseMult` x k seeds. `result.md` states it as `Error rule: unpaired, gain on the same seeds, accept at 2 se.`
- **Foods and drinks first (the `foods` and `drinks` levers, two boxes; `consumables`, the one lever they were before, is read as both; `pairs` now does nothing, kept so an old command line still runs).** Only the ticked kinds run, foods then drinks, from one loop in `core.mjs` (`kinds`): with only Foods ticked there is no Stage D and the drinks stay as the setup has them; with only Drinks ticked there is no Stage F (and no food-need measurement) and Stage D races against the baseline with the foods as set up; with neither there is no Stage F or D, as before. The owner's ruling: foods and drinks are each run separately, the best food combination and the best drink combination (all slots of each) are decided before the rest of the run, the result says what they are, and they are the baseline of every other what-if. So `main()` runs **Stage F** (foods), then **Stage D** (drinks), then the rest. Each is a whole successive-halving run (`halve(cands, baseOps, kind, true)`) of whole fillings, every candidate at cost 0, measured against the baseline so far (Stage F on the original setups, Stage D on the setups after F's choices). The cut between its stages is **per player** (`cutPool(pool, n, true)` in `tools/whatif/pools.mjs`: the first `keep` free and the first `keep` paid candidates of each player, union in pool order), so one player's fillings cannot crowd out another's (the plain cut, used by the rest of the search, is over the whole pool). After the last stage `confirmFillings` (`tools/whatif/sure.mjs`) takes the players in party order; for each it tries his accepted fillings in `rankAcceptedFirst` order and confirms the first on fresh seeds under the pick check's rule (16 up to 64 seeds per arm, `acceptBoth`, seeds 20001.., tag `sure`, the same run cache), against a baseline that already holds the earlier players' confirmed fillings; a filling that fails is replaced by his next best, and a player none of whose fillings pass keeps his current items (`unchanged`). Failed fillings go to `result.notConfirmed` as `{ ...row, step: null, kind: 'food' | 'drink', fresh }`. (Before this batch `bestPerPlayer` took the first accepted filling with no fresh check; it is no longer used by the optimizer.) The confirmed ops are appended to `baseOps` (food ops, trigger ops that came with them, drink ops), and `result.baselineOps` is that list. Everything after F and D (the trigger probe, the screen, the halvings, the greedy steps and the confirmation) is built on `applyOps(setups0, baseOps)` and measured against that baseline, so the rest-of-search rows in `result.singles` (`gain`, `se`, `buyerNet`, `payback`) are gains over the foods and drinks, not over the setup the search started from; `result.basePerUser` and the confirmation's base are still the original setups, so the confirmation is the original base against the final `baseOps` (foods and drinks included) plus the greedy steps. The rows of F and D stay in `result.singles` flagged `stage: 'food' | 'drink'` and `hiddenFood: true` (left out of the panel and `result.md`). With the lever off there is no F or D, `result.best` is `{ foods: {}, drinks: {} }` and `baselineOps` is empty.
  - **Foods** (`tools/whatif/foodfill.mjs`, pure): the need is measured once per search by `measureNeed` (`tools/whatif/engine.mjs`: 3 seeds of 20 sim hours of the base party, the HP and MP per hour delivered by the sources that are foods, kept in `<out>/need.json`). Per player: foods another food of the same type beats are dropped (except his current foods); a filling is one food of each of as many types as there are open food slots and qualifies when its HP and MP capacity (restore x 60 per hour) are at least the need x 1.25; per type the cheapest 3 per point among the foods in a qualifying filling stay (the current foods in addition); the current filling is not a candidate. Candidates are `kind: 'food-fill'`, id `<player>:foodfill=<food0>+<food1>+<food2>`; each food goes in the slot of the baseline food of its type, else a free slot of the same resource, and a new food inherits the donor's `triggerMap` entry as a `trigger` op. A food filling is also judged by the simulation: refused (`accepted` false, `judged: 'deaths' | 'kills'`) when the party's deaths per hour are higher, or its kills per hour lower, than the base's by more than z errors.
  - **Drinks** (`tools/whatif/drinkfill.mjs`, pure): a filling is one drink of each of as many different drink types as there are open drink slots (the game allows one per type). A drink has no `triggerMap` entry of its own (engine: triggers are keyed by item hrid and a drink with no entry gets the default), so a drink filling carries no trigger ops, and the trigger levers skip drink owners. Before fillings are made the player's drink pool is pruned by `pruneDrinks({ table, style, goal, current })`, rules in this order, each counted by the first rule that drops a drink (`result.drinkPruning[player]`: `style`, `table`, `dropped: { a, b, c, d }`, `kept`, `types`, `fillings`): (a) only the coffees of the player's own combat style stay (`combatStyleOf`: melee, ranged or magic from the weapon, as the engine reads it); (b) melee and ranged keep Swiftness (attack speed) and drop Channeling (cast speed), magic the opposite; (c) profit keeps Lucky and drops Wisdom, exp the reverse; (d) exact dominance inside a type (`drinkBeats`: every buff value matched or exceeded and an ask not above, one strictly; the player's current drinks are never dropped by d). On the current prices that leaves 18 drinks of 8 types and 585 fillings per player (586 on exp). Nothing else is cut by hand: clearly worse fillings drop out at the first cut of Stage D's halving. **Why rule (b)** (the owner): "all magic casters use a basic attack ability, which is one that has zero cooldown. so in practice, magic users never auto attack, they are always ability casting, so any bonuses to auto attack don't actually help them at all. non-magic users don't benefit from cast speed for the inverted reason. They only cast sometimes, and even when they do, their cast time is super short, so reducing it wouldn't help, cooldown is their bottleneck, and they fill it with auto attacks."

- **Live report (snapshots):** the whole report unfolds while the search runs (his go 2026-11-11: "Make it so": "what-if shows the recommended food and drinks as soon as available / then it shows each step as they are confirmed / overall it unfolds and updates the report as each data becomes available"). `optimize.mjs` builds the report with one function, `snapshot(result)` (a copy of `result` without the working list `timeOnly`, with `steps` and `notConfirmed` copied and `skippedNoExport` as it stands), and `publish(result)` sends `{ type: 'partial', result: snapshot(result) }` over the IPC channel when there is one (nothing on a command line). Five points: (1) after the foods stage, (2) after the drinks stage (both after the whole stage, once every player is confirmed: `best`, `baselineOps`, `drinkPruning`), (3) after the candidates are built and priced (`candidateList`, `overBudget`, `apart`, `dominated`, the count), (4) after the last halving (`singles`, `basePerUser`), (5) after each confirmed step (`steps` grows by the one final row) and after each failed pick (`notConfirmed` grows). A stopped, done or errored search carries no `partial` (the done one has `result`).
