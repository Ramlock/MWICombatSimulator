# What-if runner

`tools/whatif/runner/server.mjs`: a local web server that serves the built simulator and runs the what-if optimizer (`tools/whatif/optimize.mjs`) for it, at the lowest operating-system priority on every core. Test: `tools/test/whatif-runner.mjs`.

## Starting it

`node tools/whatif/runner/server.mjs [--port 8787] [--results <dir>] [--dist <dir>]`

- Listens on `127.0.0.1` only. `--port 0` picks a free port; the address is printed on start.
- `--results`: where each search keeps its folder; default `<home>/MWI-WhatIf/results`, never inside the repo.
- `--dist`: the built simulator to serve at `/`; default the repo's `dist/`.
- The runner sets its own priority to Node's `PRIORITY_LOW` (Windows: the idle class) at start (`createRunner`), so every process it starts inherits it; it also sets the optimizer process to it explicitly (`forkOptimizer`). The optimizer gives each run process its own priority (`optimize.mjs`, `ensure`; `batch.mjs` does the same), and `--low-priority` sets the optimizer itself low when it runs from the command line.

## Interface

JSON over HTTP, under `/api/`. Everything else is a static file from `dist/` (`/` is `index.html`); nothing outside `dist/` is served.

| Request | Answer |
|---|---|
| `GET /api/version` | `{ runner, engine }`: the runner's version (with the commit when run from a checkout) and the `bundle.<hash>.js` hash named in `dist/index.html` |
| `POST /api/search` (body JSON, `Content-Type: application/json`, up to 50 MB; a full `marketplace.json` is about 250 KB) | `{ id }`; `409 { error, id, running }` (both the running search's id) while another search runs; `400 { error }` for a malformed request |
| `GET /api/search/<id>` | `{ state, progress, error?, result? }`, `state` one of `running`, `stopped`, `done`, `error`; `result` is the search's `result.json` |
| `POST /api/search/<id>/stop` | `{ id, stopping: true }`; on a stopped search it resumes it from its `request.json`: `{ id, resumed: true }` (the window's Resume); `409` otherwise |
| `GET /api/results` | finished searches, newest first: `[{ id, finished, goal, players }]` |
| `GET /api/results/<id>` | one `result.json` |

The search body: `setups` (the page's setups, each with its `name`), `options` (`zone`, `tier`, `comdrop`, `comexp`; and the prices: `marketplace`, the game's `marketplace.json` body `{ marketData, timestamp }` as the window fetched it when the search started, or `prices`, a snapshot file name in `tools/calibration/`, never both; neither means the optimizer's committed default), `goal`, `budgets` (`{ "<player>": <coin> }`), `levers`, `players` (default: every setup), `stages`, `keep`, `export` (the character export, for the levers that need one: either the old single export, an object with its `name`, or a map `{ "<player name>": <that player's export> }`, which is what the window sends, one entry per ticked player that has one; written as it came to `export.json` and passed as `--export`; a value that is not an object is refused), `triggerCands`, and the optimizer's other flags by their command-line name without the dashes (`max-minutes` or `maxMinutes`; lists as arrays; `false` becomes `--no-<flag>`). `buildArgs` turns it into the optimizer's arguments and refuses anything else (`out`, `setups`, `cache-from` are the runner's own or not offered).

The id is a hash of the request (key order ignored), so a new snapshot is a new search, and the search's folder is `<results>/<id>/`: `request.json`, `setups/` (one file per player and `party.txt`), `marketplace.json` (the request's `options.marketplace`, written once and passed as `--prices`; a resume finds it and keeps it, because the run cache's key holds the price file), `runs.jsonl` (the run store), `progress.json`, `log.txt` (the optimizer's output, each line timestamped), then `partial.json` or `result.json`. The same request again runs in the same folder, so a stopped search resumes from its run store; a finished one is not run again.

Same origin only: a request whose `Host` is not this loopback address and port (DNS rebinding) or whose `Origin` is another site's is refused with `403`. A page of another origin can neither read the interface (no CORS headers) nor start a search (a cross-origin form post cannot send `application/json`, and its `Origin` is refused).

## The optimizer's side

- **Character exports and the levers that need them:** `owned` (items in the inventory), `abilities` (swaps to a learned ability) and `books` (learning a new ability) need the player's own export (`inventory`, `learnedAbilities`). They never block a search: a player with no export (no entry in the map; for the old single form, any player but the one named) is skipped by that lever, with no candidates, and `result.json` lists `skippedNoExport`: `[ { lever, players: [names] } ]`, empty when nothing was skipped (`partial.json` too). With no export at all those levers find nothing and every player is listed. Ability levels (`abilitylevels`) are not among them: without the export they keep their upper-bound cost, labelled as such, and never skip. In the map form the budgets come from `--budgets` only (the old form's coin still fills a missing budget).
- **Budget per player:** `--budgets A=1.5M,B=200K` (`tools/whatif/budgets.mjs`). `--budget` alone, or the exporter's coin, is every player's budget, and the budget of anyone `--budgets` leaves out; a player with no budget is an error. Each candidate is paid by its own `player`: the screen keeps a candidate whose cost fits its player's budget, and the greedy step and the rebuild after it keep one whose cost fits what its player has left (`affordable`). A change that costs nothing or frees gold is always affordable; a sale never refunds a budget (`pay`).
- **Progress:** `report()` writes `<out>/progress.json` and, when the optimizer has an IPC channel, sends `{ type: 'progress', progress }`. Fields: `stage` (`probe`, `screen`, `halving <n>`, `greedy step <n>`, `confirmation`, `done`, `stopped`), `candidatesLeft`, `runsDone` and `runsPlanned` of the current batch (one stage; cached runs are not counted), `secondsPerRun` (mean core-seconds per run in this batch, else in this call), `etaSeconds` (the batch's sim hours left times the measured core-seconds per sim hour, over the processes in use; `etaScope: 'stage'`: later stages are not in it), `elapsedSeconds`.
- **Progress parts:** `progress` also carries `parts`, one row per part of the search, built by `createParts(plan).sync(progress)` in `tools/whatif/progress.mjs` (pure; `optimize.mjs` creates the tracker once the candidates are known, with `maxSteps` from `--max-steps`, so a `probe` report has no `parts`, and `report()` calls `sync` on every report). A part: `{ kind: 'foods'|'drinks'|'screen'|'halving'|'picks'|'steps'|'step'|'moreSteps'|'confirmation', index, state: 'waiting'|'running'|'done', runsPlanned, runsDone, runsUpTo (waiting halving), candidatesLeft, etaSeconds, maxSteps ('steps'), stepsLeft ('moreSteps') }`. Every bar is there from the first report: with the `consumables` lever a `foods` and a `drinks` row first (`plan.fillings`; one row per whole stage, its candidates left shown, its runs counted as a halving's), then the screen (`setCandidates(n)` gives the rest-of-search count once F and D are done), one `halving` per further stage (the waiting ones with `runsUpTo` = the pool entering that stage, the screen's candidates cut by `keep`, times that stage's seeds; a cached run is not counted, so the real count can be lower, and `runsPlanned` is exact once the part starts), a grey `picks` row ("Confirming the picks", one row for the whole greedy phase), a grey `steps` row (`maxSteps`) and a grey `confirmation` row. **The `picks` row** counts distinct runs, not batches: `optimize.mjs` keeps `sure` ({ planned, done, counted }) and `report()` sends it as `progress.picksPlanned` / `progress.picksDone`. A run (one arm on one seed) is added to planned once, when a check asks for it; one already in the run cache is done at once, the others when their run finishes (`ensure`, tag `sure`). So the first check plans 32 (two arms x 16 seeds); 16 more seeds per arm plan 32 more; a replacement pick after a failure plans only its own arm (16), because the "chain so far" arm is the same runs; a pick that joins makes the next step's "chain so far" arm already counted, so the next step plans only the new pick's arm. (The brief's wording added both arms for a replacement; they share the chain arm, so counting the distinct runs keeps done able to reach planned.) `tools/whatif/progress.mjs` shows the row running while `stage` is `confirming picks`, grey with its counts between two checks, done and full once the confirmation starts or the search ends; planned never drops and done never exceeds it (the tracker keeps the larger planned and caps done). When `greedy step <k>` starts a `step` row takes the `steps` row's place (its runs are the re-screen after accepting step k) and a grey `moreSteps` row (`stepsLeft` = `maxSteps` - k; hidden at 0 and once the confirmation has started) follows the steps above the confirmation; the `confirmation` row turns running when it starts. So the number of rows grows as steps are added. Earlier rows turn `done` with `runsDone = runsPlanned` and `etaSeconds` 0; `etaSeconds` is the stage figure for the running row only (null for waiting). A stop (`stage: 'stopped'`) changes no row. The runner passes `progress` on unchanged, so `parts` reaches `GET /api/search/<id>` as is. Test: `tools/test/whatif-progress-parts.mjs`.
- **Stop:** the IPC message `'stop'` stops issuing runs and kills the runs in flight. Every finished run is already a whole line of `runs.jsonl` (the parent appends it), so nothing half-written is left; the optimizer writes `partial.json` with `stoppedBy: 'stop request'` and exits with code 3, as `--max-minutes` does.
- **`result.json`** additions: at the top `budgets`, `partySize`, `basePerUser` (the base the search compared against, per user, in the goal's unit: the mean over the last stage's base seeds of the goal's party figure, divided by `partySize`), `options` (zone, tier, comdrop, comexp, `prices` the price file relative to the checkout, `pricesTimestamp` the snapshot's own `timestamp` in seconds, `pricesSource` `committed` for a file of `tools/calibration/` or `snapshot` for any other such as the request's, levers; the last three are not in the run cache's key) and the base `setups`; `overBudget`, the priced candidates whose cost is above their own player's budget (`id`, `player` the payer, `desc`, `cost`, `costBound`, `costPath`, `note`), listed and never ranked, beside `apart` (unknown cost); `dominated`, the market swaps of the equip lever the search never offers because they are no better on any combat stat (`id`, `player`, `slot`, `desc`, `from` and `to` each `{ item, level }`; one entry per distinct swap, including those met when candidates are rebuilt after a step), judged by `tools/whatif/dominated.mjs`: dominated only when neither item has a noncombat stat, no combat stat of either is negative (each at its own level, through the engine's `Equipment.getCombatStat`), every combat stat of the new item is a stat of the worn one and not above it, and the non-stat fields (`combatStyleHrids`, `damageType`, `attackInterval`, `primaryTraining`, `focusTraining`, and any `equipmentDetail` field other than `type`, `levelRequirements` and the four stat and bonus maps) are equal; anything else is offered; owned items, pairs and enhancement are never filtered, and the run cache key of the offered candidates is unchanged; on every row of `steps` and `singles` its `player`, `ops`, `gainPerUser` and `sePerUser` (the party figure divided by the party size, equal split), with `accepted` and `costBound` as before; each step's `runningSpend` per player (cumulative after it; `runningCost` stays as the sum); `confirmation` carries `gainPerUser`, `sePerUser`, `accepted` and `runningSpend`.
- **Accept rule (profit goal):** a change is accepted (`accepted`) when one of the party's shared loot gain and the buyer's net is above 0 by at least z errors and the other is not a clear loss, at least -(z/2) errors (`acceptBoth`, `tools/whatif/buyer.mjs`; at z 2: one side at 2 errors, the other not below -1 error; at z 0: neither below 0 and one above). A pure cost cut (the group's loot unchanged, the buyer's supplies lower) and a change that does not touch the group at all pass when the buyer's side is clear. **The party figure on the profit goal is the shared loot gain only** (`estimate`: `gain`, `se` are the loot gain of `lootOf`, the party's profit after tax plus its consumables, with no one's food or drink in it; Owner: "Gain is per party, cost is per person"); `gainPerUser` = gain / `partySize` therefore equals `sharedGainPerUser`, which stays as a field. The confirmation's `gain`, `se`, `gainPerUser`, `sePerUser` are that figure on the fresh runs; `buyerByPlayer` is unchanged. The EXP goal keeps its metric and the party test (`gain > 0` and `gain >= z se`). `result.md` writes a gain whose absolute value is below one error as `no change (+288K ± 242K)` with `-` in the error column. Per run q = (the party's loot after tax per day over `partySize`) minus the buyer's own consumables per day; the net and its error are the search's error rule (paired or unpaired) on that one series (`buyerNet` in `tools/whatif/buyer.mjs`, never the loot error plus the supplies error). `score` is the net over the price (1 / the buyer payback; a free change with a net above 0 is Infinity) and `rank` orders by it, then the larger net, then the larger party gain (`scoreOf`, `rankEst`). There is no helps-the-party group (`acceptedParty`, `helpsParty` and `result.helpsParty` are gone; an older result may still carry them). Rows carry `buyerNet` and `buyerNetSe`. The confirmation's `accepted` is the party test; on this goal it also carries `buyerByPlayer` (`{ gain, se, payback }` per player; the payback is the player's spend over that gain, none when the spend or the gain is 0 or below). On another goal (EXP) `accepted` and `score` are as before. Each stage's pool is sorted accepted rows first, then `rankEst` (`rankAcceptedFirst`), so the cut to the next stage keeps rows that can be taken; the log prints a `step N candidate` line per finalist before each greedy step. `result.md` lists Party gain per user, ± se, Buyer's gain per day, ± se, Cost, Payback days and Cost path.
- **Chain guard (greedy steps):** `optimize.mjs` keeps `chain`, the run key of every state the search has been in (the original base, the foods and drinks baseline, the state after each accepted step), and drops, before it is estimated, every candidate whose resulting state is already in it (`dropChainStates` in `tools/whatif/pools.mjs`; the log prints the dropped ids). The key hashes the applied setup, so a full-list trigger op applied last-wins counts as the state it produces. Why: an accepted change becomes the base, and the old state rebuilt as a candidate (a trigger term back to its old value) is measured on its own low seeds against the base's more numerous seeds, so two states that simulate alike showed the same gain in both directions and the greedy loop flipped between them. The guard stays with the same-seeds gain (next bullet): it is still needed for a state the loop would otherwise revisit.
- **Pick check (the greedy chain confirms each pick before it joins; `tools/whatif/sure.mjs` the pure decisions, `confirmPick` in `tools/whatif/optimize.mjs` the runs).** The owner's go, 2026-11-11: "I would just do what we're already trying to do. Confirm the run, reduce the noise, don't recommend what you can't ensure enough." In the greedy loop the best accepted candidate (`ok[0]`) no longer joins at once: it is re-measured on fresh seeds against the chain as it is at that moment (`baseOps` before the pick's ops are added). The measurement is two arms on the same seeds, "chain so far" and "chain + this pick", 16 seeds per arm of `fin.h` hours (the last stage's hours), the search's own rules on that one reading: the error rule, and `acceptBoth` for the pass on the profit goal (the party test on another goal). **Seeds:** 20001.. (`sureOffset` = `--confirm-seed-offset` + 10000), the same block for every step, so one step's "chain + pick" arm is the next step's "chain so far" arm and the run cache gives it for free. The search keeps 1..10000, the final confirmation 10001..20000 (`pick` with `fresh` now stops at `sureOffset`; before, it took any seed above 10000). Runs are tagged `sure` in `runs.jsonl`. **Verdict** (`verdict` in `sure.mjs`): accepted passes; not accepted but the deciding figure (the buyer's net on the profit goal, the party gain on another) at least z/2 and under z errors (1 and 2 at z 2) gets 16 more seeds per arm (both arms), again, up to 64; under z/2 errors, or still not accepted at 64, fails. A pick that fails is left out and the next best of `ok` is tried (`firstConfirmed`); none left ends the chain. A failed pick leaves the finalists, so it is not offered again in a later step (a candidate rebuilt for a group the next accepted pick touched is a new candidate and is checked on its own). `result.json`: each step has `fresh` ({ `seeds` per arm, `seedFrom`, `seedTo`, `hours`, `gain`, `se` (the party's shared loot gain, totals), `gainPerUser`, `sePerUser`, `buyerNet`, `buyerNetSe` (per user, profit goal), `accepted` }); `notConfirmed` lists the failed picks, each the candidate's row plus `step` (the greedy step it was tried at) and its last `fresh`; `pickCheck` is { `seedsPerBlock`: 16, `maxSeeds`: 64, `firstSeed`: 20001 }. A merged trigger step (`mergeTriggerSteps`) gets its own `fresh`, measured by the same routine: the chain before its first merged step against the state after it (its verdict does not drop the step; the steps it merges each passed). The final confirmation is unchanged (original base against the final result on 10001..); every step is confirmed by construction, so it needs no change. **Progress:** a part `picks` (below). Test: `tools/test/whatif-sure.mjs` (scripted fresh readings: pass, fail at once, more seeds then pass, still failing at 64, a failed pick replaced), the end-to-end block of `tools/test/whatif-runner.mjs`.
- **Gain on the same seeds (unpaired rule):** a change's gain is the variant's mean minus the base's mean **on exactly the seeds the variant ran** (its lowest k that reach the stage's hours), not on the base's `baseMult` x k seeds (the owner's pick, 2026-11-10: "Compare on the same seeds"). The error is unchanged: `sqrt(sv^2/kv + sb^2/kb)` with the base's variance over all its `baseMult` x k seeds (`diffStat` in `tools/whatif/buyer.mjs`: `bs` feeds the error, the optional `bsSame` the gain; it also returns `seSame`, the error with the base's variance over the same seeds only, which `result.json` carries beside the shown one: `sharedSeSamePerUser`, `buyerNetSeSame`, the confirmation's `sharedSeSamePerUser` and `buyerByPlayer[p].seSame`; nothing uses it). Applied wherever runs become a gain against a base: `estimate` in `optimize.mjs` (the party figure, the buyer's net, the player's own supplies, the food judge's deaths and kills; so the screen, the halvings and their cuts, the Each change alone rows and ranking, and the greedy steps) and the confirmation (the original base on the result's own fresh seeds; the other fresh base seeds feed the error). The base runs on the variant's seeds are requested with the variant's (`reqPair`), so a base run not yet saved is run by the search; the base's `baseMult` x k seeds are still requested for the error. A variant whose state equals the base's has the same runs and a gain of exactly 0. The `paired` rule is unchanged. `basePerUser` and the skills report's base rates are levels, not gains, and still use the base's `baseMult` x k seeds. `result.md` states it as `Error rule: unpaired, gain on the same seeds, accept at 2 se.`
- **Foods and drinks first (the `consumables` lever; `pairs` now does nothing, kept so an old command line still runs).** The owner's ruling: foods and drinks are each run separately, the best food combination and the best drink combination (all slots of each) are decided before the rest of the run, the result says what they are, and they are the baseline of every other what-if. So `main()` runs **Stage F** (foods), then **Stage D** (drinks), then the rest. Each is a whole successive-halving run (`halve(cands, baseOps, kind, true)`) of whole fillings, every candidate at cost 0, measured against the baseline so far (Stage F on the original setups, Stage D on the setups after F's choices). The cut between its stages is **per player** (`cutPool(pool, n, true)` in `tools/whatif/pools.mjs`: the first `keep` free and the first `keep` paid candidates of each player, union in pool order), so one player's fillings cannot crowd out another's (the plain cut, used by the rest of the search, is over the whole pool). After the last stage `bestPerPlayer(pool, players)` takes each player's first accepted filling in `rankAcceptedFirst` order (a player with none accepted keeps his current items); the chosen ops are appended to `baseOps` (food ops, trigger ops that came with them, drink ops), and `result.baselineOps` is that list. Everything after F and D (the trigger probe, the screen, the halvings, the greedy steps and the confirmation) is built on `applyOps(setups0, baseOps)` and measured against that baseline, so the rest-of-search rows in `result.singles` (`gain`, `se`, `buyerNet`, `payback`) are gains over the foods and drinks, not over the setup the search started from; `result.basePerUser` and the confirmation's base are still the original setups, so the confirmation is the original base against the final `baseOps` (foods and drinks included) plus the greedy steps. The rows of F and D stay in `result.singles` flagged `stage: 'food' | 'drink'` and `hiddenFood: true` (left out of the panel and `result.md`). With the lever off there is no F or D, `result.best` is `{ foods: {}, drinks: {} }` and `baselineOps` is empty.
  - **Foods** (`tools/whatif/foodfill.mjs`, pure): the need is measured once per search by `measureNeed` (`tools/whatif/engine.mjs`: 3 seeds of 20 sim hours of the base party, the HP and MP per hour delivered by the sources that are foods, kept in `<out>/need.json`). Per player: foods another food of the same type beats are dropped (except his current foods); a filling is one food of each of as many types as there are open food slots and qualifies when its HP and MP capacity (restore x 60 per hour) are at least the need x 1.25; per type the cheapest 3 per point among the foods in a qualifying filling stay (the current foods in addition); the current filling is not a candidate. Candidates are `kind: 'food-fill'`, id `<player>:foodfill=<food0>+<food1>+<food2>`; each food goes in the slot of the baseline food of its type, else a free slot of the same resource, and a new food inherits the donor's `triggerMap` entry as a `trigger` op. A food filling is also judged by the simulation: refused (`accepted` false, `judged: 'deaths' | 'kills'`) when the party's deaths per hour are higher, or its kills per hour lower, than the base's by more than z errors.
  - **Drinks** (`tools/whatif/drinkfill.mjs`, pure): a filling is one drink of each of as many different drink types as there are open drink slots (the game allows one per type). A drink has no `triggerMap` entry of its own (engine: triggers are keyed by item hrid and a drink with no entry gets the default), so a drink filling carries no trigger ops, and the trigger levers skip drink owners. Before fillings are made the player's drink pool is pruned by `pruneDrinks({ table, style, goal, current })`, rules in this order, each counted by the first rule that drops a drink (`result.drinkPruning[player]`: `style`, `table`, `dropped: { a, b, c, d }`, `kept`, `types`, `fillings`): (a) only the coffees of the player's own combat style stay (`combatStyleOf`: melee, ranged or magic from the weapon, as the engine reads it); (b) melee and ranged keep Swiftness (attack speed) and drop Channeling (cast speed), magic the opposite; (c) profit keeps Lucky and drops Wisdom, exp the reverse; (d) exact dominance inside a type (`drinkBeats`: every buff value matched or exceeded and an ask not above, one strictly; the player's current drinks are never dropped by d). On the current prices that leaves 18 drinks of 8 types and 585 fillings per player (586 on exp). Nothing else is cut by hand: clearly worse fillings drop out at the first cut of Stage D's halving. **Why rule (b)** (the owner): "all magic casters use a basic attack ability, which is one that has zero cooldown. so in practice, magic users never auto attack, they are always ability casting, so any bonuses to auto attack don't actually help them at all. non-magic users don't benefit from cast speed for the inverted reason. They only cast sometimes, and even when they do, their cast time is super short, so reducing it wouldn't help, cooldown is their bottleneck, and they fill it with auto attacks."
  - **Free and paid pools:** every stage's cut keeps `keep[si]` free (cost 0) and `keep[si]` paid candidates (`cutPool`), union in rank order, so the many free changes (loadout tweaks, trigger terms, skill levels) do not take every place from the equipment, houses and books. The progress parts' waiting halving counts are therefore up to 2 x `keep`.
  - **`result.best`:** `{ foods: { <player>: entry }, drinks: { <player>: entry } }`, one entry per searched player; `entry.items` are the player's items after the stage in slot order, a food `{ item, trigger }` (`trigger` the readable text of its effective trigger list from `triggerText` in `tools/whatif/triggers.mjs`, e.g. `self current_hp <= 60`, or null when it always fires), a drink `{ item }` only. A changed player also has `gain`, `se`, `gainPerUser`, `sePerUser`, `buyerNet`, `buyerNetSe` (the chosen filling's figures at its last stage) and `stage`; a player the stage left alone has `unchanged: true` and no figures. Older results have no `best`.
  - **Tests:** `tools/test/whatif-food.mjs`, `tools/test/whatif-drinks.mjs` (pure), `tools/test/whatif-runner.mjs` (the `cutPool` and `bestPerPlayer` block, the Stage F and D end-to-end block, `result.md`), `tools/test/whatif-triggers.mjs`, `tools/test/whatif-progress-parts.mjs`, the last sections of `tools/test/whatif-panel.mjs`.
- **`result.md` and costs of 0:** a section `## Best foods and drinks` (one line per player, items in slot order, a food's trigger in brackets, `(no change)` for an unchanged player, then "Everything below is measured on top of these foods and drinks.") sits above `## Changes, in order`. A cost of exactly 0 has nothing to pay back, so a row's payback (and a confirmation or player line) reads `no cost, nothing to pay back`; a cost above 0 with no positive gain keeps `-`.
