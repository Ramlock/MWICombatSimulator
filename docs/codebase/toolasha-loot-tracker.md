# Toolasha's combat loot tracking, and what the exporter can read

Findings for a "combat loot" export button on `userscript/mwics-exporter.user.js` (see `game-data-fields.md` for the exporter's existing field map and method). The capture script for checking the message fields is `loot-capture-snippet.md`.

Written from source (2026-11-06) and checked against one real capture (2026-11-07, see "What the real messages showed (batch 3)"). The sections before that one are the source reading; where the capture disagreed, the section says so and the claim there is the one that stands.

## Sources

- Toolasha 2.108.4 by Celasha, CC-BY-NC-SA-4.0, libraries pinned to commit `4d71f9c5ad5c473c00558c6a7af8f0bafa763032` (the loader's `@require` lines). `toolasha-core.js`, `toolasha-combat.js` are the copies in the private repo's `docs/ground-truth/third-party/toolasha-2.108.4/`; `toolasha-ui2.js` (the loot log) was fetched from the same commit on jsDelivr (it is not in that folder). ## There is no single "combat loot tracker"

Toolasha has three separate things that track loot. They differ in what they keep and for how long.

| Piece | What it is | Where it lives | Persists |
| --- | --- | --- | --- |
| Combat Stats data (`CombatStatsDataCollector`, `toolasha-combat.js:24980`) | The latest `new_battle` message, reduced: per player the running `totalLootMap`, XP, deaths, consumables, combat stats | in memory (`latestCombatData`) and IndexedDB `ToolashaDB` / store `combatStats` / key `latestCombatRun:<characterId>` (`:25787-25795`) | one snapshot, **overwritten on every `new_battle`**; survives reloads. Each snapshot is the running total of the **whole combat session** since `combatStartTime` (days, not the newest battle), so the stored one is a multi-day sample (batch 3) |
| Expected Loot Tracker (`ExpectedLootTracker`, `:24691`) | Counts completed encounters and the monsters in them, in buckets by modifier signature; feeds Toolasha's own drop math | in memory only (`this.buckets`, `:24703`) | **not persisted**; reset on zone change, on a new combat session (battle id goes down), on character switch (`:24699-24707`, `:25530-25537`) |
| Loot Log History (`LootLogHistory`, `toolasha-ui2.js:1349`) | The game's own Loot Log (`loot_log_updated` message), merged into a longer history | IndexedDB `ToolashaDB` / store `lootLogHistory` / key `lootLog_<characterId>` (`:1352`) | up to 5000 entries, newest first, deduplicated by `characterActionId` (`:1347`, `:1378-1390`); setting `lootLogHistory`, default on (`toolasha-core.js:1221-1226`) |

Dungeon runs (`dungeonTracker`, IndexedDB `unifiedRuns`) hold no loot: the stored run has timestamp, dungeon, tier, team, duration, wave times and key counts only (`toolasha-combat.js:1461-1474`).

## What each piece holds

### 1. The game's `new_battle` message (the source of the first two)

`new_battle` arrives at the start of each encounter (Toolasha handles it as "combat start"; the data is "continuously updated" per its comment, `:25058`). Fields read by Toolasha and MWITools:

| Field | Meaning | Read at |
| --- | --- | --- |
| `battleId` | encounter counter within a combat session; goes back to 1 on a new session | `toolasha-combat.js:25513, 25527` |
| `combatStartTime` | start of the combat session (ISO string) | `:25516` |
| `monsters[]` | the monsters in this encounter; each has `hrid` | `:25456` |
| `players[]` | each party member | `:25672` |
| `players[].character.id`, `.name` | identity | `:25674, 25768` |
| `players[].totalLootMap` | **running loot for the whole combat session**, an object whose keys are opaque (`{characterId}::{itemLocationHrid}::{itemHrid}::{enhancementLevel}`, `:24964-24966`); each value has `itemHrid` and `count` | `:25771`, `:24971-24977` |
| `players[].totalSkillExperienceMap` | running XP per skill | `:25772` |
| `players[].deathCount` | player deaths this session | `:25773` |
| `players[].combatDetails.combatStats` | `combatDropQuantity`, `combatDropRate`, `combatRareFind`, `drinkConcentration` | `:25776-25781` |
| `players[].combatDetails.*Level` | the seven skill levels (Toolasha derives the raw combat level and the level-gap debuff from them) | `:24948-24961`, `:25448-25454` |
| `players[].combatConsumables[]` | food and drinks with counts | `:25680` |

The zone is **not** in `new_battle`. Toolasha takes it from the character's action queue: the first action in `characterActions` whose `actionHrid` starts with `/actions/combat/` and is not done, plus its `difficultyTier` (`getCurrentZoneInfo`, `:25380-25398`; `dataManager.getCurrentActions`, `toolasha-core.js:5532`). `characterActions` comes from `init_character_data` (`toolasha-core.js:4844`) and `actions_updated` (`:4892-4930`). A dungeon is a combat action whose `combatZoneInfo.isDungeon` is true.

### 2. Expected Loot Tracker: the only per-kill record, memory only

How kills are counted (`processExpectedLoot`, `:25413-25470`): each `new_battle` is treated as the **end of the previous encounter**. The previous battle's `monsters[].hrid` list (kept in `pendingEncounter`) is added as one kill of each of those monsters (`recordCompletedEncounter`, `:24765-24797`) to a bucket keyed by `difficultyTier | numberOfPlayers | dropRateMultiplier | rareFindMultiplier | combatDropQuantity | debuffOnLevelGap` (`:24677-24689`). The "actual loot" side is `totalLootMap` at the moment the window started, subtracted from the current one (`:25435-25437`, `:25478-25498`). Time is wall-clock from the baseline to the last completed encounter (`:24870-24875`).

Limits that matter for a comparison:

- A kill is assumed for every monster in a completed battle. A battle that ended in a player death (a wipe) is still counted as completed. `deathCount` is in the message but the tracker does not use it for this.
- It is skipped in dungeons: a dungeon counts completions only (`recordDungeonCompletion`, `:24807`), and "completion rewards only, never per-monster drops" (`:24800`).
- Wall-clock time includes any offline gap, unlike the game's own `totalActiveMillis` in the loot log.

### 3. The Loot Log entry (game's `loot_log_updated` message)

`data.lootLog` is an array, one entry per action session, newest last in the message (the panel shows newest first, `toolasha-ui2.js:1664-1686`). Fields read (`:1421-1527`, `:1379-1390`):

| Field | Meaning |
| --- | --- |
| `characterActionId` | unique id, the dedupe key |
| `actionHrid` | `/actions/combat/...` for a zone, also skilling actions (`/actions/enhancing/enhance` is skipped by Toolasha) |
| `difficultyTier` | zone tier (may be absent) |
| `actionCount` | number of actions in the session (for combat, assumed battles; unverified) |
| `startTime`, `endTime` | ISO strings |
| `totalActiveMillis` | active time, excludes offline and idle gaps; preferred over end minus start (`:1427-1431`) |
| `drops` | `{ [itemHrid]: count }` |
| `xpGains` | `{ [skillHrid]: amount }` |

This is only the player's own drops per session. It has no kills per monster, no party size, no drop-rate or quantity modifiers and no buffs. Whether the game sends the whole log on login or only changes, and how many entries it keeps, is unverified (Toolasha's extra history exists because the game's list is shorter, `:1348`, "Persists loot log entries ... for extended history").

## How a second userscript can read it

| Route | Works? | Basis |
| --- | --- | --- |
| Toolasha's IndexedDB (`ToolashaDB`) | Yes in principle: IndexedDB is per origin, not per script, so our script on `www.milkywayidle.com` can open it read-only. Gives `latestCombatRun:<id>` (one snapshot) and `lootLog_<id>` (up to 5000 entries). Not the per-kill buckets: they are never written. | store names and keys above; `dbVersion` is 20 and the DB name `ToolashaDB` (`toolasha-core.js:21, 28`) |
| `window.Toolasha` / `unsafeWindow.Toolasha` | Exposes modules (`Toolasha.Combat.combatStats` has only `initialize` and `cleanup`, `toolasha-combat.js:27995-27999`; `combatStatsDataCollector` is not in the export list, `:33568-33597`). So the tracker's objects are **not reachable** through it. | |
| Toolasha's `GM_setValue('toolasha_new_battle', ...)` | Not readable: GM storage is per script. | `toolasha-core.js:4093-4100` |
| Hooking the game's own messages, as our exporter already does | **Yes, and the only route that gets the per-kill record.** Our `MessageEvent.prototype.data` hook already sees every game message; adding `new_battle` and `loot_log_updated` to the types it keeps is a few lines, and needs Toolasha not installed at all. | `userscript/mwics-exporter.user.js:181-202` |
| Scraping the combat stats popup / loot log panel | Possible but the worst route: localized text, rounded counts, only the open panel (the same reasons as `game-data-fields.md`, "Why not read the page's HTML"). | |

What breaks the IndexedDB route: a Toolasha version that bumps `dbVersion` past what we open (opening without a version number avoids a `VersionError`, but a store rename still breaks us), a different DB name in a dev build (`ToolashaDB-dev-v<N>`, `toolasha-core.js:28`), the `lootLogHistory` setting switched off (no history), and a debounced write that has not landed yet (3 s, `SAVE_DEBOUNCE_DELAY`, `toolasha-core.js:32`). The IndexedDB route also depends on Toolasha's field names, which are its internals and change between versions.

## What the sim needs, and who has it

The sim's drop model (`results-and-profit.md`, "How drops are computed") takes per displayed player: kills per monster hrid (`simResult.deaths`), difficulty tier, number of players, `dropRateMultiplier` = `1 + combatDropRate`, `rareFindMultiplier` = `1 + combatRareFind`, `combatDropQuantity`, `debuffOnLevelGap`, and returns an expected and a sampled amount per item, per run length. Rates are divided by `numberOfPlayers` (`src/main.js:2019`).

A like-for-like comparison per zone needs, for a window in which the modifiers did not change:

| Field | `new_battle` hook (our own) | Toolasha `latestCombatRun` | Toolasha loot log history |
| --- | --- | --- | --- |
| Zone hrid, tier | yes (from `characterActions`) | no | yes |
| Kills per monster hrid | yes, from `monsters[]` of each completed battle (same assumption as Toolasha) | no | no |
| Loot per item, over exactly that window | yes (difference of `totalLootMap`) | running total only, no window | per session, not per modifier window |
| Window length (wall-clock) | yes | no | yes (and active time) |
| Number of players | yes (`players.length`) | yes | no |
| `combatDropRate`, `combatRareFind`, `combatDropQuantity` | yes | yes (latest only) | no |
| `debuffOnLevelGap` | yes, derived from the seven levels | no (only the floored `combatLevel`) | no |
| Player deaths in the window | yes (`deathCount`) | yes (latest) | no |
| Monsters killed per zone, by wave (dungeons) | no, nobody keeps it | no | no |

Toolasha does not keep, even in memory: loot per encounter (only the running total), the party's drop modifiers over time, and anything for dungeons beyond completions. Loot a player did not receive (other party members' loot) is in `totalLootMap` per player but is not what the sim compares.

Findings that change the batch 1 proposal:

1. **Kills can be counted from `battle_updated`, not assumed from `monsters[]`.** MWITools tracks each monster's `cHP` per index from `new_battle` and credits a kill when a `battle_updated` `mMap` entry reaches 0 (`:40264`, the `killed` counter, `kill` event at `:40383`); the monster hrid is the `new_battle` `monsters[index].hrid` (`:40047`). KikiMeter's header says the same ("Kills go to the player in the same message when a monster's cHP reaches 0"). This removes the wipe over-count in Toolasha's rule. Cost: handling `battle_updated`, which is frequent.
2. **The difficulty tier is not in the top level of `new_battle`.** (Checked in batch 3: the per-monster `difficultyTier` is the tier; the per-player one was 0.) KikiMeter's comment (`:2294-2305`), written after a capture, says `new_battle` has a top-level `tier` that is the guild-trial floor (1-16), and `difficultyTier` appears only per player or monster with another meaning; the personal combat tier comes from `action_completed.endCharacterAction.difficultyTier`, and Edible Tools reads it the same way (`:2315-2318`). Toolasha reads the character's queued action (`characterActions`, above). The capture confirmed it in substance (claim 5 below).
3. **Edible Tools replays its stored loot log into the page as a synthetic `loot_log_updated` message** (`:1874-1878`, `:2042`, `lastWs.dispatchEvent(new MessageEvent('message', ...))`). A recorder hooking `loot_log_updated` must dedupe by `characterActionId` or `startTime` and may see old entries again.
4. **No extension persists loot per modifier window.** KikiMeter and Edible Tools keep session-running loot, MWITools none, Toolasha one snapshot. A recorder that does is new.
5. **Extra data available from the same messages at little cost** (none of it needed for the drop comparison, all of it useful for checking the sim): kills per monster; damage dealt and taken per player (MWITools' attribution is long, `:40108-40360`, KikiMeter's rule is simpler: the player present in `pMap` caused the monster HP change in that message, header comment `:20-37`, kills `:34`, `:598`); healing; consumables used (`combatConsumables[].count` differences, or `battle_consumable_ability_updated`); XP per skill (`totalSkillExperienceMap` differences); hit and miss counts (needs attribution); time alive per monster; player deaths (`deathCount`).

Data a recorder could capture, against who captures it. "Sim" marks what the drop comparison needs (`results-and-profit.md`).

## What the real messages showed (batch 3)

One capture by a player of a few minutes of normal combat: one zone, one party, about ten encounters, taken with `loot-capture-snippet.md`. Each claim of the proposal was checked against it. The capture file and every number from it are private; this section has field names and shapes only, and every example value is invented.

**The capture could not show:** a zone or tier change, a loot log (`loot_log_updated`), `actions_updated` or `new_character_action` (none arrived, see below), a player death or wipe, a dungeon, a change of party size or of the drop modifiers, a new combat session, and a combat session that starts after the hook is installed. Anything about those is still source-reading, not observation.

| # | Claim | Result |
| --- | --- | --- |
| 1 | `new_battle` fires once per encounter | **Holds.** One per encounter, `battleId` up by 1 each time, `wave` 0 outside dungeons. `combatStartTime` was identical in all of them and days older than the capture: it is the start of the combat session, so a change of `combatStartTime` marks a new session (better than "`battleId` goes down"). The next `new_battle` arrives a constant ~3 s after the previous encounter's `action_completed` (respawn gap). |
| 2 | `totalLootMap` is cumulative for the session | **Holds, and it is much longer than a run.** It counts everything looted since `combatStartTime` (days, in the capture), is never reset, and no entry went down. Only the difference between two `new_battle` snapshots means anything. Snapshot N+1 minus snapshot N is exactly encounter N's loot: every delta was non-negative and showed up with the kills of that encounter. An entry is keyed `<characterId>::<itemLocationHrid>::<itemHrid>::<enhancementLevel>` and valued with an inventory-item record: `id`, `characterID`, `itemLocationHrid`, `itemHrid`, `enhancementLevel`, `count`, `offlineCount`, `hash`, `createdAt`, `updatedAt`. New items appear as new keys, so the key set grows. Sum `count` by `itemHrid` (and `enhancementLevel`). The map includes Coin as `/items/coin`. |
| 3 | Kills from `battle_updated` `mMap` HP reaching 0 | **Holds, exactly.** `battle_updated` is incremental: it carries only the entries that changed, and many messages have an empty `mMap`. `mMap` and `pMap` are objects keyed by index as strings (`"0"`, `"1"`), index into `new_battle` `monsters[]` / `players[]`, in no fixed order. A monster entry is `{cHP, mHP, cMP, mMP, isActive, leftCombat, atkCounter, abilityHrid, int, dmgCounter, critCounter}`; the death update has `cHP: 0` and `isActive: false`. For every encounter that had a `new_battle`, the number of indexes seen dying equalled `monsters.length`, and the hrid comes from `monsters[index].hrid`. Counting each index once per `battleId` is enough. |
| 4 | A hook installed mid-encounter loses that encounter | **New.** The first `battle_updated` messages belonged to an encounter whose `new_battle` was never seen, so its monsters and its loot baseline are unknown. The recorder must skip an encounter without a `new_battle` and take its first baseline from the first `new_battle` it sees. |
| 5 | Difficulty tier is not in `new_battle` | **Changes.** There is no top-level `tier` (top-level keys: `type`, `combatStartTime`, `battleId`, `wave`, `players`, `monsters`). `players[].difficultyTier` exists but was 0 while the party fought at a non-zero tier, so it must not be read. `monsters[].difficultyTier` carried the real tier, and `action_completed.endCharacterAction.difficultyTier` agreed with it. So the tier is in the same message as the monsters; KikiMeter's second-hand claim holds in substance, with the per-monster field as the tier source. |
| 6 | Zone from `action_completed.endCharacterAction` | **Holds.** `action_completed` fires once per encounter. `endCharacterAction` has `id`, `characterID`, `partyID`, `actionHrid` (the zone, `/actions/combat/...`), `difficultyTier`, `hasMaxCount`, `maxCount`, `currentCount`, `wave`, `isDone`, `createdAt`, `updatedAt` and more. `currentCount` equalled the finished encounter's `battleId` in the capture; do not rely on that. `new_battle` has no zone, so the zone of a window is known only after its first `action_completed`. |
| 7 | Party size from `players.length` | **Holds.** And more: every `new_battle` carries a **full record of every party member**, not only the player: `character` (with name and ids), `totalLootMap`, `totalSkillExperienceMap`, `totalAbilityExperienceMap`, `deathCount`, `combatConsumables`, `combatAbilities`, `combatBuffMap`, `combatDetails`. One browser sees the whole party's loot and modifiers. `pMap` indexes follow `players[]`. Which entry is the player themselves is not in the message (it needs the character id from `init_character_data`, which the exporter already reads). |
| 8 | Drop modifiers | **Holds.** `combatDetails.combatStats` has `combatDropRate`, `combatDropQuantity`, `combatRareFind`, `drinkConcentration` and `combatExperience`. They did not change over the capture. |
| 9 | Buffs | **New.** `combatBuffMap` is the full buff list, keyed `/buff_uniques/...`, each `{uniqueHrid, typeHrid, ratioBoost, ratioBoostLevelBonus, flatBoost, flatBoostLevelBonus, startTime, duration}` (`duration` in nanoseconds, `startTime` is the zero date for permanent buffs; auras add `multiplierForSkillHrid`, `multiplierPerSkillLevel`). `typeHrid` such as `/buff_types/combat_drop_quantity` says what it modifies, so the source of a modifier (community buff, house room, tea, guild) can be read. Temporary buffs (coffee, aura) get a new `startTime` whenever refreshed, so the map changed in nearly every `new_battle` while the drop modifiers stayed the same: **windows must not be keyed on the buff map**, only on the derived `combatStats` values. |
| 10 | Levels | **Holds, with a caveat.** `combatDetails` has `combatLevel`, `staminaLevel`, `intelligenceLevel`, `attackLevel`, `meleeLevel`, `defenseLevel`, `rangedLevel`, `magicLevel`; the values can be fractional, so they are effective levels, not stored levels. Record them as given. |
| 11 | XP | **Holds.** `totalSkillExperienceMap` is cumulative per skill, like the loot; the difference between two `new_battle` snapshots is the XP of that encounter. It is fractional. |
| 12 | Consumables | **Holds, with a split.** `combatConsumables[]` is `{itemHash, itemHrid, enhancementLevel, count, availableTime}` per player; `count` falls by one on use, so the use of the whole party is the difference between snapshots (a count that rises is a refill, ignore). `battle_consumable_ability_updated` has two payload kinds: `{ability: {abilityHrid, level, experience, availableTime}}` (ability XP and cooldown, the large majority, not needed) and `{consumable: {itemHrid, enhancementLevel, count, availableTime}}` (one use of food or a drink, by the capturing player only, `count` = remaining). |
| 13 | Player deaths | **Not shown.** `deathCount` per player was constant. No `pMap` entry ever had `isActive: false`, `leftCombat: true` or `cHP: 0`, so what a death or wipe looks like in `battle_updated` is unknown. Kills counted from `mMap` stay correct whatever happens (a wiped encounter simply has fewer dying monsters). |
| 14 | `battle_updated` volume | Several per second, small (a few hundred bytes), mostly changed entries only. `new_battle` is large (tens of KB: every party member's avatar, ability, buff and stat data) and arrives about every 20 s. A few minutes is about 1 MB, so the snippet's 40 MB cap is about two hours. The recorder keeps aggregates, never the raw messages. |
| 15 | Message order | `action_completed` of encounter N can arrive up to a few seconds **before** the last `battle_updated` that shows a monster of N dying. Attribute by `battleId` (every `battle_updated` has one), never by arrival order. |
| 16 | The hook works | **Holds.** The socket URL filter (`milkywayidle`, `/ws`) and `currentTarget.url` worked on the live game: all four message kinds above were received and the page was unaffected. Coexistence with other userscripts was not checked (which were installed is not known). |
| 17 | `loot_log_updated`, `actions_updated`, `new_character_action` | **Not shown, none arrived in a few minutes of combat.** Inferred, not observed: the game sends `loot_log_updated` at login or when the Loot Log panel is opened (Toolasha hooks it and also watches the page for the panel, `toolasha-ui2.js:1558-1565`), and `actions_updated` / `new_character_action` when the action queue changes (Toolasha uses `actions_updated` to detect flee or cancel, `toolasha-combat.js:2122`). A console snippet pasted after login cannot see login messages. The loot log's shape and history depth remain unverified; the next capture should open the Loot Log panel once and change zone once. |

### The latest `new_battle` alone is the game's own battle popup

Checked against two screenshots of the game's battle popup ("Battle Info" in the combat panel, private) taken a few minutes after the capture. Every figure in the popup is derivable from one `new_battle` message, and the viewing player's popup matched the corresponding `players[]` entry item by item:

| Popup line | Where it comes from | Checked |
| --- | --- | --- |
| Combat Duration | now minus `combatStartTime` (wall-clock, days) | matches |
| Battles | `battleId` | matches |
| Encounters/hour | `battleId` divided by the duration in hours | matches |
| Deaths | the player's `deathCount` | matches |
| Items looted | the player's `totalLootMap` summed by item | the items compared (essence, tea leaves, leather, treasure chests, Coin, ability XP) match the capture's last snapshot plus the few encounters since |
| Experience gained, per skill and per ability | `totalSkillExperienceMap`, `totalAbilityExperienceMap` | match |
| Revenue and exp per hour and per day, total revenue | the maps above, priced with market prices, divided by the duration | derived by the game; no new field |

So **`totalLootMap` is the running total of the whole combat session since `combatStartTime`, not of the newest battle**: in the capture's game that was days of continuous combat and tens of thousands of encounters. The earlier wording of this document ("holds only the newest battle's running totals") was right only in the sense that the stored snapshot is the newest one; each snapshot is the whole session. Toolasha's `latestCombatRun` (table above) is therefore a multi-day sample, kept across reloads, overwritten only by the next `new_battle`. The numbers rise monotonically across encounters in the capture: no entry went down, the key set only grew.

**What resets it: not shown by the capture.** The capture is one uninterrupted stretch of one session, and `combatStartTime` never changed in it. From source only (Toolasha treats a lower `battleId` or a new `combatStartTime` as a new combat session, `toolasha-combat.js:25513-25537`, and resets its own tracker on zone change), a stop of combat or a change of zone very likely starts a new session and zeroes the totals; a death does not stop combat (the capture's player had died several times with the totals intact, `deathCount` counts them); a reload or relog is unobserved. A cheap test for whoever owns the game account: stop combat, start it again, open the popup (is the duration back to 0?), then change zone in the same way.

**What an export of the latest `new_battle` alone gives:** per party member, over the whole session: loot per item, XP per skill and per ability, deaths, duration, number of encounters (hence encounters per hour), plus the state at that moment: drop modifiers, levels, the buff list, consumable stock, the party size, the current encounter's monsters and their tier. With the zone from the character's combat action (`init_character_data` `characterActions`, which the exporter already reads, or the latest `action_completed`), that is a full-session sample: a very low-noise per-hour loot and encounter rate for one zone and one setup, the numbers the game's own popup shows and the sim's profit per hour can be compared with directly.

**What it still lacks:**

- Kills per monster type. Only the current encounter's monsters are in the message. The mix can be estimated as `battleId` times the zone's spawn table (game data the exporter already reads), but that puts the sim's own spawn assumption into the comparison.
- The history of everything that is "current state only": `combatBuffMap` and `combatStats` are the values at the moment of the message (temporary buffs carry a `startTime` and `duration`; permanent ones have the zero date), so a coffee that expired or a house room built last week are invisible. Levels rise over a multi-day session (the XP maps show it), so the average level is unknown. Party size and composition over the session are unknown.
- Splitting the session by a change of zone, tier or modifiers: the totals mix everything since the start. A long stable farm is a clean sample; a session with changes is not.
- Loot per encounter or per monster type; the encounter at which a given drop occurred.
- Anything after a combat stop: the game zeroes it, nothing is kept.

**The smallest useful button.** "Copy combat session": the exporter keeps in memory only the latest `new_battle` (and the latest `action_completed` for the zone), and the command copies it reduced and anonymized: `battleId`, `combatStartTime` and the capture time, zone, tier, party size, the current encounter's monsters, and per player slot the loot by item, XP maps, deaths, modifiers, levels, buff list and consumable stock. No names, character ids or user ids. No storage, no clear command, no cap; it works from the first encounter after the page loads (about 20 s). It needs `new_battle` and `action_completed` in the hook's type list, a few lines on top of the existing hook.

**What a recorder adds on top** (the plan of this document): kills per monster type counted exactly from `mMap`, windows split on every change of zone, tier, party size, modifiers or levels (so a change no longer pollutes the sample), loot per window and per encounter, the modifiers over time, and survival of a combat stop or a reload (capped, with the clear command). The two share the same message hook and the same reduced player record, so the session button is the recorder's first slice, not a throwaway.

**Recommendation** (a design decision, not settled): build the session button first and ship it on its own, because it is stateless and gives every party member's multi-day sample at once, and add the recorder after, because the questions the sim comparison still has (kills per monster, modifier history, windows) need it. The button alone cannot say whether a difference comes from the drop model or from the monster mix.

### Worked example (shape only)

From the capture the batch computed, for the window between the first and last `new_battle`: encounters attributed (snapshot N to N+1), kills per monster hrid and per hour (kills counted from `mMap`), loot per item per player (snapshot difference), per hour and per kill, XP per skill, and consumables used, with the window length as the first-to-last `new_battle` time. The kill count matched the monsters listed in each `new_battle`, and the loot deltas were all non-negative. The figures are private and not in this repository.

### What this changes in the proposal

1. **Tier** from `monsters[].difficultyTier`; **zone** from the latest `action_completed`. `tierSource` becomes `"monsters"`.
2. **Window key**: zone, tier, `combatStartTime`, party size, and per player the three drop modifiers and the levels. Never the buff map.
3. **Loot, XP and consumables per window** are sums of per-encounter snapshot differences, for encounters that have both a `new_battle` and the next one. The last encounter of a window needs the next `new_battle` to close, which is also what opens the next window.
4. **Kills** from `mMap` HP, counted once per index per `battleId`, with the fallback dropped (it held exactly).
5. **One browser records the whole party**, so the export holds every player's modifiers, loot, XP and combat counters, anonymized by slot (a design decision, session-settled, with a `selfOnly` switch).
6. **A capped ring of per-encounter rows** (monster hrids, kills, loot difference, duration) is cheap and is the finest data the sim comparison can use; in the recorder spec below.
7. **Buff breakdown at window start** (`typeHrid` and boost per buff) is cheap and shows where a modifier comes from (recommended).

## Recorder spec (version 1, draft for review)

A single, self-sufficient combat recorder in the exporter. **Design decisions (session-settled, 2026-11-06):** it records everything the combat messages let it record, including damage, accuracy, healing and per-source attribution; it must be enough on its own, with no need to also run Toolasha or MWITools; reading their stored data is allowed as an optional extra only; the export carries the whole party, each member labelled only by slot with no names or ids, and a Settings switch `selfOnly` limits it to the player; read-only, nothing sent anywhere; capped record kept in each player's browser with a "Clear recorded loot" command. **Everything else below is a proposal**, marked as such, and each choice is in the open questions.

Checked against one capture of about three minutes of one zone with a party (ten encounters). "Exact" means the value is read straight from a message field or is arithmetic on fields; "heuristic" means it needs an inference (MWITools' approach, see the survey). All volumes are from that capture, scaled to an hour of continuous combat; they are estimates, not measured over a long run.

### What the combat messages carry, and how well

`battle_updated` is the only tick-level message. It has no event list: no per-hit record, no damage amount, no attacker or target. Everything below is derived from state changes between ticks. Per entity (`pMap` for players, `mMap` for monsters, keyed by index) a message holds only entities that changed, with: `cHP`, `mHP`, `cMP`, `mMP`, `isActive`, `leftCombat`, `atkCounter`, `int`, `dmgCounter`, `critCounter`, and when present `abilityHrid`, `isAutoAtk`, `isStunned`, `isBlinded`, `isSilenced`.

### Data model (proposed)

One **window** per stretch of unchanged conditions, one **encounter row** per finished encounter. Both hold, per party member by slot, the same counters; a window is the sum of its encounters.

Per player and encounter (an `unattributed` source holds what could not be credited):

```json
{
  "slot": 0,
  "dealt": { "total": 5200, "bySource": { "/abilities/...": { "amount": 3100, "casts": 4 }, "auto": { "amount": 2100, "casts": 9 }, "unattributed": { "amount": 0, "casts": 0 } }, "byMonster": { "/monsters/...": 5200 } },
  "taken": { "total": 900, "bySource": { "/monsters/...": 700, "unattributed": 200 } },
  "healed": { "regen": 360, "other": 240 },
  "mana": { "spent": 190, "regained": 120 },
  "attempts": 16,
  "splats": { "received": 6, "crit": 5 },
  "status": { "stunnedMs": 0, "blindedMs": 0, "silencedMs": 0 },
  "loot": { "/items/...": 2 },
  "xp": { "/skills/ranged": 120.5 },
  "abilityXp": { "/abilities/...": 3.2 },
  "consumablesUsed": { "/items/...": 1 },
  "deaths": 0
}
```

Encounter row: `battleId`, `startedAt` and `endedAt` (server time), `monsters[]` (`hrid`, `isBoss`, `killMs`, `maxHP`), `players[]` as above. Window: `zoneHrid`, `difficultyTier`, `numberOfPlayers`, `startedAt`, `endedAt`, fragments with active time, `battles`, `kills` per monster hrid, `players[]` as above summed, plus per player `stats` (the `combatStats` and `combatDetails` values at window start, abilities with levels), `buffEvents[]` (buff added or removed at which encounter, with `typeHrid` and boosts), and `monsterStats` per hrid (the enemy record once). Every attributed amount sits next to its `unattributed` remainder, and the file says per field whether it is exact or heuristic (`"attribution": "counter"`).

Format envelope: `{ "format": "mwics-loot", "version": 1, "exportedAt": ..., "selfOnly": false, "windows": [...], "encounters": [...], "lootLog": [] }`. `slot` is the index in `new_battle` `players[]`; `self` is set only when the player's character id is known from `init_character_data`. Names, character ids and user ids are never in the file. With `selfOnly` on, `players[]` holds only the `self` entry (if `self` cannot be determined, the export refuses and says so).

**Windows** (proposed) start at the first `new_battle` after a change of zone, tier, `combatStartTime`, party size, or any player's `combatDropRate`, `combatRareFind`, `combatDropQuantity` or levels. The buff map is never a window key (it changes almost every encounter); buff changes go to `buffEvents`. **Fragments** split a window where messages stop for longer than a gap threshold (placeholder 60 s).

### Attribution rules (proposed; each tested on the capture)

1. **Baseline.** A unit's first `battle_updated` record in an encounter has nothing to subtract from. Use the same unit's record in that encounter's `new_battle`: `players[]` / `monsters[]` carry `currentHitpoints`, `currentManapoints`, `attackAttemptCounter`, `damageSplatCounter`, `criticalDamageSplatCounter`, `preparingAbilityHrid`, `isPreparingAutoAttack`, which are the same quantities as `cHP`, `cMP`, `atkCounter`, `dmgCounter`, `critCounter`, `abilityHrid`, `isAutoAtk`. All 30 player first-records and all 25 monster first-records in the capture's encounters with a `new_battle` had a usable baseline, and 17 of the 30 players had acted since it. Without the baseline, the first record of a player who acted looks like "no actor": all 12 of the 14 messages the earlier (non-baselined) rule left unattributed were exactly that, the other 2 being the encounter with no `new_battle`. An encounter with no `new_battle` (hook installed mid-encounter) has no baseline and is skipped.
2. **Damage to a monster**: each monster whose `dmgCounter` rose took that many damage events (hit if `cHP` fell, miss otherwise). Credit them to the one player whose `atkCounter` rose; the ability is that player's previous prepared `abilityHrid` (or auto attack). Two or more player actors in one message, or none after rule 1: flagged `ambiguous`, never split by a guess. In the capture: 255 of 255, none flagged.
3. **Damage to a player**: the same, with the monsters as actors. 118 events, each with exactly one monster actor; 0 with two or more.
4. **Damage over time.** A player damage event with no monster actor is a tick of an earlier ability that has `damageOverTimeRatio` > 0 in the game's ability data (`firestorm`: ratio 1 over 6 s, `maim`: ratio 1 over 9 s; the engine ticks every 3 s, `combatSimulator.js:27,888-914`, and creates the series from the hit that landed, `:1432-1441`). The tick is attributed to the hit that is 3.0, 6.0 or 9.0 s (+-0.25 s) older on the same unit with that ability; the amount is that hit's damage x ratio / ticks. In the capture all 20 such events matched, and all 20 came from `firestorm` cast by monsters (14 from `infernal_warlock`, 4 from `abyssal_imp`, 2 from `demonic_overlord`, by the monster whose hit started each series), none from `maim`; so in this capture the damage over time is damage **taken** by the party. The rule is general: damage over time from either side, source = the caster of the ability whose hit started the series; `firestorm` and `maim` are the only abilities with `damageOverTimeRatio` above 0 in the game data (`abilityDetailMap.json`) and no ability has a heal-over-time field, so this is a game-data effect, not an inference. In the capture (value within 1, time within 0.1 s). A tick can land in the next `battleId` after the source monster has died. If two series overlap and the time matches both, the tick is flagged `ambiguous`.
5. **Other damage mechanics.** The earlier draft used "damage over time" as a label for unexplained residue; it is a real mechanic (rule 4) (`firestorm`, `maim`). Extra abilities queued by a chance stat (`blaze`, `bloom`; bloom is a heal, see Healing). Reflect (`physicalThorns`, `elementalThorns`), `retaliation`, life steal, `hpDrainRatio` (`life_drain`) and mana leech also exist in the engine (`combatUtilities.js:207-283`); none was seen in the capture, so no rule is tested. Thorns or retaliation would show as a monster damage event with no player actor while a monster actor is present (the 3 messages with both were a player's area ability and had a player actor).
6. **Healing and mana.** Regen is a formula (table); a heal ability executed by a player is the source of a rise in that message; a bloom heal and a food heal (instant or in 5 s ticks) are named sources (see Healing); mana drops equal the executed ability's cost; two casts in one message (an `atkCounter` delta of 2) cost the sum.
7. **Counters** are decoded (table): per event, hit or miss from the HP change, crit from `critCounter` equalling the new `dmgCounter`. When `dmgCounter` rose by 2 or more in one message (none in the capture) the hits are counted but the crit is only known for the last event.

Not tested because the capture has no case: thorns, retaliation, life steal, hp drain, mana leech, a player damage-over-time hit on a monster, stuns changing the executed ability.

### Damage events, decoded (batch 5)

- `dmgCounter` is a per-entity splat counter: it rises by one for every damage event the entity receives, including a miss (damage 0). `critCounter` holds the `dmgCounter` value of the last crit. Both are exact; there are no HP drops without a `dmgCounter` rise on monsters in the capture (0 of 261), and 51 rises without a drop on monsters and 44 on players are misses. Monster hit rate in the capture: 261 hits to 51 misses; player: 89 to 44 (before the baseline fix; the proportions are only illustrative, the sample is three minutes).
- `abilityHrid` is the ability the unit is **preparing next**, not the one that just ran. The one that ran is the previous record's value. This is why mana and damage line up only with the previous record: the cost is taken, and the effect lands, when the unit executes (`atkCounter` rises), and the new preparation shows in the same record.
- `int` changes with `atkCounter`; the monster values were the monster's attack or cast interval in nanoseconds (2343750000 ns = 2.34 s; the player values varied per ability and were not used).
- Damage over time and any ability with a cast time resolve in a later message than the one that shows its `abilityHrid` (rule 2 handles the executed ability; rule 4 handles DoT).

### Healing, mana: what stays open

- Exact: regen (formula), a heal ability's rise in its executing message, mana cost per cast.
- **Bloom (a named source, fits the capture).** `combatStats.bloom` is a chance; after each ability a unit casts, with that probability the engine queues a second ability `bloom` (`combatSimulator.js:1216-1222`, defined inline in `ability.js:58-95`, not in the game's ability data map; `blaze` is the same for a damage ability). Bloom heals the ally with the lowest HP percentage (`combatSimulator.js:1634-1651`, self included) for a random amount from `healingAmplify x (1 + 10)` to `healingAmplify x (0.15 x magicMaxDamage + 10)` (`combatUtilities.js:299-302`), with no mana cost, cooldown or cast time, so it lands in the same message as the cast. The capture: one player has a bloom stat (0.38); that player executed 93 actions other than the heal ability `quick_aid` (90 ability casts, 3 auto attacks); 29 of them had a non-regen HP rise in the same message (31 percent; 0.38 x 93 = 35 expected, standard deviation about 5), and 29 of the 30 rises in those messages lie inside the range predicted from that player's recorded `healingAmplify` (0.957) and `magicMaxDamage` (21.5 to 222.4); one was 495. The five `quick_aid` casts each had a rise, which is the heal ability itself. Whether bloom also rolls on auto attacks is not decided (3 auto attacks, 1 rise).
- **Quick Aid (a heal ability).** `quick_aid` heals the ally with the lowest HP percentage for `healingAmplify x (1 + flat)` to `healingAmplify x (ratio x magicMaxDamage + flat)`, flat = 40 + 0.4 per ability level, ratio = 0.3 + 0.003 per level (ability data), cast time 0.2 s, cooldown 12 s. For the one holder in the capture (level 51, recorded `healingAmplify` 0.957 and `magicMaxDamage`) the range is 120.1 to 730.6. The target may be **any party member**, not the caster. The capture has 5 casts, counted three ways that agree (5 executions by `atkCounter` with the previous prepared `abilityHrid`, 5 records that newly prepare it, 5 ability-XP steps of +0.1 in `battle_consumable_ability_updated`). All 5 have a non-regen HP rise inside the same message; of the 6 rises in those messages, 4 are in the heal range (382, 395, 501, 591; at least two landed on another player, not the caster) and 2 are below 120.1, the size of a bloom heal (bloom fires after every ability cast, including this one). I cannot say why the fifth cast shows no rise in the heal range: the target may have been nearly full so the heal was clipped by `addHitpoints`, not checked.
- **Rule (any party member, any ability)**: a non-regen HP rise on **any** player in the same message, or in a later message within 0.7 s (the 0.2 s cast plus arrival lag), as an executed heal ability or an executed ability by a player with `combatStats.bloom` > 0, is credited to that cast and to `bloom` or the heal ability by amount (inside the heal ability's range, else the bloom range); the caster and the target are separate fields. When one message holds both a heal ability and a bloom roll, the amounts are told apart by range and the record is flagged `ambiguous` where the ranges overlap. When a player's `atkCounter` rose by 2 or more in the message, the ability executed second is not visible (only the previous prepared one and the new preparation are), so a heal in that message is attributed to a possible heal ability of that player and flagged `ambiguous`.
- **Food heals over time (a game-data effect, consumables only).** A consumable with `recoveryDuration` above 0 restores `hitpointRestore` (and `manapointRestore` if the data has it) over that time in ticks every 5 s, `recoveryDuration / 5 s` ticks (`combatSimulator.js:26,1113-1139`); one with `recoveryDuration` 0 restores it at once. Example from the item data: `/items/spaceberry_cake` restores 350 over 30 s (6 ticks) with a 60 s cooldown; `/items/spaceberry_donut` restores 280 at once, cooldown 60 s. No ability has a heal over time. In the capture all 21 actor-less non-regen rises are explained: 15 are the ticks of three cake series (each series: 5.0 s apart, 58, 58, 59, 58, then a clipped tick when HP is full, which is the pattern of cumulative floors of 350/6; the sixth tick of a series is not seen when HP is full because nothing changes), 2 are the instant restores of 280 of a donut, 3 are a regen tick in the encounter that has no `new_battle` baseline (so no regen amount to compare), and 1 is a regen tick clipped at full HP. The consume itself: for the capturing player it is a `battle_consumable_ability_updated` message (`consumable` form); for the other members no such message arrives, but their `new_battle` `combatConsumables[]` count falls by one and `availableTime` = the consume time + the item's cooldown (3 of 3 consumes: consume = `availableTime` minus 60 s, first tick 5 s after it plus about 0.8 s of arrival lag). So the recorder attributes the ticks to the consumable from the count drop and `availableTime` (inferred from the snapshot, not from a consume message for those members), and a tick series ends after `recoveryDuration / 5 s` ticks.

- **Telling a consume from a market trade (other members).** A trade moves `combatConsumables[].count` too, and a market trade can move it at any time while battling, so a trade and a consume can land in one count change (for example -6 = 5 sold and 1 eaten). The count is therefore not the consume test. Rule (proposed): a consume is decided by the **cooldown restart**, that is `availableTime` changed to a new cooldown end, together with the matching restore (an instant rise equal to `hitpointRestore` or `manapointRestore`, or ticks starting 5 s after `availableTime` minus the item cooldown, for a food with a recovery time; for a drink the buff entry's `startTime` in the interval). One cooldown restart is one consume (the cooldown, 60 s for the foods seen, exceeds the roughly 20 s between `new_battle` snapshots; an item with a shorter cooldown can restart more than once per interval, then the number of restores counts them). The rest of the count change, `delta + consumes`, is booked as a trade, positive or negative, and is not flagged ambiguous. A cooldown restart with no matching restore, or a restore with no restart, is flagged. **Tested on the capture**: across 162 consecutive snapshot pairs of consumables, 23 had both a count change and an `availableTime` change (all those count changes were exactly -1; the three cake restarts and the two donut restarts also had their restores), 0 had a count change only, 0 had an `availableTime` change only, 139 had neither; so in the capture the count never moved late and a cooldown never changed without a count change. **Untested** (no trade in the capture): every case with a count change other than -1, a consume and a trade in one interval, a trade landing in the same interval as a consume, a drink or a mana food checked against its restore or buff. For the recording player a consume arrives as its own `battle_consumable_ability_updated` message (`consumable` form, 7 in the capture), so his trades can be excluded directly; the capture holds no market message of any kind (it recorded only the four combat message types, without a type census), so the name and shape of a market fill message are not known from the capture.
- **The cooldown restart alone is the consume (proposed by the owner, not settled; 23 of 23 in the capture).** Rule: a changed `availableTime` (a new cooldown end) on a consumable is one consume, with no other condition. The matching restore stops being a condition and becomes a check on the amount: the expected restore (an instant rise of `hitpointRestore` / `manapointRestore`, or its ticks every 5 s, or a drink's buff entry) is compared with what was recorded, and a mismatch sets `healMismatch` on the consume (with the expected and recorded amounts). This replaces the earlier "restart plus matching restore" wording above; the count-change split (`delta + consumes` is the trade) is unchanged. Support: all 23 cooldown restarts in the capture had a count change of exactly -1 and, where the item restores, their restore; no `availableTime` change occurred without a consume. A trade never needs to be separated from a consume by the count: the count of a food can also move by a market trade at any time while battling, the consume is decided by the cooldown restart alone, and the rest of the count change is the trade. **Session boundary:** swapping the food in a slot and changing zone cannot be done in the middle of combat; they end the combat session, and the next session starts with its own `new_battle` baseline, so a session boundary resets the food baseline (count and `availableTime` are read fresh, nothing is compared across it); they are not cases of a cooldown change inside a session. **Death (the one case left, untested).** The engine's model is predictable: a player's respawn (`combatSimulator.js:352-365`) restores HP and MP and clears buffs and crowd control but does not touch the food or drink cooldowns; a consumable's `lastUsed` is set only by a consume (`combatSimulator.js:1101`) and reset only at combat start (`combatUnit.js:558-560`, reached from `reset`, `:543-547`, where the comment at `:542` says a party wipe keeps the players' cooldowns). So a death is expected to leave `availableTime` unchanged, and a cooldown restart seen around a death is still a consume; a drink's buff entry would be gone after the respawn (buffs cleared) while its cooldown stays. This is the engine's model, not read from the game: if the game resets cooldowns on death, `availableTime` would change with no -1 count and no restore, which the recorder flags `healMismatch`, and the tell is the unit's `cHP` reaching 0 (`leftCombat`) and the `deathCount` running total rising shortly before the change. Untested until a capture contains a death. Until then the recorder books a restart as a consume and sets `healMismatch` when the restore is missing, so a surprise surfaces as a flag, not as a silent error.
- **The one rise of 495 now fits a Quick Aid** (not proven): it is on the caster, in a message where the caster's `atkCounter` rose by 2 (two actions between two records; the first executed one was an auto attack, the second is hidden), no cast within the previous 0.7 s, and 495 lies inside the heal range 120.1 to 730.6. Two records in the whole capture have an `atkCounter` delta of 2 or more. Recorded with the possible source `quick_aid` and the flag `ambiguous`. With bloom, food, regen and Quick Aid named, no HP rise in the capture is unexplained.

What `combatBuffMap` gives for the party (one snapshot per encounter, current values with `typeHrid`, flat and ratio boosts, `startTime`, `duration`): one entry per active buff, keyed by a `/buff_uniques/...` name that identifies the source family in the capture: guild buffs (attack speed, cast speed, damage), community buffs (drop quantity, wisdom), house rooms (attack, defense, intelligence, magic levels, attack and cast speed, hp regen, wisdom), coffees (critical rate and damage), auras (critical aura, fierce aura, speed aura). Equipment is not recorded as a list: teammates' gear is out of the recorder's scope (the existing exporter covers gear). The gear share of a stat is therefore only a cross-check, not a gap: the `combatStats` value minus the recorded buff entries minus the level-derived base should equal the gear's contribution, and a residual that does not match the exported gear flags a missing buff or a wrong formula.

**Buff timeline (instead of a list of missing buff inputs).** Every buff has a source and a duration, so the recorder keeps a timeline per unit and each damage window uses the buffs live at that time:

1. **Party buffs**: at each `new_battle`, per `combatBuffMap` entry, the `uniqueHrid` (the source family), `typeHrid`, boosts, `startTime` and `duration`; expiry = `startTime` + `duration`; a permanent buff has the zero date. A temporary buff that is refreshed gets a new `startTime` under the same `uniqueHrid` (seen in the capture), which the engine does by replacing the entry (`combatUnit.js:395-408`, buffs keyed by `uniqueHrid`): a changed `startTime` is a refresh, a missing key is an expiry. The instant of expiry is computed (start + duration; the engine expiry handling was not read for this note); the snapshot only fixes that it happened by the next encounter (about 20 s).
2. **Enemy debuffs and buffs from abilities** (Toxic Pollen, speed aura, frenzy, berserk): an entry is created at the executed cast (the message where the caster's `atkCounter` rose, ability = the previous prepared `abilityHrid`), with the effect values from the ability data at the caster's ability level (`combatAbilities[].level`), the duration from the data, ending at cast time + duration. Stacking rule from the engine: a buff with the same `uniqueHrid` on the same unit replaces the earlier one and restarts its clock (`combatUnit.js:395-408`), so two casters of the same ability do not stack; buffs with different `uniqueHrid` (the four Toxic Pollen entries) are independent. The window of a monster's debuff ends when the monster dies.
3. **Marked heuristic or unverified**: the exact moment an ability's buff starts (at the executing message or when the cast resolves: within one message and one cast time); whether the game's ability level scaling matches the data's per-level amounts (check by the closed-form step); a buff whose source or duration the messages do not give (none seen so far: every party entry had `uniqueHrid`, `startTime` and `duration`; monsters carried no buff entries in the capture, so their own buffs, if any, would come only from `new_battle` at spawn).

**Still really missing** (from the earlier list):

1. A `weakened` accuracy reduction (`combatUtilities.js:148-150`): the engine reads `isWeakened` and `weakenPercentage` but sets them nowhere in `src/`, and the game data has no ability, monster or buff that applies it (the word appears only in a combat-trigger condition and an item text). The same tracking would cover it only once its source is known; until then it is not recorded, and a lower recorded hit rate than predicted is the only trace.
2. The per-hit random roll (`randomInt`, `:176`): not carried and not needed; the damage of each event is exact (the HP change).
3. Mid-encounter changes of stats that are not buffs (an equipment swap, a level-up): the buff timeline covers buff changes; a swap or level-up is seen at the next `new_battle` as a change in `combatStats` or the levels (resolution one encounter, about 20 s) and splits the window; it is rare.
4. The instant at which a buff the party did not cast itself (a teammate's drink, a guild or community buff) changes between two snapshots: seen at the next snapshot, with the computed expiry for temporary ones.

**The recorder keeps raw inputs, not shares.** Per window it stores the full `combatStats`, `combatDetails` and `combatBuffMap` entries at window start and a diff per encounter, the abilities with levels, the monster stats per hrid, and per encounter the executed-ability counts per player and the cast times of every ability that applies an enemy debuff or a buff; so a share can be recomputed later when a formula is corrected. The shipped export carries inputs and recorded damage; the shares are computed from them by a closed-form function that is separate from the simulator.

### Closed-form check against the recording (proposed)

For each player and ability in a window, the function predicts the mean damage per event from the recorded inputs and the equation above, and compares it with the recorded mean damage per hit event (damage dealt divided by hit events, from exact `cHP` drops and `dmgCounter`). A window-level mismatch beyond a tolerance (placeholder: 5 percent of the mean after at least 30 hit events, with the monster's armor and resistance at spawn) sets a flag `formulaMismatch` on that player, ability and monster, with the inputs, so the term that is missing or wrong can be found. The simulator stays a validation tool for these formulas, not part of the shipped export. Hit and crit rates are checked the same way: predicted hit chance (`:152-154`) against hit events over all events, predicted crit chance against `critCounter` changes.

### Active tasks

A task only raises damage while it targets the monster being hit; the recorder therefore needs the full list, not a flag.

- **Where it lives.** Not in `new_battle`, `battle_updated` or `action_completed` (the monster and player records carry no task or quest key; the stat `taskDamage` is the bonus, not the state). It is the game's **character quests**: `init_character_data.characterQuests` (an array) at login, and `quests_updated.endCharacterQuests` whenever a task changes (Toolasha reads both, `toolasha-ui.js:8136-8144,10136,10190`). Each entry has `id`, `category` (`/quest_category/random_task` for the repeatable tasks), `status` (`/quest_status/in_progress` while active), `monsterHrid` (combat tasks) or `actionHrid`, `goalCount`, `currentCount`, `coinRerollCount`, `cowbellRerollCount`. The reward fields were not found in the sources available here; the sim does not need the reward.
- **Recorded.** The list of in-progress tasks with `monsterHrid`, `goalCount` and `currentCount`, as a timeline: a snapshot at window start and one entry per change of the set or of a `currentCount`; per encounter, which monsters had an active task, with the damage dealt and kills per monster (already in the encounter row), so task damage is the damage to those monsters. A kill that advances `currentCount` is seen in `quests_updated`. Task state belongs to the account, so it is one list per recorder, not per slot; whose task it is (the party shares monsters, tasks are per character) is the part to check: in a party only the capturing player's task list is in his browser, so other members' tasks are unknown.
- **Exact or heuristic.** Exact for the capturing player when the recorder saw `init_character_data` or `quests_updated`. Not carried for other party members.
- **When the recorder is installed after login.** The userscript runs at `document-start` and keeps the latest `init_character_data` in memory (`mwics-exporter.user.js:191-193`); an update installed mid-session needs one page reload so the hook sees the login messages. Without a reload the list is unknown until the next `quests_updated`; the recorder marks the task list `unknown` and the task bonus as not computed, and does not guess it from `taskDamage`.

### Simplest install (proposed, not built)

For a player who already has the exporter: (1) update the userscript in the manager (one update, the same script, no second install); (2) reload the game tab once, so the page hook sees the login messages (task list, own character id); (3) fight; the recorder starts by itself; (4) press **Copy loot export** in the manager's menu and paste it where asked. No console, no pasted code. What the recorder needs from the host page hook: the existing `MessageEvent.prototype.data` hook (`mwics-exporter.user.js:191`) and the type list extended with `new_battle`, `battle_updated`, `action_completed`, `quests_updated`; the rest is inside the exporter. The console snippet stays only for the first, throwaway captures.

### Ambiguous ticks: recorded raw, split afterwards

A damage event whose actor cannot be named by the rules (two or more monster actors for damage taken, two or more player actors for damage dealt, or an unmatched damage-over-time tick) is not dropped and not split by the recorder. It is stored as a raw record, and a separate post-processing step splits it by likelihood. In the capture there were none (see counts above), so this step is specified, not tested.

1. **Record fields (per ambiguous tick)**, in the encounter row's `ambiguous[]`: `battleId`, arrival time, the target (slot or monster index), the `dmgCounter` delta, the HP change (the exact damage, or 0 for a miss), whether `critCounter` now equals `dmgCounter` (crit flag, last event only if the delta is 2 or more), and for each candidate actor: slot or monster index, its hrid, the ability it executed (previous prepared `abilityHrid`, else auto), and the `atkCounter` delta. Several targets in one message are one tick with several target entries (an area ability hits all targets; each target's damage is its own exact amount).
2. **The split is post-processing**, run on the recorded data (in the export reader or a separate tool, not in the recorder). For each candidate set it computes, from the recorded inputs (`combatDetails` and `combatStats` of the candidates, the executed abilities with levels, the target's armor and resistances), the damage distribution of each candidate: the normal hit range (`sourceMinDamage` to `sourceMaxDamage`, `combatUtilities.js:162-176`, after mitigation `:191-202`) and the crit possibility as a separate case (maximum damage x (1 + critical damage), `:170-174`, weighted by the crit chance `:156-160`), times the hit chance (`:152-154`) for the miss case. The likelihood of "candidate A did this damage and B missed" against "B did it and A missed" etc. gives a probability per assignment; the tick's damage is credited fractionally, and the record keeps the probabilities, not a single winner. Because each monster's stats are exact in `new_battle`, the distributions are formulas, not fitted; over many ticks the mean of the credited damage per monster and ability is compared with the formula's mean, which is the same check as "Closed-form check" and flags a wrong term.
3. **What the recorder must keep so the split can be re-run**: the raw ambiguous ticks as above; per window the full `combatDetails` and `combatStats` per monster hrid and per player (not only their summary), the `combatBuffMap` at window start and its diffs, the executed-ability counts per candidate; the Toxic-Pollen-style debuff casts with times, since they change armor at the moment of a tick; and the unambiguous ticks (their exact damage per monster and ability is the sample the distributions are checked against). The record is raw inputs plus exact outcomes; probabilities are never stored as the only result, so a corrected formula re-splits the same ticks.
4. **Marked heuristic**: the split is a statistical estimate (marked `attribution: "likelihood"` in any share it feeds); the unambiguous ticks stay `attribution: "counter"`.

### Per-hit log (userscript 0.7.3)

Per encounter row, next to the unchanged totals: `hits: { src: [ability, ...], n, data, dropped? }`. Every dealt damage event the recorder attributes (`damageEvent`, side `m`) is appended; ambiguous ticks are not (they stay in `ambiguous[]`), and damage taken is not logged per hit yet. Each event is `delta ms since the previous event (the first from the encounter start), dealer slot, source index (into `src`), target monster index (into `monsters`), amount (the HP drop)`, all unsigned varints (7 bits per byte), then one flags byte (1 = hit, 2 = crit; a crit on a miss is 2, a plain miss 0). The bytes are base64 in `data`. `unpackHits(h, startedAt)` returns `{ t, slot, source, monster, amount, hit, crit }` per event; `filterHits` cuts to some slots (the self-only export and the helper sink use it, so another player's hits never leave in a self-only file). Caps: `REC.MAX_HITS` (20000) events per encounter, the rest counted in `dropped`; the encounter ring cap (`REC.MAX_ENCOUNTERS`) is unchanged, so the strings are bounded by it. While an encounter is open the bytes sit in a plain number array (one push per field per event, no string building); the base64 string is made once at close.

Size, estimated from the counts in a real recording (7866 encounters, 81071 dealt events, 22.4 h of fighting over a 39.6 h span; per-event times spread evenly and amounts at each source's mean, with the amount halved and doubled giving the same total): about 1.5 MB for the whole recording, 19 bytes per event including the source table and keys, about 67 KB per hour of fighting (38 KB per wall-clock hour). The largest encounter row's `hits` was 841 bytes. The existing recording file grows about 1.6 MB per wall-clock hour, so the log adds under 5 percent.

### Size and storage budget (proposed; the storage limit was not measured)

| Item | Estimate | Basis |
| --- | --- | --- |
| Encounter row, 3 players, all counters | about 1.2 KB | a reduced version (casts, mana, healing, kills, no per-source damage) measured 0.7 KB per encounter in the capture; per-source tables are the estimate |
| Ring of encounter rows | 800 rows (`REC.MAX_ENCOUNTERS`); measured about 5.6 KB a row on a replay, so about 4.5 MB, about 4 hours at about 200 encounters an hour; slimming rows is a later item | set by the owner's session for the first test |
| Window | about 20 KB (3 players x ~4 KB, enemy stats ~1.5 KB per monster hrid) | estimate |
| Windows | 200 windows = about 4 MB | proposed cap; a stable farm makes very few windows |
| Total | about 6 MB | |

Persistence (proposed): each closed window and the ring in separate keys, the open window written every 20 encounters and on page hide, so a write is never a multi-megabyte rewrite on every message. Whether the userscript manager's storage (`GM_setValue`) holds this much, or whether the exporter should use its own IndexedDB on the game's origin instead, is not checked (open question). The "Clear recorded loot" command deletes all of it. When a cap is hit, the oldest encounter row or window is dropped, never the open one.

Work per message is small: a battle_updated of a few hundred bytes is parsed once and a few counters are updated; a `new_battle` of tens of KB is parsed once per ~20 s.

| Extra source | What it adds that the recorder cannot get alone | Why it is not needed |
| --- | --- | --- |
| Toolasha's IndexedDB `lootLogHistory` (up to 5000 loot log entries) | combat sessions from before the exporter was installed | going forward the recorder has the same drops per window, with kills and modifiers, which the loot log lacks |

## Writing to disk (userscript 0.3.0)

Design decisions (session-settled): the recorder appends what it records to a file through a small local helper, so nothing has to be copied by hand; players without a helper save the recording as a file from the menu. The wire is fixed on the helper side; the userscript side is `createSink` in `userscript/mwics-exporter.user.js` (tests `recorder.test.cjs`, `recorder-hook.test.cjs`).

- **Where it sends.** Only to a helper on `127.0.0.1` or `localhost` (the `@connect` list and a check on the address menu entry), `POST <helper>/v1/combat`, header `X-MWI-Token`. Default address `http://127.0.0.1:47631`, changeable from the menu. Nothing is sent without a token. From 0.9.0 the script fetches the token itself (`GET <helper>/token`, see `docs/codebase/guild-chat.md`, "`GET /token`") and keeps it in the manager's storage; the menu entry **Set helper token** stays as a manual override and a pasted token is never replaced. The guild chat export is a separate script and still takes a pasted token. The setting **Send to the helper** (Settings) is on by default and has no effect until a token is set.
- **Body.** `{"v":1,"records":[{"key","type","data"}, ...]}`, at most 64 records and about 900 KB per request (the helper allows 1 MiB). `type` is `encounter`, `window` or `task`; `data` is the row exactly as the recording holds it (the party by slot, no names, no ids). A batch the helper refuses with 413 or 400 is halved; a single record refused is dropped from the queue and stays in the in-browser record. Anything else (helper down, wrong token) keeps the queue and retries after 2 s, doubling to 60 s; the first failure shows one toast.
- **Keys** (unique per record, under 200 characters): `enc:<start time>:<battle id>`; `win:<start time>#<battles>.<buffer events>` with `.c` appended once the window has closed, so a window is sent again as a new revision when it changed; `task:<time>`. The keys sent are remembered (last 5000, in the manager's storage), so a reload does not resend; the helper also drops a key it already holds.
- **One request path, with a watchdog (0.9.4).** The combat POST and the token GET both go through `helperCall`, the one `GM_xmlhttpRequest` call, wrapped in `guardRequest`: with no callback after `REQUEST_WATCHDOG_MS` = 30 s the request counts as failed (status 0), the sink's normal retry takes over, and a late callback is ignored. Before, a request the script manager lost left the sink `flushing` forever, so nothing more was sent until a reload.
- **When.** An encounter is sent once four later ones have closed (a food heal can credit a consume record up to four encounters late; sending earlier would store a row that is later corrected), or after 90 s without activity, or when the page is hidden or closed. A window is sent when it opens, again at most every 10 minutes while it changes, and once more when it closes. A task list is sent when it changes. With `selfOnly` on, the same filter as the recording applies, and nothing is sent until the player's own slot is known.
- **Menu names.** **Copy character export (player, gear, inventory)** (was **Copy export**), **Copy combat recording (clipboard)** (was **Copy loot export**), **Save combat recording (file)** (new: the same content as a downloaded `.json` file through a blob link, no clipboard), **Clear recorded combat data** (was **Clear recorded loot**; it does not delete what the helper already wrote), **Set helper token**, **Set helper address**, **Status** (version, counts written, held, rejected, queued, failed), **Settings** (the title shows the version).
- **Not verified here.** Behaviour against the real helper (the tests use a mocked request function); the manager's storage limit for the sent-keys list; many hours of continuous sending.

## Several game tabs (userscript, unreleased)

The script runs in every game tab and all tabs share one script storage (`mwicsRecorderEncounters`, `mwicsRecorderWindows`, `mwicsSinkSent`, `mwicsGroupState`, `mwicsGroupSnapshot`, the toggles and the helper token). Each tab keeps its own recording in memory; the menu entries (copy, save, counts in Settings) read only that tab's memory.

- **Saving the recording** (`saveRecorded`: every 20 closed encounters, page hidden, page closing) reads the shared copy first and merges (`mergeRecorded`): encounters by their sink key (`enc:<start>:<battle id>`), windows by their start time (the copy with more battles, then more buffer events, then the later end wins, a tie keeps the saving tab's), task lists by their time; each list is cut to its cap keeping the newest, in time order. The counters in `stats` add what the saving tab counted since it last loaded or saved (`recBase`), so a counter is never counted twice. **Clear recorded combat data** replaces the shared copy with the empty one; a tab that still holds rows writes them back at its next save.
- **Sent keys** (`saveSent`) are the union of the stored list and the tab's (`mergeSent`, newest 5000). Before each batch the sink reads the stored list (`adoptSent`) and drops from its queue what another tab has sent. A request already in flight in another tab is not seen: two tabs can still send the same row once, and the helper holds one copy by key.
- **Party state** (`saveGroup`, `mwicsGroupState`): the shared profiles are merged with the stored ones (`mergeProfiles`): one per player (same id, or same name), the newest by the profile's own `t` first, the newest 20 kept; the tab's own list in memory is not changed. The party members are not merged: the last tab to save writes its own.
- **Party snapshot, one per character** (`publishSnapshot`, `saveCharSnapshot`): each game tab still writes the single key `mwicsGroupSnapshot` (the latest save of any character, as before, so a page or script not yet updated keeps working), and also its own character's copy of the same text under `mwicsGroupSnapshot.<character id>` plus an index `mwicsGroupSnapshotIndex` (`[{ id, name, t }]`, newest first, one entry per character, merged by `mergeSnapIndex` so tabs do not overwrite each other's entries; the newest 10 characters stay, an older one's key is blanked). The simulator page's button (`addSimButton`, `refreshPicker`, `importPartyFromGame`, in the same script: it runs on the simulator page, no change in `src/`) shows a drop-down (`#mwicsPartyPicker`, class `form-select`, under the button) only when the index has two or more characters: each option is the name and `saved <time of the last save in the viewer's clock>`, the most recent selected; the import reads the picked character's key. With none or one it shows nothing and imports the single key. The same 30-minute age limit applies to the picked snapshot. Tests: `userscript/test/picker.test.cjs`.
- **Labyrinth zone** (`onAction`): `/actions/labyrinth/*` actions are noted as the zone like `/actions/combat/*`, so a labyrinth fight's window has a labyrinth zone (it carried the previous combat zone before).
- Tests: `userscript/test/tabs.test.cjs` (several script instances over one fake storage).

## Players to tick, zone and tier in the group snapshot (userscript 0.8.0)

The snapshot in storage (`mwicsGroupSnapshot`) is `{ t, group, slots, selected?, fight? }`. `selected` is the slot numbers in `group` (a member with no data has no slot, so it cannot be ticked). `fight` is `{ zone, tier, kind, status, source, t }`: `kind` is `combat`, `dungeon` (client data category `/action_categories/combat/dungeons`), `labyrinth` or `idle`; `source` is `party` (a `battling` party's `actionHrid` and `difficultyTier`) or `action` (the first of `characterActions`). Idle and the Labyrinth have no zone or tier. Both keys sit beside `group`, never inside it (the page's group import treats every key of the object as a slot).

Where it comes from: `init_character_data` (`characterActions`, `partyInfo`), then kept live from `actions_updated`, `action_completed` and `party_updated`. Field names for the last two and for `init_character_data` come from the game's client code and are not backed by a captured sample.

"Copy group export" copies the same: the slots plus `selected` and (when known) `fight` as top-level keys beside them (`groupWithSelection`), so the page's paste takes the copy back. The original simulator ignores the extra keys; an older build of our page would create two players named `selected` and `fight`.

The userscript's import button ticks and sets after the page's import (`applySelectionDom`, order: dungeon toggle, ticks, zone, tier). The page's own group paste does the same when the pasted object carries `selected` and `fight` (`src/groupSelection.mjs`, called from `doGroupImport`); without them it imports as before.

## Open questions, with recommendations

Design decisions already settled, not reopened: the exporter records combat itself; it records everything the combat messages allow, damage and accuracy included; it is self-sufficient and the other extensions are optional; the export is the whole party by slot with no names or ids, and a `selfOnly` setting limits it to the player; read-only, nothing sent; capped record in the browser with a clear command; the game's loot log is an extra.

1. **Ship the stateless "Copy combat session" button first, then the recorder?** Recommend yes: the button needs two message types and no storage, and gives each member's multi-day sample at once; the recorder is the full answer. The settled decisions do not say which comes first.
2. **Default of `selfOnly`.** Recommend off (whole party), as he picked it, with the switch visible in Settings. Not asked: whether the first export shows a one-time notice that the file holds the other members' data.
3. **Where the record is stored.** `GM_setValue` is the manager's storage and its limit was not checked; the exporter's own IndexedDB on the game's origin holds more but is cleared with the site's data. Recommend measuring the manager's limit first and using separate keys; fall back to IndexedDB if it is below about 8 MB.
4. **Caps: 200 windows, 2000 encounter rows, about 6 MB in total.** Estimates, not measured on a long run. Recommend adopting them and printing the real size in the Settings dialog, so they can be tuned.
5. **Window key** (zone, tier, `combatStartTime`, party size, each player's three drop modifiers and levels; never the buff map) and the **60 s gap**. A design consequence of the capture for the buff map; the rest are placeholders. Recommend adopting them.
6. **Attribution depth.** Settled by the capture rather than a choice: the rules above credit every tick in it, so v1 needs no MWITools-style remembered casts beyond the damage-over-time rule. Reflect, retaliation, life steal and drain are in the engine but untested (no case in the capture). Recommend building rules 1-4 and flagging any tick they cannot name as `ambiguous` (raw, split afterwards).
7. **Hit, miss and crit counts.** Decoded (see the table), exact. Open only whether a longer capture contradicts the reading on a unit that is stunned, blinded or dead (none in the capture). Recommend building them as decoded.
8. **A second, longer capture** (30+ minutes, loot log opened, one zone change, one stop and restart, ideally a death). Recommend yes, run in parallel with the build: it settles what resets the session, the loot log shape, death handling and the counters, none of which blocks the core.
9. **Optional imports** (Toolasha IndexedDB, loot log, MWITools history). Recommend leaving all out of the first build and adding only the loot log import after a capture shows it; the recorder does not need any.
10. **Dungeons and waves.** Recommend out of v1 (no data), as before.
11. **Share convention for damage bonuses (not decided; proposed by the owner).** Damage is mostly a product of factors, so each multiplicative factor's share could be ln(factor) / ln(total), which is order-independent, with additive bonuses inside one factor split in proportion to their size. My view: it is the right convention for the multiplicative terms (amplify, `taskDamage`, `damageTaken`, `autoAttackDamage` / `abilityDamage`, crit, the mitigation ratio 100/(100+R), hit chance on the expected value), because it does not depend on the order in which bonuses are "removed". Two caveats: shares depend on the baseline chosen as "no bonus" (a factor of 1, and for armor a target armor of 0 versus the base armor), and a debuff or a factor below 1 gives a negative share, so the report should say so. Closed form needs no simulator runs. Recommend adopting it for the multiplicative chain, and stating the baseline in the export.
12. **Active tasks for party members.** Only the capturing player's task list is in his browser. Recommend recording it as exact for him, `unknown` for the others, and leaving other members' task damage out of the closed-form check until their lists are known (each member can export their own).
13. **Heals hidden by an `atkCounter` delta of 2.** Recommend recording them as `ambiguous` (possible heal ability of that player) and checking with a longer capture how often it happens and whether the second action can be recovered from the next record.

## Test server beside the live one, talismans and the trace (userscript 0.10.1)

- **Server.** The script runs on `www.milkywayidle.com` and `test.milkywayidle.com`; `serverOf(location.hostname)` is `test` on the second and `live` everywhere else (the simulator page counts as live). Every encounter, window and task row carries `server`, and so does the export. The test server keeps its recording (`mwicsRecorderEncounters.test`, `mwicsRecorderWindows.test`), sent keys (`mwicsSinkSent.test`), party state (`mwicsGroupState.test`) and group snapshots (`mwicsGroupSnapshot.test`, `.test.<character id>`, `mwicsGroupSnapshotIndex.test`) under keys with a `.test` suffix; the live keys are unchanged, so a live tab and a test tab share a script storage without mixing. The toggles, the helper address and the token are shared. The simulator page's import button reads the live keys only (a test-server party is not offered).
- **To the helper.** The body is `{"v":1,"server":"live"|"test","records":[...]}` (the field `server` is new; a helper that ignores it still works). A test-server record key carries the prefix `test:` (`test:enc:<start>:<battle id>`, `test:win:...`, `test:task:...`), so a test row never matches a live row with the same start time and battle id. Each row's `data.server` says the same. A helper that keeps test rows in their own file routes on `server` (or on the key prefix).
- **Talismans.** The recorder keeps the self character's talismans from `init_character_data` (`characterTalismans`, the belt item in `characterItems` whose location ends in `/belt`, `combatUnit.combatDetails.combatStats.talismanPower` and `talismanSlots`), `talismans_updated` (`endCharacterTalismans` replace by id, `deletedTalismanIds` remove) and `character_stats_updated` (the same two stats). These messages do not move the encounter gap clock. At each `new_battle` every player gets `talisman`: `{ power, slots }` from the unit's own combat stats (null when the unit shows none) and, for the self player, `belt` and `talismans`: the talismans with `slotIndex` above 0 in slot order (an empty or null `talismans` means the recorder had no talisman data for that encounter, such as a tab opened before `init_character_data` was seen; it does not mean no talisman is equipped), each `{ id, type, slotIndex, locked, lines: [{ hrid, grade, value, locked, unique }] }`. `value` is the client data's `talismanModifierDetailMap[hrid].gradeValues[grade - 1]` and `unique` is its group being `/talisman_modifier_groups/special` (null when the client data is not there). A roll waiting to be accepted (`pendingModifiers`) is not part of the talisman and is left out. Not available from any message read: the modifier lines of the other party members (a shared profile was never captured for this), the belt after a mid-session change (read from the character data only), and whether `slotIndex` 0 means "not slotted" beyond what the slot and unslot messages show.
- **Trace.** On the test server (or `createRecorder({ trace: true })`) each encounter also carries `trace: { fields, src, rows, dropped? }`: one raw row per unit that changed in a `battle_updated`, columns `TRACE_FIELDS` (update number, ms from the encounter start, side, unit index, attack-attempt change, damage-splat change, HP lost, HP gained, crit-splat changed, ability index into `src`, then `atk`, `dmg` and `critN`, the unit's own fields as the game sends them, not running counts of the recorder's: `atk` its attack-attempt field, `dmg` its damage-splat field, which can go down, and `critN` the splat index of the unit's last crit splat (`criticalDamageSplatCounter`: it changes only on a crit, to that splat's index; it counts nothing)). At most `REC.MAX_TRACE` rows per encounter; the rest are counted in `dropped`. Nothing in it is an attribution or a proc; `tools/echo-analysis.mjs` reads it (below).
- Tests: `userscript/test/talisman.test.cjs`.
