# The What-if window

The page's What-if window runs the what-if optimizer (`tools/whatif/optimize.mjs`) through the local what-if runner: a program on the user's own PC that serves this page and runs the search at low priority on every core. The public website has no runner, so there the same button opens the window in its "get the runner" state (below).

## Two states

`initWhatIf` (`src/main.js`) asks `/api/version`. When no runner answers, `whatIfShowGetRunner` shows the button and puts `whatif-norunner` on `#whatIfModal`; the CSS in `index.html` then shows only `#whatIfGetRunner` (one paragraph on why, the download link, four steps: start, SmartScreen, the black window, the What-if button) and hides the search; with a runner the class is absent and that pane is hidden. The link target is `RUNNER_DOWNLOAD_URL` (`src/whatif/runnerDownload.mjs`), the one constant. Strings: `common:whatIf.get.*` in en, pt and zh (pt and zh not checked by a native speaker; the pt SmartScreen names are Microsoft's own). The zip itself: `runner-zip.md`. Test: `tools/test/whatif-get-runner-page.mjs`.

## Files

1. `src/whatif/panel.mjs`: the window's logic, without the DOM, tested in Node: the request body, the progress line, the result tables, which slots an Apply writes, and where the page's setup differs from the search's. It computes no figure: every number shown is a field of the result or of the progress, rendered with `numberHtml` (`src/numberFormat.js`), so the raw value rides along.
2. `src/whatif/applyOps.mjs`: the ops that edit a setup (enhance, equip, food, drink, ability, abilityLevel, abilityOrder, unequip, level, house, trigger). Shared: `tools/whatif/variants.mjs` re-exports it for the Node tools.
3. `src/main.js`, region "What-if window": the DOM side. `initWhatIf` asks `/api/version`; only when it answers is the button shown and the window wired. `whatIfSlots` saves the current tab first (`savePreviousPlayer`), then reads one slot per real player tab (`#playerTab .nav-link`, so a three-tab page gives three) with their names (`whatIfPlayerNames`: the character name the slot's import carried, else the tab's text; the rule is `shownNames` in `src/slotNames.mjs`). Every import path (Solo, All players, the per-player boxes) ends in `applySlotNames` (`src/main.js`), which writes a slot's unique name onto its tab once per name (a tab the player edited stays until the slot's name changes) and refreshes the Select Players labels; a name two slots share, or none, leaves the tab's text. Tests: `tools/test/slot-names.mjs`, `tools/test/slot-names-page.mjs`. With `onlySelected` it reads the window's own tick boxes, never the page's.
   The window has its own choices (`whatIfRenderChoices`): a tick box per player tab (`#whatIfPlayers`), a zone selector (`#selectWhatIfZone`) and a tier selector (`#selectWhatIfTier`). Each time the window opens (`show.bs.modal`) they are copied from the page: the players ticked on the page (none ticked on the page means none ticked here, the "tick at least one player" message shows, and the user ticks players in the window), and the page's zone and tier. The two selectors are built from the page's `#selectZone` and `#selectDifficulty` options (same values, order and names; an option keeps the page's `data-i18n` key, so the page's own language switch renames it). Edits in the window never write to the page. The budget rows, the message (shown whenever no player is ticked in the window, cleared when one is) and the request (`slots`, `options.zone`, `options.tier`) follow the window's controls. A language change redraws the names and keeps the window's picks. Apply and the "where the page differs" warning still read the page (`whatIfSlots(false)`).
   Layout: the left column (`.whatif-col`, 5/12) and the modal body are flex columns with one gap (`--whatif-gap`, 12 px) between every section (Goal, Players, Zone/Tier/note, Budgets, the button row, progress, result); Goal sits inline with its label like Zone and Tier (3/9). Each ticked player is one 31 px row (`.whatif-prow`, a grid of equal columns): name | budget | one-row paste field | status (one line, ellipsis, the whole text as its title). Five players and the Start search row fit at 1500x900 and 1100x900, the two columns' bottoms within 120 px; the page test measures it.
   Character export per player: in each ticked player's budget row, a one-row paste field (`textarea.whatif-export`, no resize) and a status beside it. A paste is validated by `parseExport` (`panel.mjs`): a JSON object with an `inventory` or `learnedAbilities` array (the userscript's "Copy character export"). A valid one is stored in `localStorage` under `whatIfExport:<player name>` (`exportKey`), replaces any kept one, and empties the box; it is kept across window opens and page reloads, and there is no clear control. A bad paste is not kept (it stays in the box and the status says so; an earlier kept export stays). A party import from userscript 0.9.3 or later also ends in this storage, for the own player only: its slot's `inventory` and `learnedAbilities` are taken out of the slot (the sim slot is as an import without them gives) and kept under the name the window shows that player by, through the same keeping function (`whatIfKeepExport`), so the row reads as after a paste; an import without those fields keeps nothing and clears nothing. The other players still need their own pasted export. The status (`exportStatus`): "kept (<the export's own name>)", "no export: skipped by <lever names>" (the ticked ones among Items you own, Abilities and New abilities; Ability levels never skip) or just "no export" when none of them is ticked, or "not a character export: not kept". The request carries `export: { "<player name>": <export> }` for every ticked player with a kept export, and no `export` when none. The storage and the box values are the data: nothing is read back from displayed text. Apply writes the new slot JSON into `playerDataMap` and reloads the screen (`updateNextPlayer`, `updateState`, `updateUI`), as an import does.
4. `index.html`: the button (hidden by default, beside Import/Export), the `whatIfModal` window and its styles (in Dark Mode the progress bar has a dark track with a border and a blue fill, so an empty bar reads as empty).
5. Strings: `common:whatIf.*` in `locales/en`, `pt` and `zh`.

## The runner's interface (JSON over HTTP, same address as the page)

1. `GET /api/version`: `{ runner, engine }`.
2. `POST /api/search`: `{ setups, options: { zone, tier, marketplace }, goal: "profit" | "exp", budgets: { "<player>": coin }, levers: [...], players }` answers `{ id }`. `levers` is the ticked lever ids, as the window lists them (`LEVERS` in `panel.mjs`: equip, foods, drinks, owned, abilities, order, triggers, houses; Foods and Drinks are two boxes, each ticked by default, each with its own name and description in en, pt and zh; the pt and zh strings of the two are not checked by a native speaker). An old request that says `consumables` is read as both by the optimizer. `marketplace` is the game's `marketplace.json` body, fetched when Start is pressed by `fetchMarketplace` (`src/marketplace.mjs`, shared with the page's Get Prices button; `searchRequest` in `panel.mjs`); when the fetch fails the window says so and starts no search (no older snapshot is used in its place); a second search while one runs is refused with the running `id`, and the window then follows that one.
3. `GET /api/search/<id>?since=<n>`: `{ state: "running" | "stopped" | "done" | "error", progress: { stage, candidatesLeft, runsDone, runsPlanned, secondsPerRun, etaSeconds }, error?, result?, partial?, partialVersion?, round?, roundVersion? }`. The window polls it every second while it runs, with `since` = the highest `partialVersion` or `roundVersion` it has drawn (`whatIf.partialVersion`, 0 for a new watch; one counter serves both); a running search carries `partial` (the report so far, the same shape as `result`) and `round` (the latest search-round record) each only when newer.
4. `POST /api/search/<id>/stop`: stops a running search; the same request on a stopped one resumes it.
5. `GET /api/results` (newest first, `{ id, finished, goal, players }`) and `GET /api/results/<id>` (one result).
6. `POST /api/search/<id>/done` with body `{ mode: 'accept' | 'skip' }` (`400` for any other): the two stage buttons, "Accept current winner" and "Skip this stage" (no stage name in the button). The runner sends `{ done: mode }` over the IPC (beside `stop`), `optimize.mjs` sets `stop.done` to the mode; the core's `race()` clears it at its start. **Accept** locks, in each pool without a lock (a player's, or the stage's single one), the best live leader whose figure the window shows as a figure (`acceptTakes` in `rounds.mjs`, fed by `gainOf`, which reads `showsFigure` from `src/whatif/figure.mjs`, the one helper the window shares: at least 4 reading seeds and a range that does not reach 0, so not "≈ 0"; a mean above 0, never a time-only lever, never a candidate the elimination rule put out), and ends the stage after the round in flight (after that round's record is published) through the one end path. The pick is taken as it is: **no pick check** (no `confirmPick`, no fresh seeds) and it enters the baseline directly (a greedy step, or a foods/drinks filling); the report marks it `acceptedAsIs: true` (the steps row, `result.best[kind][player]`) and shows "accepted as is" beside it (en/pt/zh); it is never in `notConfirmed`. A pool that had already locked keeps its pick, checked as usual. `result.endedByUser[stage] = round` (the rounds the stage finished: the report says "ended by you after round N"). **Skip** ends the stage at once: in `ensure()` (`core.mjs`) the lanes take no new runs (`skippable`; the runs already going finish and are stored, no `pool.kill()`), the race returns the earlier round's leaders (none in round 1) with no new lock, keeps the locks it already had, and the search carries on to the next stage (`result.incomplete` and `result.stoppedBy` stay unset); `endedByUser[stage]` is the number of rounds the stage finished, **0 when Skip came before the first round finished** (any reader of `endedByUser` tests `!== undefined`, not truthiness). `result.endedBySkip[stage] = true` marks a Skip (absent for an Accept): the report and the Best heading say "ended by you during round N, its finished runs kept" with N = `endedByUser` + 1 (so 1 for a Skip pressed in round 1; `endedText` in `panel.mjs`, `endedMd` in `core.mjs`, string `result.endedByUserDuring`), an Accept says "ended by you after round N". The ended stage's own line says "round N · ended by you" instead of "round N finished" (`progress.stageSkipped` from `endStage` → the row's `skipped` in `progress.mjs` → `rounds.roundSkipped`). The core publishes how many pools Accept would take each round (`progress.stageAcceptable`, the part's `acceptable`), and the window draws "Accept current winner" only while that is above 0 (so "no change leads", or a figure not yet shown, gives Skip alone); the buttons are drawn only on the race stage running now (`data-whatif-done="accept"` / `"skip"`, `data-whatif-part=<kind>:<index>`, in the stage's own line after its counters). After a press `main.js` keeps `whatIf.pressed` and the window draws both buttons disabled until the stage's row stops running; Accept also shows the note "Finishing the current round" (`data-whatif-note="accept"`; Skip has none, it ends at once). The progress redraw (`whatIfDrawProgress`, `main.js`) reuses an unchanged button node, so a poll does not replace the button under the pointer (no hover flicker). A command-line run has none. `409` when nothing runs.

Status column of the rounds table: one or two words (`clear gain`, `no clear change yet`, `party loses loot`, `still measuring`, `set aside`; `ruled out` is not listed); counts and internal states are the cell's tooltip (`rounds.status.<key>Tip`). Best foods / drinks while the stage runs: a leader without a clear gain (core flag `unclear`, plus `loses`; the entry is the final's `unchanged` form with the leader kept as `candidate`) shows the player's current items greyed, a dash for the figures, and the status with the candidate and its figures as tooltip. Players in every list follow the party's own order (`players`): `poolSorter` in `rounds.mjs` for the pools, `partyEntries` / `inParty` in `core.mjs` for `result.best`, the budgets and the per-player confirmation lines.

## The progress block

`renderProgress` (`panel.mjs`) draws stacked rows from `progress.parts` (`renderParts`; `whatif-runner.md`, "Progress parts"), output only: a title `Running · part K of N` (K = the running row's place from 1, N = the number of rows shown, placeholders included, so it grows as greedy steps are added), one grid row per part (icon cell, bold label, bar, right text), and one small line `Seconds per run <n, two decimals> · elapsed <h:mm:ss>`. The icon cell is one column of equal width for every row, a plain text glyph (`✓` done, `▶` running with the text-form selector, `○` waiting; no colour emoji), so every label starts at the same left edge. Labels: `Re-checking each chosen change` (the row after the first race, `progress.partPicks`, kind `picks`: the runs done of planned of the pick checks, running while a pick is checked, grey with its counts between checks), `Best foods` and `Best drinks` (the first two rows when the search has the foods-and-drinks stages, each with ` · <candidatesLeft> options left`; strings `progress.partFoods` and `progress.partDrinks`), `Change 1` (kind `screen`: the first race picks change 1), `Narrowing down, round <n>` (kind `halving`, no longer built by the search, only an old progress file has it) with ` · <candidatesLeft> options left`, `Choosing changes one at a time: up to <maxSteps>, stops when none helps` (grey, until step 1 starts), `Change <k+1>` (the race of greedy step k, run after change k, looks for change k+1: `stepLabel` in `panel.mjs` adds the 1, once, for the row and for the ended-by-you line), `More changes: up to <stepsLeft> more` (grey; `stepsLeft` = `maxSteps - k - 1`, the changes still choosable after the running row), `Final check: only if a change is chosen` (grey) and `Final check of the whole set` once it runs. The picks part of a search whose every pick the check left out inside a race (the pick check also runs on the leaders' reading seeds, with no run of its own: `progress.picksLeftOut` = `result.notConfirmed.length`, set by `report()`) is done, no bar, and reads "None confirmed (left out: N)." (`progress.picksNoneConfirmed`), never "Not run". Right text: `<done> / <planned> runs · <h:mm:ss> left` (running), `<planned> / <planned> runs · done`, `up to <runsUpTo> runs` (a waiting halving), nothing for the other grey rows. A done row has a green bar, the running row a blue one, a waiting row is grey. A stopped, failed or finished search keeps its rows, but only a running search (`status.state`) has a `Running` title or a running row: the part that was running when the search stopped is drawn halted (`whatif-part-halted`, `■`, grey bar, `round N stopped`, its figures kept, no done button), and a resumed search drops the old report's `Stopped` mark at once (`whatIfShowStatus`). In the rounds tables the pool's title (player, pool, counts, range width, sort order) is the first header cell of its own table, in place of the Change column's header (over the slot columns of a foods or drinks table, the slot names on a second header row). A race stage that has ended (by its lock, the round limit or the Done button; `progress.stageEnded` names it, set in `race()` only on that normal end, not on a stop) is a done row at once, with the last round record's contention counts (`report()` runs after each round record, so the row no longer keeps the first look's), however long the pick checks that follow keep reporting the same stage name (`progress.mjs` `sync`). A race row in any state (running, done, halted) has no bar and is ONE line (`whatif-part-race`, no right-hand text cell): its name, how it stands, then its counts, "✓ Best foods · ended by you · 191 runs · 9,550 simulated hours · 126 still in the running" (`raceLine` in `renderParts`). A count of 0 (`progress.contendingCount`, `pausedCount`, `droppedCount`, `runsCount`, `hoursCount`) is left out, so is "done" (the tick says it; also on the bar rows) and the round of a stage that had one round (a Skip in round 1 reads `progress.endedByYou`, "ended by you"; several rounds read `rounds.roundSkipped` / `roundFinished`); a running stage keeps its round, phase, live counts and its Accept / Skip buttons on that line, which wraps when too long and never scrolls sideways (the window test checks the Done state at 1920 and 1366). A count of 1 reads in the singular through the `<key>One` strings (`plural` in `panel.mjs`; `nOf` in `core.mjs` for the console lines). A progress with no `parts` (an older search) draws the single line as before. Strings `common:whatIf.progress.*` in en, pt and zh (pt and zh not checked by a native speaker). Styles `.whatif-part*` in `index.html`.

## What the window reads from a result

1. Top: `goal`, `budgets` per player, `setups` (the base the search ran on), `confirmation` (`gainPerUser`, `sePerUser`, `cost`, `payback`, and on a profit goal `buyerByPlayer`: `{ gain, se, payback }` per player; shown as the first line "Confirmed on fresh runs: <gain> ± <error> per user per day, Cost <cost>" and one line per player, "<player>: gain <gain> ± <error> per day, pays back in <payback> days", a dash when the payback is none or 0; a result without `buyerByPlayer` shows its party payback and a run-the-search-again line instead), `best` (the foods and drinks the search chose first; drawn above the chosen changes, see item 9), `apart` (unknown cost, listed, never ranked), `overBudget` (priced but above its player's budget: "Priced, over budget", player, change and cost, listed apart in the same style, never ranked), `options.pricesTimestamp` and `options.pricesSource` (one amber warning line, `pricesLine` in `panel.mjs`, only when the prices are a problem: a market snapshot 24 hours old or more when shown says its time and age; the simulator's own saved snapshot always says so; a younger market snapshot has no line).
2. Each row of `steps` and `singles`: `player`, `desc`, `sharedGainPerUser` and `sharedSePerUser` (the party gain per player per day and its error), `buyerNet` and `buyerNetSe` (the gain of the player who pays, per day, and its error), `cost`, `costBound: "upper"` (printed as "≤" on the cost and the payback), `payback` (the buyer's payback; none or a net of 0 or below shows "—", except that a cost of exactly 0 shows "no cost, nothing to pay back", `whatIf.result.noCost`; the same words stand in a player's confirmation line when his `runningSpend` is 0, and in `result.md`), `costPath` and `note` (How it is bought: the path, with the note in brackets and without the "; upper bound (XP inside the level unknown)" caveat, which the footnote under the table keeps), `accepted` (a single that is not is grey and sits behind one "Show N more not accepted" toggle), `ops`; a single also `lastStage`. Both tables (Chosen changes, Each change alone) read: [# and] Player, Change, Shared loot gain per user, ± error, Buyer's gain, ± error, Cost, Payback days, How it is bought, Apply. A result with no `buyerNet` (an older one) shows a dash in both buyer cells, and on an EXP goal they are dashes too. The old Spent, Stage, Shared gain and Own supplies columns, the "spent of budget" line and the helps-the-party table are gone; a row of an older result flagged `helpsParty: true` shows as an ordinary row. The search accepts a change when one of the party gain and the buyer's net is above 0 by at least z errors and the other is not below -(z/2) errors (`acceptBoth`, `whatif-runner.md`); the party gain is the group's shared loot gain per player, before anyone's own food and drink. A gain figure (party or buyer, in both tables, the confirmation line and each player's confirmation line) whose absolute value is less than one error shows the words "no change" (`whatIf.result.noChange`) with the real value as the hover title ("+288K ± 242K"), the error cell next to it shows "—" with the same title; one error or more shows the number. The Change column of Each change alone is 50em wide and wraps (`index.html`), so at 1920x1080 the table has no horizontal bar even for a food change of about 230 characters; the page test measures it at 1920, 1600 and 1366 wide.
3. Game names: the runner writes each `desc` with the game's internal ids (the last part of a hrid, e.g. `pathseeker_boots_refined`, `feet`). The window shows names instead, in the page's current language, in the steps, the singles, the over-budget list and the unknown-cost list (`localizeDesc` in `panel.mjs`; output only, the result keeps the ids and Apply reads the ops). The names are the game bundle's own tables, read as the page's `data-i18n` lookups read them (`i18next.getResourceBundle`, with English as the fallback, `namesFrom`): `itemNames` (a refined item has its own entry with the page's "★"), `abilityNames`, `skillNames`, `equipmentTypeNames` (the slot), `combatTriggerDependencyNames` and `combatTriggerConditionNames`. A trigger desc (`<owner> trigger: <terms>`) reads its terms as dependency and condition (a condition id can equal an ability id with a different name); a house room is written as its English name and is looked up by that name in `houseRoomNames`. The player name leading a desc is never translated; where it is the row's own player (a step or single has a Player column, an over-budget row a "<player>," lead of its own) it is left off the shown desc, so the player shows once; the unknown-cost list has no player column, so its descs keep the lead. An id with no name stays as it is. The language-change handler redraws the result, so the names follow. Not covered: `costPath` and `note` are the runner's text.
   The "where the page differs" warning (`renderDiff`, `diffLabel`, `hridsToNames` in `panel.mjs`) shows names the same way, through the same lookup (`namesFrom`; its tables also hold `houseRoomNames` and `combatTriggerComparatorNames` for it), output only: `diffSetups` and its differences stay raw. The ids a difference holds: in the field, a skill level (`magicLevel`, shown "<skill name> level" from `skillNames` and the `diff.level` string), a slot (`feet`, an `equipmentTypeNames` entry), a house room hrid, and the owner hrid of a `triggers <hrid>` field (an item or an ability); in the values, an item hrid with its enhancement (`/items/x +12`), a food or drink item hrid, an ability hrid with its level, and the hrids inside a trigger's terms, which are shown as JSON (dependency, condition and comparator). An hrid is read by its kind (`/items/`, `/abilities/`, ...) and replaced by its name; one with no name, or of a kind with no table, stays as it is. The words `food 1`, `drink 1`, `ability 1`, `triggers`, `player`, `present`, `absent` and the JSON keys are the code's own words, not ids, and stay.
4. Zone line: under the goal line, "Zone: <name>, tier <N> · base party profit <figure> per user per day" (`zoneLine` in `panel.mjs`): the zone and tier of the request (`options.zone`, `options.tier`; the name is the page's `actionNames` entry in the shown language) and `basePerUser`, the base the search compared against, per user. The base figure shows for a profit goal only. When `basePerUser` is below 0 (the raw field) a line under it says the party loses money at base here, so a gain means losing less. A result with no zone (an older one) shows neither; one with no `basePerUser` shows the zone only.
5. Folds: every detail list is one line (`foldLine` in `panel.mjs`, class `whatif-fold-line`): its bold heading, its small grey note and, at the right end of the same line, its toggle; the closed lists (`closedList`), the count lines (`countList`: the skipped swaps and the export skips) and Each change alone all draw it. Over them all, one "See details" toggle (`result.detailsShow` / `detailsHide`), closed by default, opens `#whatIfDetails`, which holds, each still closed on its own: Each change alone (and its not-shown line), Priced over budget, Pays back too slowly, Left out in the race, Not confirmed, the two swaps-skipped lines, the export-skips line, Unknown cost, and the "≤" footnote. Its `data-whatif-more` lists two ids, `whatIfDetails whatIfRounds`: the click handler (`main.js`) opens or closes every body a toggle lists, the first deciding, so the search rounds (`#whatIfRounds`, drawn under the result) open and close with the details; `whatIfShowResult` hides `#whatIfRounds` while such a toggle is closed and shows it when there is no result yet (no toggle). The toggle is drawn when the details hold anything, the result carries `round`, or the search runs. Outside it, always in view: the warnings, Goal, Zone and base profit, Best foods and drinks, Chosen changes with their Apply buttons, the gain legend, the confirmation and the per-player table. The grey singles and the "Priced, over budget" list each sit closed behind one toggle (`data-whatif-more="<id of the list it opens>"`; open on click, closed on a second click; a redraw, such as a language change, closes them). The over-budget heading keeps its count.
5a. Fresh readings and the picks not confirmed (the pick check, `whatif-runner.md`): a step with a `fresh` reading shows it on a second line inside its gain cells: the party gain cell shows "fresh <gain> ± <error>, <seeds> seeds" from `fresh.gainPerUser`, `sePerUser` and `seeds`, the buyer's gain cell the same from `buyerNet` and `buyerNetSe` (`freshLine` in `panel.mjs`, class `whatif-fresh`: small and muted, no new column, the error cells and the existing columns unchanged; a step without a reading has no second line). A line under the steps table (`result.freshLegend`) says what the second line is. An accepted pick (`acceptedAsIs`) has no fresh reading and is never in `notConfirmed`; its steps-table cell and its Best-table cell carry the small mark `data-accepted-as-is` (`result.acceptedAsIs`). Every list the window draws as a table is drawn by one helper (`listTable` in `panel.mjs`): with no row it is ONE grey line "None." (`result.none`, `data-none`), never a header row over nothing or a label of its own; "Each change alone" with nothing accepted is that line, its grey rows kept behind their toggle in a hidden table of their own (header included); an empty rounds-table pool is the same line, without its title (a run of empty pools is one line). `notConfirmed` (the picks the search left out) is one heading "Not confirmed on fresh seeds" with its count and a Show / Hide toggle; the list sits closed behind it like the over-budget list (`data-whatif-more="whatIfNotConfirmed"`): "<player>, <change>: <at>, fresh runs: party gain <g> ± <e>, buyer's gain <g> ± <e>, <seeds> seeds" (the gain only on an EXP goal). `<at>` is "at step <n>" for a pick, "in the foods" for a food filling that failed its check and "in the drinks" for a drink filling (`notConfirmedAtStep`, `notConfirmedAtFood`, `notConfirmedAtDrink`, chosen by the row's `kind`; a filling has `step: null`). Nothing when absent or empty (an older result). Output only.
5b. One row per setting in "Each change alone": two rows that change the same setting (a trigger's value 4550 and its value 6400) are alternatives, only one can be taken, so the core (`singleRows` in `core.mjs`, through `hideSettingAlternatives` in `tools/whatif/alternatives.mjs`) keeps the first in the search's own order (accepted rows first, then `rankEst`: for free rows the larger buyer's gain, then the larger party gain) and sets `hiddenAlt: true` on the others; they stay in `result.singles` (and the file), keep their indexes (the apply keys `single:<i>` are not renumbered), and the window (`hiddenRow` in `panel.mjs`) draws them nowhere, neither in the table nor behind the grey toggle, and counts them in no figure (`result.md` skips them too). The setting is the key `settingKey(ops)` from the ops' targets (`opTarget`): enhance, equip and unequip share player + slot; trigger player + `hrid`; house player + room; ability player + slot index (or the replaced ability); abilityLevel the same, as its own kind; abilityOrder player; level player + skill; food and drink player + slot; a change of several ops keys on all its targets together (sorted), so it groups only with a change of exactly the same targets. Paid rows are grouped too (the owner's ruling: one row for paid as well, the best-ranked by gain per price shows, the rest stay in the file): equipment +5 and +6 of one slot, a house room +1 and +2; a free row and a paid row of one setting group too, the free one first. The constant `GROUP_PAID` (`alternatives.mjs`, on) is the one switch; set to false it leaves paid rows alone. "Chosen changes", the steps and "Apply 1 to N" read `result.steps`, not `singles`, so they are unaffected. The food rows are one case of the same function (`hideFoodRows` in `foodfill.mjs` calls `hideAlternatives` keyed by player, flag `hiddenFood`). Tests: `tools/test/whatif-alternatives.mjs` (the key per op kind, the helper, the foods case), the block "One row per setting" in `tools/test/whatif-panel.mjs`, one check in `tools/test/whatif-synthetic.mjs`.
5c. It is the same fold every closed list uses (`data-whatif-more` toggle, `.whatif-more` body, handler in `main.js`, open folds kept across a running report), so there is one collapse code path.

N is the group's length; nothing is computed. An absent or empty group (an older result) shows nothing. The `otherStyle` group (swaps to another style's or element's gear, `whatif-runner.md`) has the same fold right after it: "N swaps skipped (only another style's bonuses)", id `whatIfOtherStyle`, one row per swap in the same form.

Nothing when absent or empty. Output only.
8. Every Apply button applies the best foods and drinks first, then its own change (`opsFor` in `panel.mjs`): `result.baselineOps` (the chosen food and drink fillings, with the trigger ops that came with them), then, for Apply on step n, the ops of steps 1 to n together, or, for Apply on a single, its own ops. The search measures every row on top of those foods and drinks, so one click gives the measured setup. A result without `baselineOps` (an older one) or with an empty one applies exactly what it applied before; a single that does not exist applies nothing. An op naming a player no tab is named after applies nothing and names that player. The button labels are unchanged ("Apply", "Apply 1 to n"): they do not say what they apply.

Best foods and drinks (`bestBlock` in `panel.mjs`, drawn by `renderResult` above "Chosen changes, in order", output only): from `result.best`, a "Best foods" and a "Best drinks" group (`whatIf.result.bestFoods`, `bestDrinks`), one line per player, "<player>: A, B, C" in slot order, each item through the page's `itemNames` (the item's last id part if no name). A food with a trigger shows it in parentheses, its terms named through `combatTriggerDependencyNames` and `combatTriggerConditionNames` like a trigger desc; a drink never does. A player the search left alone (`unchanged: true`, and not a so-far leader that carries a status) has no row, even when other players' rows show: his row holds no information. When every player of a kind is that, the table is one line, outside See details: "Best foods: no change" with the stage note after it ("· ended by you during round 1, its finished runs kept"), `data-best-none`. A line "Everything below is measured on top of these foods and drinks." (`bestBaseline`) follows the block. A result with no `best`, or with both groups empty (the lever was off), shows nothing and does not fail. Lines carry the class `whatif-best-line`.

Two labels worth knowing (`panel.mjs`, `renderResult`). **Left out versus not confirmed:** `result.notConfirmed` entries carry `inRace: true` when the pick check on the race's own reading seeds refused a leader (`refute` in the foods and drinks stages, `refuteStep` in a greedy step; the change led a race at some point and had no run of its own); the window lists those under "Left out in the race" (`result.leftOut*`, its own closed list and count) and keeps "Not confirmed" (the old wording: the fresh runs did not confirm them) for the picks that were locked and then failed their own fresh runs (the foods and drinks confirmation, a step's `firstConfirmed`). **No pick:** the "Chosen changes" line of a result with no steps says "No change gains beyond its error within the budgets" only when every candidate was decided; when the screen or a greedy step ended on the round limit with changes still in the running (`result.endedByCap[stage] = { rounds, left }`, set in `race()`; the foods and drinks stages do not count) it says "The search reached its round limit (N rounds) with M changes still in the running; none was picked" (`result.noStepsCap`), and when the user ended such a stage (`result.endedByUser`) "You ended the search for changes before it picked one" (`result.noStepsUser`); the line carries `data-no-steps="cap" | "user" | "none"`. The rows below (Each change alone, the rounds table) are as before; the search picks the same. pt and zh wording is unchecked.

## The live report

`whatIfShowStatus` (`src/main.js`) draws `status.partial` while the search runs, through the same `renderResult(result, t, now, names, running)` (`panel.mjs`) as the final result, with `running = true`; the version is kept in `whatIf.partialVersion` and sent as `since` on the next poll (`API.status(id, since)`). What a running report shows differs from the final one only by what it leaves out and marks: a line at the top says the results fill in as the search goes and the rows shown are final (`whatIf.result.running`); the foods and drinks (`best`) show as soon as they arrive, each changed player's line with a second small muted line, the fresh reading that confirmed it (`whatIf.result.freshBest`, class `whatif-fresh`; `freshBestExp` on an EXP goal); the steps heading carries "so far" (`result.soFar`) and is not drawn until the first step; the "no steps" and "no singles" messages, the confirmation (the totals) and the baseline line (which waits until both groups are there) are not drawn while running; the Each change alone block is skipped when only the hidden food rows exist. A fold the user opened stays open when one running report replaces another (`whatIfShowResult` keeps them); the final result replaces the last snapshot and draws as before. A search that stops (or errors) with a report on screen keeps it, redrawn with `running = 'stopped'`: the top line then reads "Stopped: this is where the search got to" (`result.stoppedMark`). A language change redraws with the same `running` (`whatIf.resultRunning`). Strings in en, pt, zh; the pt and zh wording of the new keys is for a native reader.

## Search rounds

`renderRounds(round, t, names)` (`panel.mjs`) draws `status.round` (the runner's round record, `whatif-runner.md`, "The rounds search") into `#whatIfRounds`, a slot in `index.html` under `#whatIfResult`; output only (no button or input; the existing Stop button is the only control). `whatIfShowStatus` (`src/main.js`) sets `whatIf.round` from `status.round` while the search runs and from `status.result.round` when it is done, so the last round stays on screen after a stop; `whatIfWatch` clears it for a new watch. Contents: one small head line `Search rounds · round <n> finished · simulated hours <h> · still in the running <c> · set aside for now <p> [· ruled out <r>] · ± covers <coverage>% of cases`, then, per pool (`free`, `paid`; the player's name is in the pool heading in the foods and drinks stages, so no row repeats it), a heading with the counts and "sorted by <column>, best first", and a `whatif-table` of the current leaders in that order: the change (a foods or drinks pool has one column per food or drink slot holding the new item of a slot the candidate changes and, in a slot it leaves alone, the player's current item greyed (`change.current`, the item in that slot now) or a greyed `empty` for a slot empty now and staying empty (`whatIf.rounds.slotEmpty`); any other pool has one Change column through `localizeDesc`; an unchanged trigger is the default and is not written), cost, hours simulated (one column; the search and fresh split is in its title), shared loot gain per user, buyer's gain (the two heads and their tooltips are `col.partyGain` / `col.buyerGain`, one definition `gainTh` for every table that has them), payback days, status (`still in the running`, `set aside for now`, `checked on fresh runs`, `ruled out`, `no clear change yet` with `not yet different from no change` as its tooltip; the Status column is 16em so none of these wraps at 1920 or 1366 wide, the `fresh runs: n, m more needed ...` sentence may take two lines). A progress row of a race stage reads `round <n> running` (`finished` once the stage is done); the first look's head reads `round <n> running` too. The sorted column is strictly best-first among the rows that have a figure. Figures are written `value ± half-width` by one helper (`fit` in `panel.mjs`, precision follows the half-width; a range spanning 0 reads `≈ 0 ± X`, the row is greyed and says "no clear change yet"); the window computes no figure. A figure rests on a number of seeds (`figureSeeds` in `src/whatif/figure.mjs`: the search's own seeds on a first-look row, the fresh reading seeds on any other); with fewer than 4 (`FIGURE_MIN_SEEDS`, the one place the number is written, read by the window and the core) the Shared loot gain and the Buyer's gain cells draw no number and no ±: a dim `—` with the hover text "Needs more runs before a figure can be shown" (`rounds.needsMoreRuns`; `pmCell` in `panel.mjs` is the one helper for both columns, in the rounds tables and the Best tables). At 4 seeds or more the cell draws `value ± range` as before, with the grey `≈ 0 ± X` and its row greying. The old `no range yet` string (`rounds.noRange`) is gone. Order (`sortRows` in `tools/whatif/core.mjs`, display only: no choice of the search reads the order of these rows; every row carries `built`, its place in the list the race was built from): while no row of a pool has 4 seeds the rows keep the order the candidates were built in, the pool's `sortedBy` is `null`, its `sortPending` names the column it will sort by, and the heading reads `sorted by <column> once figures exist` (`rounds.sortedByLater`), and no range width on the heading (`rangeWidth` and `rangeWidthPrev` are null: no figure under 4 seeds, so none from a build-order row) instead of `sorted by <column>, best first`; once some row has 4 seeds the rows with a figure sort best-first and the rows without follow in build order. The first-look table (`provisional`) follows the same rule through the same `sortRows`; its line `so far N of M candidates have a first figure` and the Status `still measuring` are unchanged. A leader with no fresh runs yet shows `no fresh runs yet`; with fewer than the minimum it shows how many more runs are needed. The Chinese and Portuguese wording of the new strings (`rounds.needsMoreRuns`, `rounds.sortedByLater`) is not checked by a native speaker. While round 1 runs, the record is provisional (`provisional: true`): the section shows `first look: so far N of M candidates have a first figure` and the rows with status `first`; the real table replaces it at the end of round 1. The "Unknown cost, not ranked" list starts collapsed. Strings `common:whatIf.rounds.*` in en, pt and zh (pt and zh for a native reader). Dark mode and one scroll axis come from the surrounding window (the section sets no overflow of its own).
