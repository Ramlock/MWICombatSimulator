# The What-if window

The page's What-if window runs the what-if optimizer (`tools/whatif/optimize.mjs`) through the local what-if runner: a program on the user's own PC that serves this page and runs the search at low priority on every core. The public website has no runner, so there the same button opens the window in its "get the runner" state (below).

## Two states

`initWhatIf` (`src/main.js`) asks `/api/version`. When no runner answers, `whatIfShowGetRunner` shows the button and puts `whatif-norunner` on `#whatIfModal`; the CSS in `index.html` then shows only `#whatIfGetRunner` (one paragraph on why, the download link (the exe), four steps: start, SmartScreen, the black window, the What-if button) and hides the search; with a runner the class is absent and that pane is hidden. The link targets are the two constants of `src/whatif/runnerDownload.mjs`: `RUNNER_DOWNLOAD_URL` (Windows, `WhatIfRunner.exe`) and `RUNNER_ZIP_URL` (the Linux part, `WhatIfRunner.zip`). Strings: `common:whatIf.get.*` in en, pt and zh (pt and zh not checked by a native speaker; the pt SmartScreen names are Microsoft's own). The downloads themselves (the Windows exe, the Linux zip): `runner-zip.md`. Test: `tools/test/whatif-get-runner-page.mjs`.

## Layout: the rule and its parts

The window follows one rule: **no fact travels inside a sentence.** A number, a state, a name or a count is a table cell or a chip (`span.whatif-chip`; a labelled one holds `span.whatif-chip-k` then the value); a sentence is allowed only as a tooltip, behind a help mark, or as a warning that changes what the result means (`.whatif-callout`: the base loses money, an error). The helpers are in `panel.mjs`: `chip(html, cls, tip)`, `help(tip)` (a `span.whatif-help`, "?", `tabindex=0`, its sentence in `data-tip`; one tooltip, `div.whatif-tip`, serves every mark of the window: `attachTips` in `src/whatif/tip.mjs`, attached to `#whatIfModal` once, shows it on the mark's hover or keyboard focus with `position: fixed`, under the mark (above it when there is no room below), moved inside the window's `.modal-content` cut to the screen, so no cell that hides its overflow (a stage row's label) cuts it and it adds no scrollbar; while it shows it follows the mark each frame and hides once the mark has neither hover nor focus or has left the page), `fig(label, value)` (a small labelled figure, `.whatif-fig`), `arrowed(html)` (a change text split into `.whatif-from` → `.whatif-to`). Dark only; table heads have a background, rows are zebra, numbers are right-aligned in tabular figures.

1. **State chip:** `#whatIfState` in the title bar (`whatIfSetState`, `main.js`): idle, starting, searching, stopping, stopped by you, done, error (`whatIf.stateChip.*`).
2. **Setup and result are separate areas.** The setup form is `#whatIfSetup` (two columns: Goal, Players, then Zone and Tier on one row on the left; What to search, the payback limit and the budget per player on the right). Once a search runs or a result shows, `whatIfShowSetup` (`main.js`) hides it and shows `#whatIfSummary`, one bar of chips (`#whatIfSummaryChips`: goal, zone and tier, each ticked player's budget or `budgetPlaceholder` ("no limit"), the payback limit (`paybackChip`, `days`), the ticked kinds of change) with an "Edit setup" button (`#buttonWhatIfEditSetup`, `whatIf.setupOpen`, text `editSetup` / `hideSetup`). Idle with no result, the form is open and the bar hidden. Goal and zone show once: in the bar, or in the open form; the result's own chip row holds only the base profit. The Start / Stop row (`#whatIfStartRow`, `.whatif-toolbar`) sits under both.
3. **What to search** (`#whatIfLevers`): a compact grid of ticks, each a short bold name (`lever.<id>.name`) and a help mark holding its sentence (`lever.<id>.desc`); a tick that cannot be used shows the chip "needs export" (`needsExport`, CSS `:has(input:disabled)::after` from `data-off`). The players' help mark (`choicesNote`, "Players whose tab holds a setup start ticked when this window opens…") sits beside the Players heading (`data-whatif-tip`, filled by `whatIfTips`).
4. **Pending states:** the one Start / Stop button (`#buttonWhatIfSearch`, below) shows "Starting…" or "Stopping…" (disabled) at once; a pressed Skip or Accept gets `whatif-pending` and reads "Skipping…" / "Accepting…" (`progress.stageSkipping`, `stageAccepting`). Stop is an outlined red button.
5. **Left-out counts:** under the answer, one row of amber chip buttons, one per limit that left changes out ("3 over the payback limit", "1 over budget": `result.leftOutPayback`, `leftOutBudget`, singular `…One`, the list's note as title; the changes with no known cost have no chip, their list under See details says it); each opens its list and See details together (`data-whatif-more="<list id> whatIfDetails"`). Old prices are an amber chip (`result.pricesChip`, the full `pricesLine` sentence as its title). With no answer drawn (a report still running, or a result with no confirmation) these chips join the result's top line (Results, item 4) instead.

6. **Language switch:** `languageChanged` (`initWhatIf`, `main.js`) draws every part again: the tips, the choices and setup, the list, the state badge and the Start / Stop button (`whatIfDrawSearchButton`), the progress table (`whatIfDrawProgress`), the rounds, the result (with the setup warning) and the charts. A set's How it is bought chip names each member's path (`priceHow` splits the core's " + "). The setup warning's slots (`diffLabel`): a food or drink slot by the game's item category word (`itemCategoryNames`), an ability slot by the game's ability slot word (`words.ability`), then its number.
7. **Running mark:** the result's top line holds the running mark; when the mark would stand alone there (no base profit yet, nothing left out) and a Best foods or drinks heading already carries "so far" (its tooltip the same `result.running` sentence), the line is not drawn. A stopped report keeps its stopped mark line.
8. **Stage buttons:** Accept current winner and Skip this stage are `btn-outline-light` while live; disabled (pressed, or Stopping) they are dimmed (`.whatif-stage-done:disabled`, opacity .35), the pressed one amber.
9. **Stage marks:** the mark (check, arrow, circle) is the stage row's first cell, a table cell centred on its row like every other cell (`.whatif-parts-table td.whatif-part-mark` in `index.html`, the one rule for it), so it sits level with the State chip in a tall running row and beside a stage name on two lines. Test: `tools/test/whatif-window.mjs` ("stage marks").

Tests: `tools/test/slot-names.mjs`, `tools/test/slot-names-page.mjs`. With `onlySelected` it reads the window's own tick boxes, never the page's.
   The window has its own choices (`whatIfRenderChoices`): a tick box per player tab (`#whatIfPlayers`), a zone selector (`#selectWhatIfZone`) and a tier selector (`#selectWhatIfTier`). Each time the window opens (`show.bs.modal`) every player whose slot holds a character starts ticked and every other starts unticked, whatever the page's own ticks are (a reload keeps the imported group, `restoreImportedGroup`, but not the page's ticks, and an import without `selected` ticks nobody on the page); the zone and tier are copied from the page. "Holds a character" is `slotHasData` (`panel.mjs`): the slot's setup has some skill level above 1, some equipment, or some food, drink or ability chosen, as a party import, a one-player import or a setup made by hand gives; an untouched tab is the page's empty player and does not; zone, simulation time, house rooms, triggers, achievements and the name are not looked at. With no player holding one, none is ticked, the "tick at least one player" message shows, and the user ticks players in the window. The two selectors are built from the page's `#selectZone` and `#selectDifficulty` options (same values, order and names; an option keeps the page's `data-i18n` key, so the page's own language switch renames it). Edits in the window never write to the page. The budget fields (each starts empty with the placeholder `whatIf.budgetPlaceholder`; empty or 0 is sent as 0 and means no limit, `whatIfBudgetValue` in `src/main.js`; the payback limit field starts at 0, no limit), the message (shown whenever no player is ticked in the window, cleared when one is) and the request (`slots`, `options.zone`, `options.tier`) follow the window's controls. A language change redraws the names and keeps the window's picks. Apply and the "where the page differs" warning still read the page (`whatIfSlots(false)`).
   Layout: the setup form is two columns (`.whatif-col`, 5/12 and 7/12), each a flex column of sections with one gap (`--whatif-gap`, 12 px); the Players heading carries its help mark. Zone and Tier share one row (`.row.gx-2`, two `col-6` input groups, each half the left column, the label inside the group). Under that row, a full-width input group holds the guild's shrine level (`#inputWhatIfShrineCap`, label `whatIf.shrineCap`; empty = the game's maximum): `whatIfReadSettings` (`main.js`) rejects anything but a whole number of 0 or more (`whatIf.badShrineCap`), and `searchBody` (`panel.mjs`) sends it as `shrineCap` only when Shrines is ticked and the field is filled. The budget per player (heading `whatIf.budgets`, "Budget per player (coin, empty or 0 = no limit)") sits in the right column under the payback limit: `#whatIfBudgets` is one row of five equal cells (`.whatif-pcell`, `repeat(5, minmax(0, 1fr))`), one per ticked player, each the player's name (ellipsis), the budget field and the export mark under it. Five players fit at 1920x1080, 1500x900 and 1100x900 with no horizontal scroll; the page test measures it.
   Character export per player: there is no paste field. A party import from userscript 0.9.3 or later carries the own player's `inventory` and `learnedAbilities`, and so does a Tracker character export pasted into one player's own import field (Group Combat tab, "Player N import"): `doGroupImport` (`main.js`) sends the all-players field, or the per-player fields when it is empty, through the one `splitGroupImport`; they are taken out of the slot (the sim slot is as an import without them gives) and kept, through `whatIfKeepExport` (`whatIfKeepImportedExports`, `main.js`), in `localStorage` under `whatIfExport:<the name the window shows that player by>` (`exportKey`). `parseExport` (`panel.mjs`) validates it (a JSON object with an `inventory` or `learnedAbilities` array); a valid one replaces any kept one, a bad one is not kept. It is kept across window opens and page reloads, and there is no clear control; an import without those fields keeps nothing and clears nothing. Under each player's budget a chip (`.whatif-pstatus`, `data-export-status`, the whole text as its title) says where that player's owned items and abilities come from (`exportStatus`): "items and abilities: Tracker import" (`exportFromTracker`) when an export is kept, else "items and abilities: none" (`exportFromNone`). Items you own and Abilities stay greyed while no ticked player has one (`whatIfApplyExportLevers`, note `exportLeverOff` behind their help mark). The request carries `export: { "<player name>": <export> }` for every ticked player with a kept export, and no `export` when none. The storage is the data: nothing is read back from displayed text. Apply writes the new slot JSON into `playerDataMap` and reloads the screen (`updateNextPlayer`, `updateState`, `updateUI`), as an import does.

## The runner's interface (JSON over HTTP, same address as the page)

1. `GET /api/version`: `{ runner, engine }`.
2. `POST /api/search`: `{ setups, options: { zone, tier, marketplace }, goal: "profit" | "exp", budgets: { "<player>": coin }, levers: [...], players }` answers `{ id }`. `levers` is the ticked lever ids, as the window lists them (`LEVERS` in `panel.mjs`: equip, foods, drinks, owned, abilities, order, triggers, houses, shrines; Shrines is the guild shrine lever, and the field under Tier, `inputWhatIfShrineCap` (empty by default = the game's maximum; a whole number of 0 or more, else the window says `badShrineCap` and starts nothing), is the guild's shrine level, sent as `shrineCap` only when Shrines is ticked and the field is filled (`searchBody`); a shrine row's How column, and its line in the over-budget and pays-back-too-slowly lists, show its split (`shrineSplitText`, key `shrine.split`: tokens required; the credits as market items in Coin, or as spare tokens), and its change names the shrine in the shown language (`guildShrineNames`); Foods and Drinks are two boxes, each ticked by default, each with its own name and description in en, pt and zh; the pt and zh strings of the two are not checked by a native speaker). An old request that says `consumables` is read as both by the optimizer. `marketplace` is the game's `marketplace.json` body, fetched when Start is pressed by `fetchMarketplace` (`src/marketplace.mjs`, shared with the page's Get Prices button; `searchRequest` in `panel.mjs`); when the fetch fails the window says so and starts no search (no older snapshot is used in its place); a second search while one runs is refused with the running `id`, and the window then follows that one.
3. `GET /api/search/<id>?since=<n>`: `{ state: "running" | "stopped" | "done" | "error", progress: { stage, candidatesLeft, runsDone, runsPlanned, secondsPerRun, etaSeconds }, error?, result?, partial?, partialVersion?, round?, roundVersion? }`. The window polls it every second while it runs, with `since` = the highest `partialVersion` or `roundVersion` it has drawn (`whatIf.partialVersion`, 0 for a new watch; one counter serves both); a running search carries `partial` (the report so far, the same shape as `result`) and `round` (the latest search-round record) each only when newer.
4. `POST /api/search/<id>/stop`: stops a running search; the same request on a stopped one resumes it.
5. `GET /api/results` (newest first, `{ id, finished, goal, players, stopped? }`) and `GET /api/results/<id>` (one result, or a stopped search's `partial.json`). "Earlier searches" (`whatIfLoadList`, kept in `whatIf.earlier`, drawn by `whatIfDrawList`, redrawn on a language change with the selection kept, read again when the window opens and when a search is done or stopped) lists both, a stopped one with "Stopped" (`whatIf.state.stopped`, en/pt/zh) at the end of its entry. Show (`whatIfLoadResult`) draws the report, its last search round (`round`) under it, and for a stopped entry the stopped mark, as the window shows a search right after Stop; `whatIf.resultLoaded` marks a report put on show this way, so a watched search's poll never turns its stopped mark into a running one. A new search's Start clears the result on show, its setup warning and its rounds (`whatIfClearResult`, once the settings are read; a start the window refuses keeps them); Resume does not clear. A page reload shows no result until Show. Tests: `tools/test/whatif-window.mjs`, `tools/test/whatif-runner.mjs`.

**Polling** (`whatIfWatch`, `whatIfPoll`, `whatIfPollSoon` in `src/main.js`; the wait is `pollDelay` in `panel.mjs`): the window watches one search with one poll loop, one request at a time (the next poll is set once the last answer is in, so a slow runner never piles requests up). The wait is `POLL_MS` (1 s); after a press of Stop, Resume or a stage button the loop polls at once (`whatIfPollSoon`) and then every `FAST_POLL_MS` (250 ms) for `FAST_FOR_MS` (30 s), and, for a pressed stage button, as long as its part is still running. The runner answers Stop and Resume at once (`{ stopping }`, `{ resumed }`); the window's change shows at the poll that sees the new state. Stop keeps the report version and rounds the window has (`partialVersion`, `round`), so nothing is fetched again or blanked; a new search id starts from 0, and so does a Resume (a new optimizer process; the runner may have restarted). Tests: `tools/test/whatif-panel.mjs` (`pollDelay`), `tools/test/whatif-window.mjs` (Stop shows Start and Resume within 900 ms of the click when the runner stops 300 ms after it; no status request after Stop asks from 0).

**The Start / Stop button** (`#buttonWhatIfSearch` in `index.html`; its one state function is `whatIfDrawSearchButton` in `src/main.js`, which decides the label, the look and what a click does, and returns that action; the click, `whatIfSearchButton`, does what it returns): one button shows what a click would do. Start (`btn-primary`) when no search runs; "Starting…", disabled, from the click until the runner reports the search; Stop (`btn-outline-danger`, outlined red) while it runs; "Stopping…", disabled, from the click until it reads stopped. On a stopped search it reads Resume while the window's settings are the ones that search was started with, and Start once one differs (changing it back gives Resume again); a finished search reads Start. "The settings" are the request the window would send without its prices (`settingsKey` in `panel.mjs`: `searchBody` with no market snapshot, as one string: goal, zone, tier, budgets, payback limit, levers, the players' setups and kept exports); `whatIf.sentKey` is the key of the search started from this window (null for one it did not start), compared with the window's key now (`whatIfReadSettings(false)`, the same reading a start does, without marking the fields); fresh prices alone never turn Resume into Start. The window redraws the button on every `input` and `change` in it while a search is stopped. A click on Resume continues that search with its stored runs: `POST /api/search/<id>/stop` on a stopped search, which the runner restarts from its own saved request (same settings, prices and folder; `whatif-runner.md`); at the click it reads Starting, as a start. `whatIf.pending` (`'starting'` / `'stopping'`) is the click not yet shown: it is set at the click, before any request, and cleared by `whatIfShowStatus` when the runner's state shows (Starting on any state; Stopping once the state is not running). A start that ends with no search watched (a check, the price fetch or the runner failed) and a failed stop clear it, so the button is back to what it was, with the message. `whatIfDrawSearchButton` is the only code that sets the button, and it sets the title bar's state chip (`whatIfSetState`) from the same state, so the two never disagree; the window draws it on open too, so a window opened on a running search shows Stop (opening copies the page again, so on a stopped search it shows Resume only if the page gives the same settings). Strings `whatIf.start`, `starting`, `stop`, `stopping`, `resume` (en/pt/zh). Tests: `tools/test/whatif-window.mjs` (the four states, Starting and Stopping right at the click, a failed start and a failed stop back to Start and Stop, the window reopened on a running search, Resume on a stopped search with nothing changed, Start once the payback limit changes and Resume again when it changes back, Resume reading Starting at the click and continuing the same search with no new search posted, Start on the finished search), `tools/test/whatif-panel.mjs` (`settingsKey`: a market snapshot changes nothing, a budget does).
6. `POST /api/search/<id>/done` with body `{ mode: 'accept' | 'skip' }` (`400` for any other): the two stage buttons, "Accept current winner" and "Skip this stage" (no stage name in the button). The runner sends `{ done: mode }` over the IPC (beside `stop`), `optimize.mjs` hands the mode to the core's `stop.press(mode)` (`core.mjs` `main`): it sets `stop.done` and, while a race batch runs, ends that batch's runs in flight through the pool's `drop()` (`dropRuns`, set by `ensure()` only for the race's own batches); an ended run is not stored, its compute is lost. The core's `race()` clears `stop.done` at its start. Both buttons end the stage at once: a press during a round's runs makes `ensure()` return `BY_USER` and the race ends through `userEnd` with the last finished round's leaders (none in round 1); a press after the round's last run ends it after that round's record, as before. **Accept** locks, in each pool without a lock (a player's, or the stage's single one), the best live leader whose figure the window shows as a figure (`acceptTakes` in `rounds.mjs`, fed by `gainOf`, which reads `showsFigure` from `src/whatif/figure.mjs`, the one helper the window shares: at least 4 reading seeds and a range that does not reach 0, so not "≈ 0"; a mean above 0, never a time-only lever, never a candidate the elimination rule put out), and ends the stage through the one end path: pressed during a round's runs, with what the last finished round offered (`prevTakes`, the figures the window showed); pressed after the round's last run, with that round's. The pick is taken as it is: **no pick check** (no `confirmPick`, no fresh seeds) and it enters the baseline directly (a greedy step, or a foods/drinks filling); the report marks it `acceptedAsIs: true` (the steps row, `result.best[kind][player]`) and shows "accepted as is" beside it (en/pt/zh); it is never in `notConfirmed`. A pool that had already locked keeps its pick, checked as usual. `result.endedByUser[stage] = round` (the rounds the stage finished: the report says "ended by you after round N"). **Skip** ends the stage at once: in `ensure()` (`core.mjs`) the lanes take no new runs and the runs in flight are ended (`skippable`; `pool.drop()`, never `pool.kill()`; a run that had finished is stored, an ended one is not), the race returns the earlier round's leaders (none in round 1) with no new lock, keeps the locks it already had, and the search carries on to the next stage (`result.incomplete` and `result.stoppedBy` stay unset); `endedByUser[stage]` is the number of rounds the stage finished, **0 when Skip came before the first round finished** (any reader of `endedByUser` tests `!== undefined`, not truthiness). `result.endedBySkip[stage] = true` marks a Skip (absent for an Accept): the report and the Best heading say "ended by you during round N, its finished runs kept" with N = `endedByUser` + 1 (so 1 for a Skip pressed in round 1; `endedText` in `panel.mjs`, `endedMd` in `core.mjs`, string `result.endedByUserDuring`), an Accept says "ended by you after round N". The ended stage's own line says "round N · ended by you" instead of "round N finished" (`progress.stageSkipped` from `endStage` → the row's `skipped` in `progress.mjs` → `rounds.roundSkipped`). The core publishes how many pools Accept would take each round (`progress.stageAcceptable`, the part's `acceptable`), and the window draws "Accept current winner" only while that is above 0 (so "no change leads", or a figure not yet shown, gives Skip alone); the buttons are drawn only on the race stage running now (`data-whatif-done="accept"` / `"skip"`, `data-whatif-part=<kind>:<index>`, in the last cell of the stage's row). After a press `main.js` keeps `whatIf.pressed` and the window draws both buttons disabled until the stage's row stops running (no note: both end the stage at once); the pressed button shows its pending state (Layout, item 4): `whatif-pending`, "Accepting…" or "Skipping…". The progress redraw (`whatIfDrawProgress`, `main.js`) reuses an unchanged button node, so a poll does not replace the button under the pointer (no hover flicker). A command-line run has none. `409` when nothing runs.

Status column of the rounds table: one or two words (`clear gain`, `no clear change yet`, `party loses loot`, `still measuring`, `set aside`; `ruled out` is not listed); counts and internal states are the cell's tooltip (`rounds.status.<key>Tip`). Best foods / drinks while the stage runs: a leader without a clear gain (core flag `unclear`, plus `loses`; the entry is the final's `unchanged` form with the leader kept as `candidate`) shows the player's current items greyed, a dash for the figures, and the status with the candidate and its figures as tooltip. Players in every list follow the party's own order (`players`): `poolSorter` in `rounds.mjs` for the pools, `partyEntries` / `inParty` in `core.mjs` for `result.best`, the budgets and the per-player confirmation lines.

## The progress block

The stage list (`#whatIfProgress`) and the search rounds (`#whatIfRounds`) are redrawn at every status poll, in place: `morphInto` (`src/whatif/morph.mjs`) parses the new markup apart and brings the box to it node by node, keeping every node of the same kind at the same place and writing only changed attributes and text. A control whose markup did not change is not touched, so the stage button under the pointer keeps its hover (a node replaced, or moved out of the page and back, dropped its hover and faded back in through the button's transition at every poll: the flicker), and a help mark keeps its tooltip; a real change (pressed, Stopping, no leader to accept) shows at once in the same node.

`renderProgress` (`panel.mjs`) draws the stage list from `progress.parts` (`renderParts`; `whatif-runner.md`, "Progress parts") as one table, output only. Its head is the title "Search progress" (`progress.title`) with three labelled figures beside it: Stage K / N (K = the running row's place from 1, N = the rows shown, placeholders included), Seconds per run (two decimals) and elapsed (h:mm:ss). Columns (`progress.col.*`): mark, Stage, State, Round, Runs, Sim. hours, Contenders, Set aside, Ruled out, Progress, Details, and the buttons. The layout is fixed (`table-layout: fixed`, a `colgroup` from `PART_COL_WIDTHS` in `panel.mjs`; Details takes the rest of the width): no state, badge, count, bar or text of a row moves or resizes a column; a long text in Details is cut with its whole text in the cell's tooltip, and labels and buttons wrap. Every column title fits its column on one line in en, pt and zh at 1920 wide (`whatif-window.mjs`, "column titles"; Ruled out is 6.5rem for pt's Descartadas). One row per part (`tr.whatif-part.whatif-part-<state>`, `data-kind`, `data-state`): the mark (`✓` done, `▶` running, `○` waiting, `■` halted, `–` not run), the bold stage name, a state chip (`whatif-st-<state>`, text `progress.st.*`: Done, Running, Waiting, Stopped, Not run, Ended by you, Searching, Checking leaders, Checking the winner; the sentence it stands for, such as the pick check's runs, why a part never ran, the time left or the rounds to separate the leaders, is the chip's title), the round, the runs (a race's runs; any other part "done / planned", with a 4 px bar while it runs), the simulated hours, the three contention counts (a done row shows no Contenders nor Set aside: its race is over), Progress (a race row: ruled out over all its candidates as a bar and a %, its header's help mark says it counts changes, not time; 100 % when done; it moves back when candidates come back) and Details (the winner under check, named as the result names it, with its check's runs; else the runs of this round kept from before a stop, and the last winner its check left out, every one with its figures in the help mark, followed while the race goes on by how many candidates returned to the race). A count of 0 is an empty cell; a waiting row is dim and has no bar. Names: `Best foods`, `Best drinks`, `Change 1` (kind `screen`), `Change <k+1>` (`stepLabel`), `More changes: up to <stepsLeft> more`, `Final check of the whole set`; the long names are a short name with their sentence behind a help mark: `Changes, one at a time` (`progress.partStepsShort`; help `partSteps`, "…up to <maxSteps>, stops when none helps") and the waiting final check (help `partConfirmationWaiting`). Each row carries its own pick check: Searching, then Checking the winner, then Done (or Searching again when its winner was left out). Checking the winner covers all of the Change's work from its race's end until its pick is taken or left out (`whatif-runner.md`, "Progress parts"), so Done never shows while that work runs. Only a running search has a running row: the part running when the search stopped is drawn halted, its figures kept, no buttons. A race stage that has ended is a done row at once, with the last round record's counts. An error is a red callout under the table. A progress with no `parts` (an older search) draws the single line as before. Strings `common:whatIf.progress.*` in en, pt and zh. Styles `.whatif-part*`, `.whatif-parts-table` in `index.html`.

## What the window reads from a result

1. Top: the answer first, under its heading (`result.answer`, "All chosen changes together, checked on fresh runs", drawn only with a confirmation): the per-player table from `confirmation` (Player, Gain per day as `value ± error`, Pays back in (days); the party row "Party (the shared loot, per user)" with its Cost; `buyerByPlayer` per player; a dash when the payback is none or 0; a result without `buyerByPlayer` shows its party payback and a run-the-search-again line instead), then the left-out chips (Layout, item 5), then `best` (item 9), then Chosen changes. `apart` (unknown cost) and `overBudget` (priced above its player's budget) are listed only under See details, as tables (item 5). `options.pricesTimestamp` / `pricesSource`: the old-prices chip (`pricesLine` in `panel.mjs` decides when: a market snapshot 24 hours old or more, or the simulator's own saved snapshot).
2. Each row of `steps` and `singles`: `player`, `desc`, `sharedGainPerUser` and `sharedSePerUser` (the party gain per player per day and its error), `buyerNet` and `buyerNetSe` (the gain of the player who pays, per day, and its error), `cost`, `costBound: "upper"` (printed as "≤" on the cost and the payback), `payback` (the buyer's payback; none or a net of 0 or below shows "—", except that a cost of exactly 0 shows "no cost, nothing to pay back", `whatIf.result.noCost`; the same words stand in a player's confirmation line when his `runningSpend` is 0, and in `result.md`), `costPath` and `note` (the core's `priceFields`): How it is bought, the price path, rendered by one helper (`pricePath` in `panel.mjs`, keys `whatIf.price.*`, en, pt and zh) for every list with a cost: the How it is bought cell of Chosen changes and Each change alone (the path as a chip, its notes as the chip's title), and "(<price path>)" after the cost in the Cost cell of the Priced, over budget and Pays back too slowly tables (notes in brackets), where a plain market buy (`costPath` "market", no note) names none. A shrine row (`shrineSplit`, from the core's `priceFields`) shows its split instead of a path, "<tokens> Guild Tokens required; Guild Credits: <coin> Coin as market items, or <tokens> spare Guild Tokens" (`shrineSplitText`, key `whatIf.shrine.split`): as the How it is bought chip, and after the cost in the closed lists; one helper, `pathHtml`, picks the split or the price path for both. The paths and the pricer's notes read in the shown language, a path or note the table does not know as the core wrote it; without the "; upper bound (XP inside the level unknown)" caveat, which the footnote under the table keeps (TODO row 99, his pick "B: each row names how it was priced"), `accepted` (a single that is not is grey and sits behind one "Show N more not accepted" toggle), `ops`; a single also `lastStage`. A result with no `buyerNet` (an older one) shows a dash in both buyer cells, and on an EXP goal they are dashes too. The old Spent, Stage, Shared gain and Own supplies columns, the "spent of budget" line and the helps-the-party table are gone; a row of an older result flagged `helpsParty: true` shows as an ordinary row. The search accepts a change when one of the party gain and the buyer's net is above 0 by at least z errors and the other is not below -(z/2) errors (`acceptBoth`, `whatif-runner.md`); the party gain is the group's shared loot gain per player, before anyone's own food and drink. A gain figure (party or buyer, in both tables, the confirmation line and each player's confirmation line) whose absolute value is less than one error shows the words "no change" (`whatIf.result.noChange`) with the real value as the hover title ("+288K ± 242K"), the error cell next to it shows "—" with the same title; one error or more shows the number. The Change column of Each change alone is 50em wide and wraps (`index.html`), so at 1920x1080 the table has no horizontal bar even for a food change of about 230 characters; the page test measures it at 1920, 1600 and 1366 wide.

The names are the game bundle's own tables, read as the page's `data-i18n` lookups read them (`i18next.getResourceBundle`, with English as the fallback, `namesFrom`): `itemNames` (a refined item has its own entry with the page's "★"), `abilityNames`, `skillNames`, `equipmentTypeNames` (the slot), `combatTriggerDependencyNames` and `combatTriggerConditionNames`. An id with no name stays as it is. The language-change handler redraws the result, so the names follow. Not covered: `costPath` and `note` are the runner's text.

## The live report

`whatIfShowStatus` (`src/main.js`) draws `status.partial` while the search runs, through the same `renderResult(result, t, now, names, running)` (`panel.mjs`) as the final result, with `running = true`; the version is kept in `whatIf.partialVersion` and sent as `since` on the next poll (`API.status(id, since)`). What a running report shows differs from the final one only by what it leaves out and marks: a line at the top says the results fill in as the search goes and the rows shown are final (`whatIf.result.running`); the foods and drinks (`best`) show as soon as they arrive, each changed player's line with a second small muted line, the fresh reading that confirmed it (`whatIf.result.freshBest`, class `whatif-fresh`; `freshBestExp` on an EXP goal); the steps heading carries "so far" (`result.soFar`) and is not drawn until the first step or the first "so far" row; the "no steps" and "no singles" messages, the confirmation (the totals) and the baseline line (which waits until both groups are there) are not drawn while running; the Each change alone block is skipped when only the hidden food rows exist. A fold the user opened stays open when one running report replaces another (`whatIfShowResult` keeps them); the final result replaces the last snapshot and draws as before. A search that stops (or errors) with a report on screen keeps it, redrawn with `running = 'stopped'`: the top line then reads "Stopped: this is where the search got to" (`result.stoppedMark`). A language change redraws with the same `running` (`whatIf.resultRunning`). **The "so far" rows:** while a Change is searched (the screen or a greedy step, its pick check included), every candidate of the latest round record (`whatIf.round`, the record the Search rounds table draws) whose gain so far (its figure in that table) is above 0 is a row under Chosen changes, in order, below the confirmed rows, largest first: no number, its figure as the rounds table has it (the gain, half its range as the error, the buyer's gain), its cost and payback, and in place of the Apply button a "so far" chip (`result.soFar`) whose title says it is not checked yet, goes away if it stops being positive, joins the chosen changes when its check passes and cannot be applied (`result.soFarRowTip`). `soFarSteps(round, progress, steps)` in `panel.mjs` picks them (none when the record is of another stage than the one the progress names, a foods or drinks race, a ruled-out, figure-less or non-positive candidate, or one already among `steps`; a record lists each pool's leaders, so those are the candidates that can show), and `renderResult(..., soFar)` draws them with the confirmed rows' own row code (`stepRow`). `whatIfShowResult` passes them only for a running report the window watches (none for a stopped one, a finished one or one from Earlier searches), and `whatIfShowStatus` redraws the report when they change (`whatIf.soFarKey`), so a row comes and goes at the next round record with no new report. Tests: the "so far" block in `tools/test/whatif-panel.mjs`, and "so far, in the page" in `tools/test/whatif-window.mjs`. Strings in en, pt, zh; the pt and zh wording of the new keys is for a native reader.

## Search rounds

Contents: a head, the title "Search rounds" with labelled figures (Round, simulated hours, still in the running, set aside for now with its help mark, ruled out, Coverage), then, per pool (`free`, `paid`; the player's name is a chip in the pool heading in the foods and drinks stages, so no row repeats it), a title cell with chips (the owner, Contenders N, Set aside N, "sorted by <column>, best first") and a help mark for the range width, and a `whatif-table` of the current leaders in that order: the change (a foods or drinks pool has one column per food or drink slot holding the new item of a slot the candidate changes and, in a slot it leaves alone, the player's current item greyed (`change.current`, the item in that slot now) or a greyed `empty` for a slot empty now and staying empty (`whatIf.rounds.slotEmpty`); any other pool has one Change column through `localizeDesc`, split from → to, with the player as a chip when the pool is not one player's; an unchanged trigger is the default and is not written), cost, hours simulated (one column; the search and fresh split is in its title), shared loot gain per user, buyer's gain (the two heads and their tooltips are `col.partyGain` / `col.buyerGain`, one definition `gainTh` for every table that has them), payback days, status as a chip, its counts as the chip's title (`still in the running`, `set aside for now`, `checked on fresh runs`, `ruled out`, `no clear change yet` with `not yet different from no change` as its tooltip; the Status column is 16em so none of these wraps at 1920 or 1366 wide, the `fresh runs: n, m more needed ...` sentence may take two lines). A progress row of a race stage reads `round <n> running` (`finished` once the stage is done); the first look's head reads `round <n> running` too. The sorted column is strictly best-first among the rows that have a figure. Figures are written `value ± half-width` by one helper (`fit` in `panel.mjs`, precision follows the half-width; a range spanning 0 reads `≈ 0 ± X`, the row is greyed and says "no clear change yet"); the window computes no figure. Order (`sortRows` in `tools/whatif/core.mjs`, display only: no choice of the search reads the order of these rows; every row carries `built`, its place in the list the race was built from): while no row of a pool has 4 seeds the rows keep the order the candidates were built in, the pool's `sortedBy` is `null`, its `sortPending` names the column it will sort by, and the heading reads `sorted by <column> once figures exist` (`rounds.sortedByLater`), and no range width on the heading (`rangeWidth` and `rangeWidthPrev` are null: no figure under 4 seeds, so none from a build-order row) instead of `sorted by <column>, best first`; once some row has 4 seeds the rows with a figure sort best-first and the rows without follow in build order. The first-look table (`provisional`) follows the same rule through the same `sortRows`; its line `so far N of M candidates have a first figure` and the Status `still measuring` are unchanged. A leader with no fresh runs yet shows `no fresh runs yet`; with fewer than the minimum it shows how many more runs are needed. The Chinese and Portuguese wording of the new strings (`rounds.needsMoreRuns`, `rounds.sortedByLater`) is not checked by a native speaker. While round 1 runs, the record is provisional (`provisional: true`): the section shows `first look: so far N of M candidates have a first figure` and the rows with status `first`; once the round's cut is made (before the leaders' check, which can take minutes), the first look goes out again with only the changes still standing, so the table drops the ones ruled out at once, and the progress row's Contenders and Set aside take that round's counts at the same moment (core.mjs race; test tools/test/whatif-cut-redraw.mjs); the real table replaces it at the end of round 1. The Payback cell of a rounds-table row follows the same 4-run rule as the two gain cells, through the one helper (figCell in panel.mjs: the dim dash and the needsMoreRuns hover text). The "Unknown cost, not ranked" list starts collapsed. Strings `common:whatIf.rounds.*` in en, pt and zh (pt and zh for a native reader). Dark mode and one scroll axis come from the surrounding window (the section sets no overflow of its own).

## The search chart

1. `src/charts/base.mjs`, the shared base of the page's Chart.js charts (the planned XP-per-hour chart can use it too; it knows no what-if field): `THEME` and `darkAxis` (dark colours, tick formatter, fixed range), the geometry as pure functions (`clipRange`, `barGeometry`, `bandRuns`: what a ± bar or band draws and which end ran off the chart edge) and `errorBarsPlugin`, the Chart.js plugin that draws a dataset's `errorBars` (a bar per point, caps, the figure's mark) and `errorBand` (a shaded band along the line); an end beyond the chart area is drawn fading out at the edge. A band is filled with a vertical gradient that fades over the last 14 px at the area's top and bottom (`scaleAlpha`), so a band that reaches an edge runs off the chart; a band end of ±Infinity (a range open on that side) is drawn to that edge (`bandRuns`). Tests: `tools/test/charts-base.mjs`.
2. `src/whatif/history.mjs`, the chart's data (`buildHistory`; no DOM, no estimate: every figure is a field of a round record): the finished round records grouped by stage, pool and candidate (a line per candidate that was among the pool's leaders, a point per round where its figure shows, which is the 4-seed rule of `hasFigure`), the pool's sort column read from its record (`buyerNet`, `payback` with `paybackLow` / `paybackHigh`, or `reading`; a payback is better the lower it is), the per-round `toBeat` level (the lowest lower end among the leaders that have a figure; for a payback the highest upper end) and the latest round's leaders in table order with their rank and the previous round's position (`prev`, given by the core). A stage run again (a resumed search replays its stages from round 1 into the same file) keeps only its last run (`lastRuns`). A stage with no record (Skip before the first round finished) is not in the history; the window shows that stage's "no rounds" note. The live window and a finished search both go through `buildHistory`: the live one from the status's `rounds`, a finished one from `GET /api/results/<id>/rounds` (`whatif-runner.md`). Tests: `tools/test/whatif-history.mjs`. A stage with no finished round yet but a provisional record (`buildHistory(records, { firstLook })`) is given `firstLook: true`, `rounds: 0` and that record's pools, so the first look is a chart of bars only; a stage with finished rounds ignores the provisional record. A stage is drawn running only while the progress' stage names it and its end mark (stageEnded) does not: an ended race stage stays the progress' stage through what follows under its name (its pick checks, the base runs of a search that picked nothing), and its line then reads like its Done row (whatIfDrawChartsNow in main.js). To beat: it stays in `buildHistory` (the core publishes no figure on the table's scale; `line` in `rounds.mjs` is the cost-scaled search bound).
3. `src/whatif/chartModel.mjs`, what one pool's chart draws (pure, tested): `poolModel(pool, { hover, flying })` gives `mode` (`empty`: no row has a figure, so no canvas and the note "no figures yet" (`chart.noFigures`), or, on a stage that has ended, "no change reached the runs a figure needs" (`chart.noFiguresEnded`; which stages have ended is `endedStages` in `chartView.mjs`: every stage but the running one while the search runs, every stage of a finished search, every stage but the last of a stopped one; test `tools/test/whatif-chart-note.mjs`); `bars`: only the latest round has figures, so bars and no lines; `lines`), the lines (one per candidate that was among the leaders, worst first so the best are on top; `x` is the round, `y` the table's sorted figure: the buyer's gain, or the payback of a paid pool with the axis reversed so up is better, and the axis title says it), the column of the latest round's ± bars at the right edge (in table order; `columnLayout` places them past the last round), the axis (`fitAxis`: it fits the latest round's bars; 0 and the to-beat level are included only when within one span of them) and the colours (`rankColor`, by the latest rank, thin lines; a line that left the top 10 or was set aside is grey and dashed, and continues if the candidate comes back). The ± band is drawn only for the top 3 (`BAND_TOP`) and the hovered line. A figure or ± under 4 seeds is never drawn (`hasFigure`). A paid pool's point with an open high end (`openHigh`) gets a band whose high is Infinity, drawn to the top edge. Test: `tools/test/whatif-chart-model.mjs`.
4. `src/whatif/chartView.mjs`, the drawing: `createChartHost(container, opts)` keeps one block per stage and pool (a stage line, a pool line, one Chart.js canvas that is never recreated while its pool is shown); `update(history, { running, flying, endedByUser })`, `clear()`, `redraw()`. Chart.js is the page's global; the shared `errorBarsPlugin` draws the bars (the column bars are one-point datasets with `errorBars`, the bands come from `errorBand`), and a small plugin draws the 0 line, the to-beat line, the separator before the column and the pulse. The y axis slides to its new fit over 350 ms. Hover isolates one line (the others dim to alpha 0.18) and calls `onHover(id)`; Chart.js replays its last pointer event after every `update()`, so the host remembers the native event the pointer left with and ignores that replay (the pointer leaving the canvas or its box clears the isolation). A click calls `onPick(id)`. A stage ended by Skip before round 1 shows a note and no canvas (`chart.noRounds`); a stage ended by Accept after round N draws its chart; a finished step keeps its chart. A candidate with a run in flight (`progress.inFlight.ids`, the running stage only) has a pulse ring on its bar, and the running stage's line says "N runs in flight" (`progress.inFlight.runs`, `renderParts`). Strings `common:whatIf.chart.*` and `progress.inFlight*` (pt and zh are not checked by a native speaker). A level line's label (`levelsPlugin`) sits above its line, or under it when it would overlap a label already drawn or leave the chart area (`levelLabelY`, `LABEL_H`), so the "to beat" label never covers the 0 label.
5. `src/main.js`: `#whatIfCharts` (above `#whatIfRounds`). The history is the status's `rounds` (records newer than `since`, accumulated in `whatIf.rounds`) while the search runs, and, for a finished or earlier search (or when the window opened on it), one `GET /api/results/<id>/rounds` (`API.rounds`, `whatIfLoadRounds`, once per search id), both through `buildHistory`. `whatIfDrawCharts` wraps the drawing in a try/catch (a fault in the chart is logged as "What-if chart:" and never read as "the runner is gone"). Hover marks the table row of the candidate (`tr[data-cand]`, class `whatif-hot`; the id is kept in `whatIf.hotCand` and the mark put back after each redraw of the table, which happens every poll); a click scrolls to that row.
6. Stage names and the moments that touch the chart: a block's stage line uses `stageLabel` (`panel.mjs`, the one function that also names the result's ended-by-you lines): Best foods, Best drinks, Change 1 for the screen, Change N + 1 for `greedy step N`, and "<that stage>, budget groups" for the race of a set's budget groups (`screen groups`, `greedy step N groups`). "N runs in flight" (`progress.inFlight.runs`) is a part of the running race row's Details cell (`renderParts`). A stage ended by Skip before its first round finished has no round record, so it gets the no-rounds note (`result.endedByUser[stage] === 0`) and no canvas; Accept or Skip after round N keeps the chart of its N rounds. Stop then Resume keeps the window's `whatIf.rounds` (same search id); the resumed run replays its stages from round 1 and `lastRuns` keeps each stage's last run. A stopped search shown from "Earlier searches" reads its rounds the same way as a finished one (`GET /api/results/<id>/rounds` answers for any saved report, `savedReport`). The check stage (the confirmation of the picks) is not a race and writes no round record, so it draws no chart.

Best foods and Best drinks: `result.best.<kind>.<player>.items` are in slot order and each carries its `slot`; `same: true` marks the item the player has in that slot now (a food also needs an unchanged trigger), which the table greys; `empty` lists the slots empty now and after (a greyed `empty`), `slots` the slot count. A so-far entry (`soFar`) also carries `notFirst: true` when the search's pick (best ranked by its own search runs) is not the first non-ruled-out row of its pool in the rounds table (ordered by the fresh runs); the table then has one line under it (`whatIf.result.pickNote`). How the pick is chosen is unchanged.

A gain and its error are written in one cell, "value ± error", in every table (Chosen changes, Each change alone, the confirmation table, Best foods and drinks, the rounds tables) and in the report text (`result.md`, the skill levels and the charm report); there is no separate "± error" column. The Best tables use the rounds table helper (`pm`: `≈ 0 ± X`, greyed, when the range reaches 0; under 4 seeds the cell is the dash of `pmCell`, no figure); the other tables keep the "no change" word rule (inside one error or under the size floor). A row whose shared loot gain range (profit goal) is entirely below 0 has the status `loses` ("party loses loot", long wording as its tooltip; `rowShape` in `tools/whatif/core.mjs`), which comes before `zero` and the confirmed-style statuses; it changes no choice of the search, and the row is not greyed.
