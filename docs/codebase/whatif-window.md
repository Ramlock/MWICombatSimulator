# The What-if window

The page's What-if window runs the what-if optimizer (`tools/whatif/optimize.mjs`) through the local what-if runner: a program on the user's own PC that serves this page and runs the search at low priority on every core. The public website has no runner, so there the same button opens the window in its "get the runner" state (below).

## Two states

`initWhatIf` (`src/main.js`) asks `/api/version`. When no runner answers, `whatIfShowGetRunner` shows the button and puts `whatif-norunner` on `#whatIfModal`; the CSS in `index.html` then shows only `#whatIfGetRunner` (one paragraph on why, the download link, four steps: start, SmartScreen, the black window, the What-if button) and hides the search; with a runner the class is absent and that pane is hidden. The link target is `RUNNER_DOWNLOAD_URL` (`src/whatif/runnerDownload.mjs`), the one constant. Strings: `common:whatIf.get.*` in en, pt and zh (pt and zh not checked by a native speaker; the pt SmartScreen names are Microsoft's own). The zip itself: `runner-zip.md`. Test: `tools/test/whatif-get-runner-page.mjs`.

## Layout: the rule and its parts

The window follows one rule: **no fact travels inside a sentence.** A number, a state, a name or a count is a table cell or a chip (`span.whatif-chip`; a labelled one holds `span.whatif-chip-k` then the value); a sentence is allowed only as a tooltip, behind a help mark, or as a warning that changes what the result means (`.whatif-callout`: the base loses money, an error). The helpers are in `panel.mjs`: `chip(html, cls, tip)`, `help(tip)` (a `span.whatif-help`, "?", `tabindex=0`, its sentence in `data-tip`; the CSS in `index.html` shows it on hover and on keyboard focus, no tooltip JS), `fig(label, value)` (a small labelled figure, `.whatif-fig`), `arrowed(html)` (a change text split into `.whatif-from` → `.whatif-to`). Dark only; table heads have a background, rows are zebra, numbers are right-aligned in tabular figures.

1. **State chip:** `#whatIfState` in the title bar (`whatIfSetState`, `main.js`): idle, starting, searching, stopping, stopped by you, done, error (`whatIf.stateChip.*`).
2. **Setup and result are separate areas.** The setup form is `#whatIfSetup` (two columns: Goal, Players, then Zone and Tier on one row on the left; What to search, the payback limit and the budget per player on the right). Once a search runs or a result shows, `whatIfShowSetup` (`main.js`) hides it and shows `#whatIfSummary`, one bar of chips (`#whatIfSummaryChips`: goal, zone and tier, each ticked player's budget or `budgetPlaceholder` ("no limit"), the payback limit (`paybackChip`, `days`), the ticked kinds of change) with an "Edit setup" button (`#buttonWhatIfEditSetup`, `whatIf.setupOpen`, text `editSetup` / `hideSetup`). Idle with no result, the form is open and the bar hidden. Goal and zone show once: in the bar, or in the open form; the result's own chip row holds only the base profit. The Start / Stop row (`#whatIfStartRow`, `.whatif-toolbar`) sits under both.
3. **What to search** (`#whatIfLevers`): a compact grid of ticks, each a short bold name (`lever.<id>.name`) and a help mark holding its sentence (`lever.<id>.desc`); a tick that cannot be used shows the chip "needs export" (`needsExport`, CSS `:has(input:disabled)::after` from `data-off`). The players' help mark (`choicesNote`, "Copied from the page when this window opens…") sits beside the Players heading (`data-whatif-tip`, filled by `whatIfTips`).
4. **Pending states:** Start shows "Starting…" and Stop "Stopping…" (disabled) at once; a pressed Skip or Accept gets `whatif-pending` and reads "Skipping…" / "Accepting…" (`progress.stageSkipping`, `stageAccepting`), Accept's tooltip "Finishing the current round". Stop is an outlined red button.
5. **Left-out counts:** under the answer, one row of amber chip buttons, one per limit that left changes out ("3 over the payback limit", "1 over budget", "1 unknown cost": `result.leftOutPayback`, `leftOutBudget`, `leftOutApart`, singular `…One`, the list's note as title); each opens its list and See details together (`data-whatif-more="<list id> whatIfDetails"`). Old prices are an amber chip (`result.pricesChip`, the full `pricesLine` sentence as its title).

## Files

1. `src/whatif/panel.mjs`: the window's logic, without the DOM, tested in Node: the request body, the progress line, the result tables, which slots an Apply writes, and where the page's setup differs from the search's. It computes no figure: every number shown is a field of the result or of the progress, rendered with `numberHtml` (`src/numberFormat.js`), so the raw value rides along.
2. `src/whatif/applyOps.mjs`: the ops that edit a setup (enhance, equip, food, drink, ability, abilityLevel, abilityOrder, unequip, level, house, trigger). Shared: `tools/whatif/variants.mjs` re-exports it for the Node tools.
3. `src/main.js`, region "What-if window": the DOM side. `initWhatIf` asks `/api/version`; only when it answers is the button shown and the window wired. `whatIfSlots` saves the current tab first (`savePreviousPlayer`), then reads one slot per real player tab (`#playerTab .nav-link`, so a three-tab page gives three) with their names (`whatIfPlayerNames`: the character name the slot's import carried, else the tab's text; the rule is `shownNames` in `src/slotNames.mjs`). Every import path (Solo, All players, the per-player boxes) ends in `applySlotNames` (`src/main.js`), which writes a slot's unique name onto its tab once per name (a tab the player edited stays until the slot's name changes) and refreshes the Select Players labels; a name two slots share, or none, leaves the tab's text. Tests: `tools/test/slot-names.mjs`, `tools/test/slot-names-page.mjs`. With `onlySelected` it reads the window's own tick boxes, never the page's.
   The window has its own choices (`whatIfRenderChoices`): a tick box per player tab (`#whatIfPlayers`), a zone selector (`#selectWhatIfZone`) and a tier selector (`#selectWhatIfTier`). Each time the window opens (`show.bs.modal`) they are copied from the page: the players ticked on the page (none ticked on the page means none ticked here, the "tick at least one player" message shows, and the user ticks players in the window), and the page's zone and tier. The two selectors are built from the page's `#selectZone` and `#selectDifficulty` options (same values, order and names; an option keeps the page's `data-i18n` key, so the page's own language switch renames it). Edits in the window never write to the page. The budget fields (each starts empty with the placeholder `whatIf.budgetPlaceholder`; empty or 0 is sent as 0 and means no limit, `whatIfBudgetValue` in `src/main.js`; the payback limit field starts at 0, no limit), the message (shown whenever no player is ticked in the window, cleared when one is) and the request (`slots`, `options.zone`, `options.tier`) follow the window's controls. A language change redraws the names and keeps the window's picks. Apply and the "where the page differs" warning still read the page (`whatIfSlots(false)`).
   Layout: the setup form is two columns (`.whatif-col`, 5/12 and 7/12), each a flex column of sections with one gap (`--whatif-gap`, 12 px); the Players heading carries its help mark. Zone and Tier share one row (`.row.gx-2`, two `col-6` input groups, each half the left column, the label inside the group). The budget per player (heading `whatIf.budgets`, "Budget per player (coin, empty or 0 = no limit)") sits in the right column under the payback limit: `#whatIfBudgets` is one row of five equal cells (`.whatif-pcell`, `repeat(5, minmax(0, 1fr))`), one per ticked player, each the player's name (ellipsis), the budget field and the export mark under it. Five players fit at 1920x1080, 1500x900 and 1100x900 with no horizontal scroll; the page test measures it.
   Character export per player: there is no paste field. A party import from userscript 0.9.3 or later carries the own player's `inventory` and `learnedAbilities`, and so does a Tracker character export pasted into one player's own import field (Group Combat tab, "Player N import"): `doGroupImport` (`main.js`) sends the all-players field, or the per-player fields when it is empty, through the one `splitGroupImport`; they are taken out of the slot (the sim slot is as an import without them gives) and kept, through `whatIfKeepExport` (`whatIfKeepImportedExports`, `main.js`), in `localStorage` under `whatIfExport:<the name the window shows that player by>` (`exportKey`). `parseExport` (`panel.mjs`) validates it (a JSON object with an `inventory` or `learnedAbilities` array); a valid one replaces any kept one, a bad one is not kept. It is kept across window opens and page reloads, and there is no clear control; an import without those fields keeps nothing and clears nothing. Under each player's budget a chip (`.whatif-pstatus`, `data-export-status`, the whole text as its title) says where that player's owned items and abilities come from (`exportStatus`): "items and abilities: Tracker import" (`exportFromTracker`) when an export is kept, else "items and abilities: none" (`exportFromNone`). Items you own and Abilities stay greyed while no ticked player has one (`whatIfApplyExportLevers`, note `exportLeverOff` behind their help mark). The request carries `export: { "<player name>": <export> }` for every ticked player with a kept export, and no `export` when none. The storage is the data: nothing is read back from displayed text. Apply writes the new slot JSON into `playerDataMap` and reloads the screen (`updateNextPlayer`, `updateState`, `updateUI`), as an import does.
4. `index.html`: the button (hidden by default, beside Import/Export), the `whatIfModal` window and its styles (in Dark Mode the progress bar has a dark track with a border and a blue fill, so an empty bar reads as empty).
5. Strings: `common:whatIf.*` in `locales/en`, `pt` and `zh`.

## The runner's interface (JSON over HTTP, same address as the page)

1. `GET /api/version`: `{ runner, engine }`.
2. `POST /api/search`: `{ setups, options: { zone, tier, marketplace }, goal: "profit" | "exp", budgets: { "<player>": coin }, levers: [...], players }` answers `{ id }`. `levers` is the ticked lever ids, as the window lists them (`LEVERS` in `panel.mjs`: equip, foods, drinks, owned, abilities, order, triggers, houses; Foods and Drinks are two boxes, each ticked by default, each with its own name and description in en, pt and zh; the pt and zh strings of the two are not checked by a native speaker). An old request that says `consumables` is read as both by the optimizer. `marketplace` is the game's `marketplace.json` body, fetched when Start is pressed by `fetchMarketplace` (`src/marketplace.mjs`, shared with the page's Get Prices button; `searchRequest` in `panel.mjs`); when the fetch fails the window says so and starts no search (no older snapshot is used in its place); a second search while one runs is refused with the running `id`, and the window then follows that one.
3. `GET /api/search/<id>?since=<n>`: `{ state: "running" | "stopped" | "done" | "error", progress: { stage, candidatesLeft, runsDone, runsPlanned, secondsPerRun, etaSeconds }, error?, result?, partial?, partialVersion?, round?, roundVersion? }`. The window polls it every second while it runs, with `since` = the highest `partialVersion` or `roundVersion` it has drawn (`whatIf.partialVersion`, 0 for a new watch; one counter serves both); a running search carries `partial` (the report so far, the same shape as `result`) and `round` (the latest search-round record) each only when newer.
4. `POST /api/search/<id>/stop`: stops a running search; the same request on a stopped one resumes it.
5. `GET /api/results` (newest first, `{ id, finished, goal, players }`) and `GET /api/results/<id>` (one result).
6. `POST /api/search/<id>/done` with body `{ mode: 'accept' | 'skip' }` (`400` for any other): the two stage buttons, "Accept current winner" and "Skip this stage" (no stage name in the button). The runner sends `{ done: mode }` over the IPC (beside `stop`), `optimize.mjs` sets `stop.done` to the mode; the core's `race()` clears it at its start. **Accept** locks, in each pool without a lock (a player's, or the stage's single one), the best live leader whose figure the window shows as a figure (`acceptTakes` in `rounds.mjs`, fed by `gainOf`, which reads `showsFigure` from `src/whatif/figure.mjs`, the one helper the window shares: at least 4 reading seeds and a range that does not reach 0, so not "≈ 0"; a mean above 0, never a time-only lever, never a candidate the elimination rule put out), and ends the stage after the round in flight (after that round's record is published) through the one end path. The pick is taken as it is: **no pick check** (no `confirmPick`, no fresh seeds) and it enters the baseline directly (a greedy step, or a foods/drinks filling); the report marks it `acceptedAsIs: true` (the steps row, `result.best[kind][player]`) and shows "accepted as is" beside it (en/pt/zh); it is never in `notConfirmed`. A pool that had already locked keeps its pick, checked as usual. `result.endedByUser[stage] = round` (the rounds the stage finished: the report says "ended by you after round N"). **Skip** ends the stage at once: in `ensure()` (`core.mjs`) the lanes take no new runs (`skippable`; the runs already going finish and are stored, no `pool.kill()`), the race returns the earlier round's leaders (none in round 1) with no new lock, keeps the locks it already had, and the search carries on to the next stage (`result.incomplete` and `result.stoppedBy` stay unset); `endedByUser[stage]` is the number of rounds the stage finished, **0 when Skip came before the first round finished** (any reader of `endedByUser` tests `!== undefined`, not truthiness). `result.endedBySkip[stage] = true` marks a Skip (absent for an Accept): the report and the Best heading say "ended by you during round N, its finished runs kept" with N = `endedByUser` + 1 (so 1 for a Skip pressed in round 1; `endedText` in `panel.mjs`, `endedMd` in `core.mjs`, string `result.endedByUserDuring`), an Accept says "ended by you after round N". The ended stage's own line says "round N · ended by you" instead of "round N finished" (`progress.stageSkipped` from `endStage` → the row's `skipped` in `progress.mjs` → `rounds.roundSkipped`). The core publishes how many pools Accept would take each round (`progress.stageAcceptable`, the part's `acceptable`), and the window draws "Accept current winner" only while that is above 0 (so "no change leads", or a figure not yet shown, gives Skip alone); the buttons are drawn only on the race stage running now (`data-whatif-done="accept"` / `"skip"`, `data-whatif-part=<kind>:<index>`, in the last cell of the stage's row). After a press `main.js` keeps `whatIf.pressed` and the window draws both buttons disabled until the stage's row stops running; The pressed button shows its pending state (Layout, item 4): `whatif-pending`, "Accepting…" or "Skipping…", Accept's tooltip `progress.stageFinishing`. The progress redraw (`whatIfDrawProgress`, `main.js`) reuses an unchanged button node, so a poll does not replace the button under the pointer (no hover flicker). A command-line run has none. `409` when nothing runs.

Status column of the rounds table: one or two words (`clear gain`, `no clear change yet`, `party loses loot`, `still measuring`, `set aside`; `ruled out` is not listed); counts and internal states are the cell's tooltip (`rounds.status.<key>Tip`). Best foods / drinks while the stage runs: a leader without a clear gain (core flag `unclear`, plus `loses`; the entry is the final's `unchanged` form with the leader kept as `candidate`) shows the player's current items greyed, a dash for the figures, and the status with the candidate and its figures as tooltip. Players in every list follow the party's own order (`players`): `poolSorter` in `rounds.mjs` for the pools, `partyEntries` / `inParty` in `core.mjs` for `result.best`, the budgets and the per-player confirmation lines.

## The progress block

`renderProgress` (`panel.mjs`) draws the stage list from `progress.parts` (`renderParts`; `whatif-runner.md`, "Progress parts") as one table, output only. Its head is the title "Search progress" (`progress.title`) with three labelled figures beside it: Stage K / N (K = the running row's place from 1, N = the rows shown, placeholders included), Seconds per run (two decimals) and elapsed (h:mm:ss). Columns (`progress.col.*`): mark, Stage, State, Round, Runs, Sim. hours, In the running, Set aside, Ruled out, and the buttons. One row per part (`tr.whatif-part.whatif-part-<state>`, `data-kind`, `data-state`): the mark (`✓` done, `▶` running, `○` waiting, `■` halted, `–` not run), the bold stage name, a state chip (`whatif-st-<state>`, text `progress.st.*`: Done, Running, Waiting, Stopped, Not run, Ended by you, Searching, Checking leaders, Checking picks; the sentence it stands for, such as the pick check's runs, why a part never ran, the time left or the rounds to separate the leaders, is the chip's title), the round, the runs (a race's runs; any other part "done / planned", with a 4 px bar while it runs), the simulated hours and the three contention counts. A count of 0 is an empty cell; a waiting row is dim and has no bar. Names: `Best foods`, `Best drinks`, `Change 1` (kind `screen`), `Re-checking each chosen change` (kind `picks`), `Change <k+1>` (`stepLabel`), `More changes: up to <stepsLeft> more`, `Final check of the whole set`; the long names are a short name with their sentence behind a help mark: `Changes, one at a time` (`progress.partStepsShort`; help `partSteps`, "…up to <maxSteps>, stops when none helps") and the waiting final check (help `partConfirmationWaiting`). A picks part whose every pick was left out in a race reads "None confirmed (left out: N)" in its chip title. Only a running search has a running row: the part running when the search stopped is drawn halted, its figures kept, no buttons. A race stage that has ended is a done row at once, with the last round record's counts. An error is a red callout under the table. A progress with no `parts` (an older search) draws the single line as before. Strings `common:whatIf.progress.*` in en, pt and zh. Styles `.whatif-part*`, `.whatif-parts-table` in `index.html`.

## What the window reads from a result

1. Top: the answer first, under its heading (`result.answer`, "All chosen changes together, checked on fresh runs", drawn only with a confirmation): the per-player table from `confirmation` (Player, Gain per day as `value ± error`, Pays back in (days); the party row "Party (the shared loot, per user)" with its Cost; `buyerByPlayer` per player; a dash when the payback is none or 0; a result without `buyerByPlayer` shows its party payback and a run-the-search-again line instead), then the left-out chips (Layout, item 5), then `best` (item 9), then Chosen changes. `apart` (unknown cost) and `overBudget` (priced above its player's budget) are listed only under See details, as tables (item 5). `options.pricesTimestamp` / `pricesSource`: the old-prices chip (`pricesLine` in `panel.mjs` decides when: a market snapshot 24 hours old or more, or the simulator's own saved snapshot).
2. Each row of `steps` and `singles`: `player`, `desc`, `sharedGainPerUser` and `sharedSePerUser` (the party gain per player per day and its error), `buyerNet` and `buyerNetSe` (the gain of the player who pays, per day, and its error), `cost`, `costBound: "upper"` (printed as "≤" on the cost and the payback), `payback` (the buyer's payback; none or a net of 0 or below shows "—", except that a cost of exactly 0 shows "no cost, nothing to pay back", `whatIf.result.noCost`; the same words stand in a player's confirmation line when his `runningSpend` is 0, and in `result.md`), `costPath` and `note` (How it is bought: the path as a chip, the note as its title, without the "; upper bound (XP inside the level unknown)" caveat, which the footnote under the table keeps), `accepted` (a single that is not is grey and sits behind one "Show N more not accepted" toggle), `ops`; a single also `lastStage`. Both tables (Chosen changes, Each change alone) read: [# and] Player, Change, Shared loot gain per user, ± error, Buyer's gain, ± error, Cost, Payback days, How it is bought, Apply. A result with no `buyerNet` (an older one) shows a dash in both buyer cells, and on an EXP goal they are dashes too. The old Spent, Stage, Shared gain and Own supplies columns, the "spent of budget" line and the helps-the-party table are gone; a row of an older result flagged `helpsParty: true` shows as an ordinary row. The search accepts a change when one of the party gain and the buyer's net is above 0 by at least z errors and the other is not below -(z/2) errors (`acceptBoth`, `whatif-runner.md`); the party gain is the group's shared loot gain per player, before anyone's own food and drink. A gain figure (party or buyer, in both tables, the confirmation line and each player's confirmation line) whose absolute value is less than one error shows the words "no change" (`whatIf.result.noChange`) with the real value as the hover title ("+288K ± 242K"), the error cell next to it shows "—" with the same title; one error or more shows the number. The Change column of Each change alone is 50em wide and wraps (`index.html`), so at 1920x1080 the table has no horizontal bar even for a food change of about 230 characters; the page test measures it at 1920, 1600 and 1366 wide.
3. Game names: the runner writes each `desc` with the game's internal ids (the last part of a hrid, e.g. `pathseeker_boots_refined`, `feet`). The window shows names instead, in the page's current language, in the steps, the singles, the over-budget list and the unknown-cost list (`localizeDesc` in `panel.mjs`; output only, the result keeps the ids and Apply reads the ops). The names are the game bundle's own tables, read as the page's `data-i18n` lookups read them (`i18next.getResourceBundle`, with English as the fallback, `namesFrom`): `itemNames` (a refined item has its own entry with the page's "★"), `abilityNames`, `skillNames`, `equipmentTypeNames` (the slot), `combatTriggerDependencyNames` and `combatTriggerConditionNames`. A trigger desc (`<owner> trigger: <terms>`) reads its terms as dependency and condition (a condition id can equal an ability id with a different name); a house room is written as its English name and is looked up by that name in `houseRoomNames`. The player name leading a desc is never translated; where it is the row's own player (a step or single has a Player column, an over-budget row a "<player>," lead of its own) it is left off the shown desc, so the player shows once; the unknown-cost list has no player column, so its descs keep the lead. An id with no name stays as it is. The language-change handler redraws the result, so the names follow. Not covered: `costPath` and `note` are the runner's text.
   The "where the page differs" warning (`renderDiff`, `diffLabel`, `hridsToNames` in `panel.mjs`) shows names the same way, through the same lookup (`namesFrom`; its tables also hold `houseRoomNames` and `combatTriggerComparatorNames` for it), output only: `diffSetups` and its differences stay raw. The ids a difference holds: in the field, a skill level (`magicLevel`, shown "<skill name> level" from `skillNames` and the `diff.level` string), a slot (`feet`, an `equipmentTypeNames` entry), a house room hrid, and the owner hrid of a `triggers <hrid>` field (an item or an ability); in the values, an item hrid with its enhancement (`/items/x +12`), a food or drink item hrid, an ability hrid with its level, and the hrids inside a trigger's terms, which are shown as JSON (dependency, condition and comparator). An hrid is read by its kind (`/items/`, `/abilities/`, ...) and replaced by its name; one with no name, or of a kind with no table, stays as it is. The words `food 1`, `drink 1`, `ability 1`, `triggers`, `player`, `present`, `absent` and the JSON keys are the code's own words, not ids, and stay.
4. Base profit: the result's own chip row holds one labelled chip, "base party profit <figure>" with "per user per day" as its title (`zoneBase` in `panel.mjs`: `basePerUser`, profit goal only, none when the result holds no zone); goal, zone and tier show in the summary bar (Layout, item 2), not here. The summary bar takes the goal and zone names from the locale (`whatIf.goal.<value>`, `actionNames.<zone>`), not from the selects' text, so it follows a language change at once. When `basePerUser` is below 0 an amber callout says the party loses money at base here, so a gain means losing less.
5. Folds: every detail list is one line (`foldLine` in `panel.mjs`, class `whatif-fold-line`): its bold label, a count chip (`whatif-chip-n`), a help mark holding the list's note, and, at the right end, a plain Show / Hide toggle (`result.dominatedShow` / `dominatedHide`; the count is the chip, never in the toggle). Behind it the list is a table, one fact per column (`detailTable`, class `whatif-list`): Priced, over budget (Player, Change, Cost), Pays back too slowly (Player, Change, Cost, Payback days; "no gain to pay it back" as a chip), Left out in the race and Not confirmed (Player, Change, Stage as a chip whose title says readings in the race or fresh runs, Shared loot gain per user, Buyer's gain), Unknown cost, not ranked (Change, the reason as a chip). The count lines (`countList`) have a fixed label and the old sentence in the help mark: Swaps skipped (`result.dominatedK`; Player, Change), Other style only (`otherStyleK`), Players skipped (`skippedNoExportK`; the lever as a chip, the players as chips). Over them all, one "See details" toggle (`result.detailsShow` / `detailsHide`), closed by default, opens `#whatIfDetails`, which holds, each still closed on its own: Each change alone (and its not-shown line), the lists above, and the "≤ upper bound" chip with its help mark. Its `data-whatif-more` lists two ids, `whatIfDetails whatIfRounds`: the click handler (`main.js`) opens or closes every body a toggle lists, the first deciding, so the search rounds open and close with the details; `whatIfShowResult` hides `#whatIfRounds` while such a toggle is closed and shows it when there is no result yet. Outside it, always in view: the answer, the left-out chips, Best foods and drinks, Chosen changes with their Apply buttons. A redraw keeps the folds that were open.
5a. Fresh readings and the picks not confirmed (the pick check, `whatif-runner.md`): a step with a `fresh` reading shows it on a second line inside its gain cells: the party gain cell shows "fresh <gain> ± <error>, <seeds> seeds" from `fresh.gainPerUser`, `sePerUser` and `seeds`, the buyer's gain cell the same from `buyerNet` and `buyerNetSe` (`freshLine` in `panel.mjs`, class `whatif-fresh`: small and muted, no new column, the error cells and the existing columns unchanged; a step without a reading has no second line). A line under the steps table (`result.freshLegend`) says what the second line is. An accepted pick (`acceptedAsIs`) has no fresh reading and is never in `notConfirmed`; its steps-table cell and its Best-table cell carry the small mark `data-accepted-as-is` (`result.acceptedAsIs`). Every list the window draws as a table is drawn by one helper (`listTable` in `panel.mjs`): with no row it is ONE grey line "None." (`result.none`, `data-none`), never a header row over nothing or a label of its own; "Each change alone" with nothing accepted is that line, its grey rows kept behind their toggle in a hidden table of their own (header included); an empty rounds-table pool is the same line, without its title (a run of empty pools is one line). `notConfirmed` (the picks the search left out) is a closed list (item 5, `data-whatif-more="whatIfNotConfirmed"`), one row per pick: Player, Change, the Stage chip `<at>`, the party gain and the buyer's gain (a dash on an EXP goal). `<at>` is "at step <n>" for a pick, "in the foods" for a food filling that failed its check and "in the drinks" for a drink filling (`notConfirmedAtStep`, `notConfirmedAtFood`, `notConfirmedAtDrink`, chosen by the row's `kind`; a filling has `step: null`). Nothing when absent or empty (an older result). Output only.
5b. One row per setting in "Each change alone": two rows that change the same setting (a trigger's value 4550 and its value 6400) are alternatives, only one can be taken, so the core (`singleRows` in `core.mjs`, through `hideSettingAlternatives` in `tools/whatif/alternatives.mjs`) keeps the first in the search's own order (accepted rows first, then `rankEst`: for free rows the larger buyer's gain, then the larger party gain) and sets `hiddenAlt: true` on the others; they stay in `result.singles` (and the file), keep their indexes (the apply keys `single:<i>` are not renumbered), and the window (`hiddenRow` in `panel.mjs`) draws them nowhere, neither in the table nor behind the grey toggle, and counts them in no figure (`result.md` skips them too). The setting is the key `settingKey(ops)` from the ops' targets (`opTarget`): enhance, equip and unequip share player + slot; trigger player + `hrid`; house player + room; ability player + slot index (or the replaced ability); abilityLevel the same, as its own kind; abilityOrder player; level player + skill; food and drink player + slot; a change of several ops keys on all its targets together (sorted), so it groups only with a change of exactly the same targets. Paid rows are grouped too (the owner's ruling: one row for paid as well, the best-ranked by gain per price shows, the rest stay in the file): equipment +5 and +6 of one slot, a house room +1 and +2; a free row and a paid row of one setting group too, the free one first. The constant `GROUP_PAID` (`alternatives.mjs`, on) is the one switch; set to false it leaves paid rows alone. "Chosen changes", the steps and "Apply 1 to N" read `result.steps`, not `singles`, so they are unaffected. The food rows are one case of the same function (`hideFoodRows` in `foodfill.mjs` calls `hideAlternatives` keyed by player, flag `hiddenFood`). Tests: `tools/test/whatif-alternatives.mjs` (the key per op kind, the helper, the foods case), the block "One row per setting" in `tools/test/whatif-panel.mjs`, one check in `tools/test/whatif-synthetic.mjs`.
5c. "Each change alone" starts collapsed: its fold line (label, count chip, help mark, Show / Hide) stays in view and opens a hidden body (`#whatIfEachChange`) holding the whole table, the grey rows and their own toggle included. It is the same fold every closed list uses (`data-whatif-more` toggle, `.whatif-more` body, handler in `main.js`, open folds kept across a running report), so there is one collapse code path.
6. Skipped swaps: a non-empty `dominated` group (the equip swaps never offered because they are no better on any stat, `whatif-runner.md`) is the count line "Swaps skipped" with its count chip, the sentence "N swaps skipped (no better on any stat)" in its help mark, and its table (Player, Change through `localizeDesc`) closed behind Show / Hide (`data-whatif-more="whatIfDominated"`). The `otherStyle` group has the same fold right after it, "Other style only", id `whatIfOtherStyle`. An absent or empty group shows nothing.
7. Skipped for want of an export: a non-empty `skippedNoExport` group (`whatif-runner.md`) is the count line "Players skipped" (count = distinct players; the sentence "N players skipped by <lever names>" in its help mark), its table one row per lever (the lever name as a chip, its players as chips), closed behind Show / Hide (`data-whatif-more="whatIfSkippedNoExport"`). Nothing when absent or empty. Output only.
8. Every Apply button applies the best foods and drinks first, then its own change (`opsFor` in `panel.mjs`): `result.baselineOps` (the chosen food and drink fillings, with the trigger ops that came with them), then, for Apply on step n, the ops of steps 1 to n together, or, for Apply on a single, its own ops. The search measures every row on top of those foods and drinks, so one click gives the measured setup. A result without `baselineOps` (an older one) or with an empty one applies exactly what it applied before; a single that does not exist applies nothing. An op naming a player no tab is named after applies nothing and names that player. The button labels are unchanged ("Apply", "Apply 1 to n"): they do not say what they apply.

9. Best foods and drinks (`bestBlock` in `panel.mjs`, drawn by `renderResult` above "Chosen changes, in order", output only): from `result.best`, a "Best foods" and a "Best drinks" table (Player, one column per slot, Shared loot gain per user, Buyer's gain; the buyer's split "<loot> loot share + <amount> food and drink saved" is a help mark in the row), each item through the page's `itemNames`, a food's trigger in parentheses. A player the search left alone (`unchanged: true`, and not a so-far leader with a status) has no row. The title line (`div.whatif-h.whatif-chips`) carries the chips: "so far" while the stage runs, "Ended by you" with the ended sentence (`endedText`) in a help mark; when every player of a kind is unchanged the table is only that title with a "no change" chip (`data-best-none`). The sentence "Everything below is measured on top of these foods and drinks" (`bestBaseline`) is the help mark on the Chosen changes heading. A result with no `best`, or with both groups empty, shows nothing.

Two labels worth knowing (`panel.mjs`, `renderResult`). **Left out versus not confirmed:** `result.notConfirmed` entries carry `inRace: true` when the pick check on the race's own reading seeds refused a leader (`refute` in the foods and drinks stages, `refuteStep` in a greedy step; the change led a race at some point and had no run of its own); the window lists those under "Left out in the race" (`result.leftOut*`, its own closed list and count) and keeps "Not confirmed" (the old wording: the fresh runs did not confirm them) for the picks that were locked and then failed their own fresh runs (the foods and drinks confirmation, a step's `firstConfirmed`). **No pick:** the "Chosen changes" line of a result with no steps says "No change gains beyond its error within the budgets" only when every candidate was decided; when the screen or a greedy step ended on the round limit with changes still in the running (`result.endedByCap[stage] = { rounds, left }`, set in `race()`; the foods and drinks stages do not count) it says "The search reached its round limit (N rounds) with M changes still in the running; none was picked" (`result.noStepsCap`), and when the user ended such a stage (`result.endedByUser`) "You ended the search for changes before it picked one" (`result.noStepsUser`); the line carries `data-no-steps="cap" | "user" | "none"`. The rows below (Each change alone, the rounds table) are as before; the search picks the same. pt and zh wording is unchecked.

## The live report

`whatIfShowStatus` (`src/main.js`) draws `status.partial` while the search runs, through the same `renderResult(result, t, now, names, running)` (`panel.mjs`) as the final result, with `running = true`; the version is kept in `whatIf.partialVersion` and sent as `since` on the next poll (`API.status(id, since)`). What a running report shows differs from the final one only by what it leaves out and marks: a line at the top says the results fill in as the search goes and the rows shown are final (`whatIf.result.running`); the foods and drinks (`best`) show as soon as they arrive, each changed player's line with a second small muted line, the fresh reading that confirmed it (`whatIf.result.freshBest`, class `whatif-fresh`; `freshBestExp` on an EXP goal); the steps heading carries "so far" (`result.soFar`) and is not drawn until the first step; the "no steps" and "no singles" messages, the confirmation (the totals) and the baseline line (which waits until both groups are there) are not drawn while running; the Each change alone block is skipped when only the hidden food rows exist. A fold the user opened stays open when one running report replaces another (`whatIfShowResult` keeps them); the final result replaces the last snapshot and draws as before. A search that stops (or errors) with a report on screen keeps it, redrawn with `running = 'stopped'`: the top line then reads "Stopped: this is where the search got to" (`result.stoppedMark`). A language change redraws with the same `running` (`whatIf.resultRunning`). Strings in en, pt, zh; the pt and zh wording of the new keys is for a native reader.

## Search rounds

`renderRounds(round, t, names)` (`panel.mjs`) draws `status.round` (the runner's round record, `whatif-runner.md`, "The rounds search") into `#whatIfRounds`, a slot in `index.html` under `#whatIfResult`; output only (no button or input; the existing Stop button is the only control). `whatIfShowStatus` (`src/main.js`) sets `whatIf.round` from `status.round` while the search runs and from `status.result.round` when it is done, so the last round stays on screen after a stop; `whatIfWatch` clears it for a new watch. Contents: a head, the title "Search rounds" with labelled figures (Round, simulated hours, still in the running, set aside for now with its help mark, ruled out, Coverage), then, per pool (`free`, `paid`; the player's name is a chip in the pool heading in the foods and drinks stages, so no row repeats it), a title cell with chips (the owner, In the running N, Set aside N, "sorted by <column>, best first") and a help mark for the range width, and a `whatif-table` of the current leaders in that order: the change (a foods or drinks pool has one column per food or drink slot holding the new item of a slot the candidate changes and, in a slot it leaves alone, the player's current item greyed (`change.current`, the item in that slot now) or a greyed `empty` for a slot empty now and staying empty (`whatIf.rounds.slotEmpty`); any other pool has one Change column through `localizeDesc`, split from → to, with the player as a chip when the pool is not one player's; an unchanged trigger is the default and is not written), cost, hours simulated (one column; the search and fresh split is in its title), shared loot gain per user, buyer's gain (the two heads and their tooltips are `col.partyGain` / `col.buyerGain`, one definition `gainTh` for every table that has them), payback days, status as a chip, its counts as the chip's title (`still in the running`, `set aside for now`, `checked on fresh runs`, `ruled out`, `no clear change yet` with `not yet different from no change` as its tooltip; the Status column is 16em so none of these wraps at 1920 or 1366 wide, the `fresh runs: n, m more needed ...` sentence may take two lines). A progress row of a race stage reads `round <n> running` (`finished` once the stage is done); the first look's head reads `round <n> running` too. The sorted column is strictly best-first among the rows that have a figure. Figures are written `value ± half-width` by one helper (`fit` in `panel.mjs`, precision follows the half-width; a range spanning 0 reads `≈ 0 ± X`, the row is greyed and says "no clear change yet"); the window computes no figure. A figure rests on a number of seeds (`figureSeeds` in `src/whatif/figure.mjs`: the search's own seeds on a first-look row, the fresh reading seeds on any other); with fewer than 4 (`FIGURE_MIN_SEEDS`, the one place the number is written, read by the window and the core) the Shared loot gain and the Buyer's gain cells draw no number and no ±: a dim `—` with the hover text "Needs more runs before a figure can be shown" (`rounds.needsMoreRuns`; `pmCell` in `panel.mjs` is the one helper for both columns, in the rounds tables and the Best tables). At 4 seeds or more the cell draws `value ± range` as before, with the grey `≈ 0 ± X` and its row greying. The old `no range yet` string (`rounds.noRange`) is gone. Order (`sortRows` in `tools/whatif/core.mjs`, display only: no choice of the search reads the order of these rows; every row carries `built`, its place in the list the race was built from): while no row of a pool has 4 seeds the rows keep the order the candidates were built in, the pool's `sortedBy` is `null`, its `sortPending` names the column it will sort by, and the heading reads `sorted by <column> once figures exist` (`rounds.sortedByLater`), and no range width on the heading (`rangeWidth` and `rangeWidthPrev` are null: no figure under 4 seeds, so none from a build-order row) instead of `sorted by <column>, best first`; once some row has 4 seeds the rows with a figure sort best-first and the rows without follow in build order. The first-look table (`provisional`) follows the same rule through the same `sortRows`; its line `so far N of M candidates have a first figure` and the Status `still measuring` are unchanged. A leader with no fresh runs yet shows `no fresh runs yet`; with fewer than the minimum it shows how many more runs are needed. The Chinese and Portuguese wording of the new strings (`rounds.needsMoreRuns`, `rounds.sortedByLater`) is not checked by a native speaker. While round 1 runs, the record is provisional (`provisional: true`): the section shows `first look: so far N of M candidates have a first figure` and the rows with status `first`; the real table replaces it at the end of round 1. The "Unknown cost, not ranked" list starts collapsed. Strings `common:whatIf.rounds.*` in en, pt and zh (pt and zh for a native reader). Dark mode and one scroll axis come from the surrounding window (the section sets no overflow of its own).
