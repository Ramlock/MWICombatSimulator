# The What-if window

The page's What-if window runs the what-if optimizer (`tools/whatif/optimize.mjs`) through the local what-if runner: a program on the user's own PC that serves this page and runs the search at low priority on every core. The public website has no runner, so it shows no What-if button.

## Files

1. `src/whatif/panel.mjs`: the window's logic, without the DOM, tested in Node: the request body, the progress line, the result tables, which slots an Apply writes, and where the page's setup differs from the search's. It computes no figure: every number shown is a field of the result or of the progress, rendered with `numberHtml` (`src/numberFormat.js`), so the raw value rides along.
2. `src/whatif/applyOps.mjs`: the ops that edit a setup (enhance, equip, food, drink, ability, abilityLevel, abilityOrder, unequip, level, house, trigger). Shared: `tools/whatif/variants.mjs` re-exports it for the Node tools.
3. `src/main.js`, region "What-if window": the DOM side. `initWhatIf` asks `/api/version`; only when it answers is the button shown and the window wired. `whatIfSlots` saves the current tab first (`savePreviousPlayer`), then reads one slot per real player tab (`#playerTab .nav-link`, so a three-tab page gives three) with their tab names; with `onlySelected` it reads the window's own tick boxes, never the page's.
   The window has its own choices (`whatIfRenderChoices`): a tick box per player tab (`#whatIfPlayers`), a zone selector (`#selectWhatIfZone`) and a tier selector (`#selectWhatIfTier`). Each time the window opens (`show.bs.modal`) they are copied from the page: the players ticked on the page (none ticked on the page means none ticked here, the "tick at least one player" message shows, and the user ticks players in the window), and the page's zone and tier. The two selectors are built from the page's `#selectZone` and `#selectDifficulty` options (same values, order and names; an option keeps the page's `data-i18n` key, so the page's own language switch renames it). Edits in the window never write to the page. The budget rows, the message (shown whenever no player is ticked in the window, cleared when one is) and the request (`slots`, `options.zone`, `options.tier`) follow the window's controls. A language change redraws the names and keeps the window's picks. Apply and the "where the page differs" warning still read the page (`whatIfSlots(false)`).
   Layout: the left column (`.whatif-col`, 5/12) and the modal body are flex columns with one gap (`--whatif-gap`, 12 px) between every section (Goal, Players, Zone/Tier/note, Budgets, the button row, progress, result); Goal sits inline with its label like Zone and Tier (3/9). Each ticked player is one 31 px row (`.whatif-prow`, a grid of equal columns): name | budget | one-row paste field | status (one line, ellipsis, the whole text as its title). Five players and the Start search row fit at 1500x900 and 1100x900, the two columns' bottoms within 120 px; the page test measures it.
   Character export per player: in each ticked player's budget row, a one-row paste field (`textarea.whatif-export`, no resize) and a status beside it. A paste is validated by `parseExport` (`panel.mjs`): a JSON object with an `inventory` or `learnedAbilities` array (the userscript's "Copy character export"). A valid one is stored in `localStorage` under `whatIfExport:<player name>` (`exportKey`), replaces any kept one, and empties the box; it is kept across window opens and page reloads, and there is no clear control. A bad paste is not kept (it stays in the box and the status says so; an earlier kept export stays). The status (`exportStatus`): "kept (<the export's own name>)", "no export: skipped by <lever names>" (the ticked ones among Items you own, Abilities and New abilities; Ability levels never skip) or just "no export" when none of them is ticked, or "not a character export: not kept". The request carries `export: { "<player name>": <export> }` for every ticked player with a kept export, and no `export` when none. The storage and the box values are the data: nothing is read back from displayed text. Apply writes the new slot JSON into `playerDataMap` and reloads the screen (`updateNextPlayer`, `updateState`, `updateUI`), as an import does.
4. `index.html`: the button (hidden by default, beside Import/Export), the `whatIfModal` window and its styles (in Dark Mode the progress bar has a dark track with a border and a blue fill, so an empty bar reads as empty).
5. Strings: `common:whatIf.*` in `locales/en`, `pt` and `zh`.

## The runner's interface (JSON over HTTP, same address as the page)

1. `GET /api/version`: `{ runner, engine }`.
2. `POST /api/search`: `{ setups, options: { zone, tier, marketplace }, goal: "profit" | "exp", budgets: { "<player>": coin }, levers: [...], players }` answers `{ id }`. `marketplace` is the game's `marketplace.json` body, fetched when Start is pressed by `fetchMarketplace` (`src/marketplace.mjs`, shared with the page's Get Prices button; `searchRequest` in `panel.mjs`); when the fetch fails the window says so and starts no search (no older snapshot is used in its place); a second search while one runs is refused with the running `id`, and the window then follows that one.
3. `GET /api/search/<id>`: `{ state: "running" | "stopped" | "done" | "error", progress: { stage, candidatesLeft, runsDone, runsPlanned, secondsPerRun, etaSeconds }, error?, result? }`. The window polls it every second while it runs.
4. `POST /api/search/<id>/stop`: stops a running search; the same request on a stopped one resumes it.
5. `GET /api/results` (newest first, `{ id, finished, goal, players }`) and `GET /api/results/<id>` (one result).

## The progress block

`renderProgress` (`panel.mjs`) draws stacked rows from `progress.parts` (`renderParts`; `whatif-runner.md`, "Progress parts"), output only: a title `Running · part K of N` (K = the running row's place from 1, N = the number of rows shown, placeholders included, so it grows as greedy steps are added), one grid row per part (icon cell, bold label, bar, right text), and one small line `Seconds per run <n, two decimals> · elapsed <h:mm:ss>`. The icon cell is one column of equal width for every row, a plain text glyph (`✓` done, `▶` running with the text-form selector, `○` waiting; no colour emoji), so every label starts at the same left edge. Labels: `Screen`, `Halving <n>` with ` · <candidatesLeft> options left`, `Greedy steps: up to <maxSteps>, stops when none helps` (grey, until step 1 starts), `Greedy step <k>`, `More greedy steps: up to <stepsLeft> more` (grey), `Confirmation: only if a step is accepted` (grey) and `Confirmation` once it runs. Right text: `<done> / <planned> runs · <h:mm:ss> left` (running), `<planned> / <planned> runs · done`, `up to <runsUpTo> runs` (a waiting halving), nothing for the other grey rows. A done row has a green bar, the running row a blue one, a waiting row is grey. A stopped or finished search keeps its rows. A progress with no `parts` (an older search) draws the single line as before. Strings `common:whatIf.progress.*` in en, pt and zh (pt and zh not checked by a native speaker). Styles `.whatif-part*` in `index.html`.

## What the window reads from a result

1. Top: `goal`, `budgets` per player, `setups` (the base the search ran on), `confirmation` (`gainPerUser`, `sePerUser`, `cost`, `payback`), `apart` (unknown cost, listed, never ranked), `overBudget` (priced but above its player's budget: "Priced, over budget", player, change and cost, listed apart in the same style, never ranked), `options.pricesTimestamp` and `options.pricesSource` (one line: the snapshot's time and its age when shown, or that the simulator's own saved snapshot was used).
2. Each row of `steps` and `singles`: `player`, `desc`, `gainPerUser`, `sePerUser`, `cost`, `costBound: "upper"` (printed as "≤" on the cost, the payback, and that player's running spend from that step on), `payback` (none shows "—"), `accepted` (a single that is not is grey, and sits collapsed behind one "Show N more below 2 errors" toggle, N being the count of those rows), `ops`; a single also `lastStage`, `costPath`, `note`; a step also `runningSpend` per player.
3. Game names: the runner writes each `desc` with the game's internal ids (the last part of a hrid, e.g. `pathseeker_boots_refined`, `feet`). The window shows names instead, in the page's current language, in the steps, the singles, the over-budget list and the unknown-cost list (`localizeDesc` in `panel.mjs`; output only, the result keeps the ids and Apply reads the ops). The names are the game bundle's own tables, read as the page's `data-i18n` lookups read them (`i18next.getResourceBundle`, with English as the fallback, `namesFrom`): `itemNames` (a refined item has its own entry with the page's "★"), `abilityNames`, `skillNames`, `equipmentTypeNames` (the slot), `combatTriggerDependencyNames` and `combatTriggerConditionNames`. A trigger desc (`<owner> trigger: <terms>`) reads its terms as dependency and condition (a condition id can equal an ability id with a different name); a house room is written as its English name and is looked up by that name in `houseRoomNames`. The player name leading a desc is never translated; where it is the row's own player (a step or single has a Player column, an over-budget row a "<player>," lead of its own) it is left off the shown desc, so the player shows once; the unknown-cost list has no player column, so its descs keep the lead. An id with no name stays as it is. The language-change handler redraws the result, so the names follow. Not covered: `costPath` and `note` are the runner's text.
   The "where the page differs" warning (`renderDiff`, `diffLabel`, `hridsToNames` in `panel.mjs`) shows names the same way, through the same lookup (`namesFrom`; its tables also hold `houseRoomNames` and `combatTriggerComparatorNames` for it), output only: `diffSetups` and its differences stay raw. The ids a difference holds: in the field, a skill level (`magicLevel`, shown "<skill name> level" from `skillNames` and the `diff.level` string), a slot (`feet`, an `equipmentTypeNames` entry), a house room hrid, and the owner hrid of a `triggers <hrid>` field (an item or an ability); in the values, an item hrid with its enhancement (`/items/x +12`), a food or drink item hrid, an ability hrid with its level, and the hrids inside a trigger's terms, which are shown as JSON (dependency, condition and comparator). An hrid is read by its kind (`/items/`, `/abilities/`, ...) and replaced by its name; one with no name, or of a kind with no table, stays as it is. The words `food 1`, `drink 1`, `ability 1`, `triggers`, `player`, `present`, `absent` and the JSON keys are the code's own words, not ids, and stay.
4. Zone line: under the goal line, "Zone: <name>, tier <N> · base party profit <figure> per user per day" (`zoneLine` in `panel.mjs`): the zone and tier of the request (`options.zone`, `options.tier`; the name is the page's `actionNames` entry in the shown language) and `basePerUser`, the base the search compared against, per user. The base figure shows for a profit goal only. When `basePerUser` is below 0 (the raw field) a line under it says the party loses money at base here, so a gain means losing less. A result with no zone (an older one) shows neither; one with no `basePerUser` shows the zone only.
5. Folds: the grey singles and the "Priced, over budget" list each sit closed behind one toggle (`data-whatif-more="<id of the list it opens>"`; open on click, closed on a second click; a redraw, such as a language change, closes them). The over-budget heading keeps its count.
6. Skipped swaps: when the result has a non-empty `dominated` group (the equip swaps the search never offered because they are no better on any stat, `whatif-runner.md`), one line after the over-budget list reads "N swaps skipped (no better on any stat)" with a Show / Hide toggle on it; the list (`<player>, <desc>` per row, `desc` through `localizeDesc` like the other lists, so game names and the same player-lead rule) sits closed behind it, in the same fold as the other two (`data-whatif-more="whatIfDominated"`). N is the group's length; nothing is computed. An absent or empty group (an older result) shows nothing.
7. Helps the party, costs its buyer: a non-empty `result.helpsParty` (rows the party test passed and the buyer test refused, `whatif-runner.md`) shows a group after "Each change alone" with the heading `result.helpsParty` and the hint `result.helpsPartyHint`, the same columns as "Each change alone", no Apply button. Those rows (`helpsParty: true`) are left out of "Each change alone"; the Apply keys of the other rows keep their indexes in `singles`. An absent or empty field (an older result) shows no group and no hint.
7. Skipped for want of an export: when the result has a non-empty `skippedNoExport` group (`whatif-runner.md`), one folded line after the skipped-swaps line reads "N players skipped by <lever names>" (N = distinct players, the lever names as the window shows them, `result.skippedNoExport` string) with a Show / Hide toggle; the list ("<Lever name>: <players>" per lever) sits closed behind it (`data-whatif-more="whatIfSkippedNoExport"`). Nothing when absent or empty. Output only.
8. Apply on step n applies the ops of steps 1 to n together; Apply on a single applies its own. An op naming a player no tab is named after applies nothing and names that player.

## Tests

1. `tools/test/whatif-panel.mjs`: the logic and the strings in en, pt and zh.
2. `tools/test/whatif-exports.mjs`: the export map end to end: the window's request, status and result line (pure), the runner's old and new forms, and the optimizer on a generic party (skips, `skippedNoExport`, no throw).
3. `tools/test/whatif-progress-parts.mjs`: the parts across a whole search, the rows the panel draws, the old single line.
4. `tools/test/whatif-window.mjs`: the built page (`dist/`) in our own headless Chrome against a fake runner that implements the interface above; `--shots <dir>` saves dark pictures of the window.
